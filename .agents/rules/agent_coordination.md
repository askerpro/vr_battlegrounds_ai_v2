# Координация задач и контрактов

Код протокола находится в `F:/UnityProjects/agent-infra`, продуктовый вход —
`python Tools/agents/coordination.py`. Состояние всех linked worktree определяется через
`git-common-dir`: `.agent-state/coordination/` основного checkout.

## Активация и действующий флоу

Пока режим `off` или config отсутствует, действует существующий конвейер AGENTS.md.
Новый runtime и строгий режим включаются только в подготовленное окно обслуживания,
после регистрации действующих задач. Агенты не меняют режим и общую базу вручную.
Настройку режима выполняет сопровождающий из основного checkout.

Строгий режим требует регистрацию, согласованные контракты и допуск этапа перед записью
или запросом Unity worker. Публикация баз worker, finish и recovery принадлежат editor-broker.
Допуск этапа не является Unity-арендой; во время размышлений Unity-аренду не держать.

## Один документ задачи

Канонический путь: `tasks/<task-id>/Readme.md`. Владелец пишет цель, мотивацию, границы,
архитектуру, короткий план, критерии приёмки и следующие действия. Это компактный обзор
для человека и другого агента: ориентир до 400 слов, без JSON, трассировок и истории обсуждений.
Полный текущий анализ — в соседнем `Details.md`; машинный план — только в `plan.json`.
Схема машинного плана:

- `task_id`, `owner` — стабильные идентификаторы; `client` — `codex`, `claude` или `other`.
- `session_id` — необязательный подтверждённый ID клиентской сессии для дополнительной привязки.
- `worktree` — абсолютный путь своего checkout; `base_sha` — полный SHA принятой базы.
- `doc_path` — точно `tasks/<task-id>/Readme.md`; `title` — краткое название.
- `stages` — этапы с `id`, `writes`, `after`, `needs`. Один worktree исполняет один этап.
- `writes` — точные относительные пути или завершающий `/**`; соседняя `.meta` входит в область ассета.
- `after` — объекты `{"task":"...","stage":"...","state":"verified|accepted|merged"}`.
- `needs` — объекты `{"contract":"...","revision":1,"aspects":["..."],"readiness":"agreed|active"}`.
  Неизвестное влияние объявляется аспектом `*`.

Первичные Readme.md, Details.md и plan.json можно создать до допуска; игровой код на этом
основании не редактируется. Fenced-план в Readme.md поддерживается только для перехода;
при наличии plan.json удалить старый блок, чтобы не было двух источников.
План регистрируется только из своего worktree:

```powershell
python Tools/agents/coordination.py register --document tasks/<task-id>/Readme.md --expected-revision 0
python Tools/agents/coordination.py status
python Tools/agents/coordination.py inbox --task <task-id> --owner <owner>
```

Агент читает сводку других планов и полные документы пересекающихся задач; для Git-документа
ссылка включает ветку `agents/status` либо точный SHA. Основной `dev` может отставать по
документам незавершённых задач. Публикация документов не принимает игровой код.
Хаб хранит ссылки на локальный документ и источник плана. Снимок зарегистрированной ревизии
формируется автоматически: его вручную не редактируют. Изменение локального плана блокирует
начало/продолжение этапа и вливание до обновления регистрации; старый допуск не расширяется.
Остановка этапа и завершение Unity-аренды остаются доступны для безопасного перехода.
При изменении согласованных контрактов требуется обычное согласование ревизии и ACK.

В `agents/status` автоматически публикуются компактный Readme.md, plan.json,
Details.md (если есть), coordination-state.json и общий индекс `tasks/README.md`.
Таблица этапов в обзоре компактная, технические факты и большие структуры вынесены в JSON.

Вспомогательные исходники, архитектурные решения и планы хранятся под Git рядом с
`Readme.md` в `tasks/<task-id>/`. Они входят в `writes` соответствующего этапа;
Readme.md, Details.md и plan.json разрешено обновлять без допуска; исполняемые
вспомогательные исходники требуют допуска этапа. Текущий статус ведётся только в Readme.md.

Материалы задачи: tools/ — временные пробы/утилиты анализа, contracts/ — собственные спецификации,
changelog/<YYYY-MM-DD>-<slug>.md — отдельные записи изменений, reports/ — локальные
сгенерированные/отладочные артефакты вне Git. Шаблоны — [в папке этой задачи](../../tasks/agent-coordination-protocol/templates/Readme.md).

Долгоживущие утилиты обслуживания проекта — в Tools/<категория>/; их создание или
перенос — отдельный пункт с областью записи и проверкой. В задаче остаётся ссылка,
в Tools — единственная поддерживаемая копия. Брокер/прокси/мост по-прежнему в agent-infra.

Собственные обязательства синхронизации — в after/needs локального плана, причины —
в Details.md, важные блокеры — в Readme.md. Хаб хранит подтверждённые контракты/ACK,
допуски, события и очередь вливания, а не вторую вручную редактируемую копию планов.

## Изоляция документов

Задачи не пишут в README.md, Docs/README.md, CHANGELOG.md, Docs/CHANGELOG.md,
Docs/UltimateXR/sdk-patches.md, Docs/Mirror/mirror-patches.md,
Docs/BlazeAI/sdk-patches.md и tasks/README.md. Это также касается новых SDK-журналов
с именем sdk-patches.md / mirror-patches.md в Docs.
Проверка отклоняет эти writes, включая широкие scopes, содержащие общий файл.
Перенести записи изменений в собственный changelog/, номера SDK получать patch-reserve.
Новые материалы задач не создавать в Docs/tasks; чужие папки tasks не объявлять своими.
Старые общие журналы сохраняются как история, их автоматическая консолидация пока не реализована.

В Docs попадают очищенные действующие требования, принятая архитектура и текущее состояние.
Для переноса из задачи — отдельный этап с владельцем тематического файла, без дневника разработки.
Пересечения таких файлов и игрового кода по-прежнему требуют координации.

При переносе существующей задачи владелец меняет `doc_path`, пути в `writes` и ссылки,
удаляет общие индексы/журналы из writes, переносит их будущие записи в свою папку,
регистрирует новую ревизию через `--expected-revision <текущая ревизия>`. Старый документ
становится указателем на новый, а не вторым журналом. Чужие документы и ACK не переносить
от имени их владельцев. Обновление runtime выполняет сопровождающий в окно обслуживания.

Промежуточные результаты, отладочные данные, пробы и отчёты сохраняются локально
в `tasks/<task-id>/reports/` своего worktree. Паттерн `/tasks/*/reports/` исключён из Git.
Запись в `reports` своей зарегистрированной задачи разрешена без допуска этапа;
это не даёт права менять код или отчёты другой задачи. В документе задачи остаются
краткие выводы и явно помеченные локальные ссылки на доказательства.

## Этапы и доказательства

`begin --task ... --stage ... --owner ...` возвращает приватный token. В общие документы
и сообщения token не переносится. Перед записью действует PreToolUse; перед worker —
request/begin/guard брокера, ticket закрепляет task/stage/epoch.

`verify --token ... --sha ... --evidence ...` фиксирует фактическую проверку конкретного SHA.
Её выполняют после finish/recovery собственной Unity-аренды. `accept --task ... --stage ...
--owner ... --sha ... --source ...` фиксирует реальное подтверждение пользователя, его нельзя
выдумывать или выводить из успешной компиляции. Rebase требует проверки и приёмки нового SHA.
`stop` требует безопасного завершения worker; истечение допуска само не освобождает область.

## Контракты и новые требования

Контракт имеет одного владельца. Инициатор использует `change-request`, указывает исходную
ревизию, требование, минимальную правку, аспекты и цену перехода. Владелец использует
`contract-propose`, остальные — `contract-ack`, владелец завершает `contract-agree`.
ACK относится к точной ревизии контракта и прочитанного плана; отсутствие ACK не является согласием.

Спецификация ревизии содержит `summary`, `motivation`, `transition_cost`, `aspects`,
`compatibility` (`additive`/`breaking`), `providing_stage`. Для `structural: true` нужен
`architecture_decision` с источником отдельного согласования. Предоставляющий этап должен
быть новым запланированным этапом: прежнее вливание не доказывает новую реализацию.

Совместимое расширение сохраняет старые допуски. Несовместимое изменение ждёт безопасной
остановки затронутых исполняемых потребителей и блокирует их прежние требования после
согласования. Незатронутые аспекты продолжают работу. Реализация становится active после
проверенного принятого вливания; при отказе остаётся прежний действующий контракт.

## Общение агентов: принятое правило от 2026-10-09

**Inbox хаба — основной канал общения для всех агентов независимо от вендора.**
Каждый координационный запрос, ответ, решение и блокер записывается адресным `message`.
Штатное сообщение — дополнительный сигнал «прочитай inbox», а не отдельный источник
договорённостей. Сначала записать сообщение в inbox, затем уведомить получателя.
Не обещать универсальную доставку или пробуждение.
Хаб остаётся источником планов, согласованных ревизий/ACK контрактов, допусков,
зависимостей и очереди вливания. Решение из переписки записать в документ задачи
и оформить командами контракта до зависимой реализации. Чат сам не меняет контракт.

Один маршрут для любого адресата:

1. Отправитель записывает адресное сообщение через `message --to <task-id-получателя>`:
   своя задача, ссылка на обзор/спецификацию, точная ревизия, требуемое действие,
   зависимый этап. Не пересылать токены, полный чат и большие отчёты.
2. При доступном штатном общении своего вендора отправитель сам уведомляет адресата:
   «прочитай inbox», task-id и event_id. Для другого вендора или недоступной/неподтверждённой
   штатной доставки передаёт эти данные человеку для ручного уведомления.
   Новый чат ради доставки не создаётся.
3. Получатель читает свой inbox и необходимые документы, **всегда записывает ответ
   адресным `message`**, выполняет `ack-events` для конкретных прочитанных и учтённых ID.
   Об ответе уведомляет тем же маршрутом: штатным сигналом либо через человека.
   Если содержательная переписка уже состоялась в штатном канале, её координационные
   запросы, ответы и выводы всё равно записать в inbox до зависимых действий.

```powershell
python Tools/agents/coordination.py message --task <my-task> --owner <my-owner> --to <recipient-task> --kind coordination_requested --body "<краткий запрос и ссылки>"
python Tools/agents/coordination.py inbox --task <my-task> --owner <my-owner>
python Tools/agents/coordination.py ack-events --task <my-task> --owner <my-owner> --event <event-id>
```

Проверять status, свой inbox и актуальные after/needs/контракты при регистрации/возобновлении,
перед begin этапа, новой заявкой/началом работы Unity worker и заявкой на вливание,
а также после уведомления. Если inbox возвращает полную страницу, разобрать её,
подтвердить конкретные события и прочитать следующую; непрочитанное не подтверждать.
Активную Unity-операцию не прерывать ради сообщений: после подготовленного пакета
сначала finish, затем разбор координации. Остановку/finish/recovery не задерживать.

Чтение, доставка человеком и ACK сообщения не означают согласия с контрактом или
выполнения запроса. `contract-ack` относится к точной ревизии и выполняется отдельно.
Нет ответа — нет согласия: зависимая работа ждёт, независимая продолжается.
Обязательства отражаются в after/needs, Details.md и кратком статусе Readme.md;
правила допуска проверяет ядро, а не переписка.

Собственные watch/daemon, клиентские адаптеры, управляемые LLM-сессии и автоматическое
межвендорное пробуждение **отложены решением пользователя**. Новые службы и клиентские
хуки доставки не устанавливать в рамках текущего протокола. Пробы сохранены как
исследование, не как рабочий маршрут. [Принятое решение](../../tasks/agent-coordination-protocol/communication-policy.md).

## Вливание

В строгом режиме прямой push заменяется `merge-request --task ... --stage ... --owner ...
--base <полный SHA origin/dev> --sha <принятый SHA>`, затем `merge-execute --request ... --owner ...`.
Брокер сверяет конкретный SHA, контракты, области и реальную ancestry предшественников в
удалённой dev; в каждый момент выполняется один push. Ожидающая зависимая заявка не блокирует
независимую. Перемещение remote требует rebase и новой проверки. Force запрещён.

После неизвестного результата push — только `merge-recover`, без повторного push.
Успешное вливание возвращает `publish_base_required`: сопровождающий выполняет штатный
`editor-broker.py publish-base --wait --sha <новая принятая база>`.
Отрицательный неопределённый исход сопровождающий разрешает через `merge-resolve` только
после подтверждения завершения операции, с `--expected-remote <наблюдаемый SHA>` и `--source`.
Команда не выполняет push и не может скрыть уже влитого кандидата; при активном процессе
получает отказ. При недостатке доказательств заявка остаётся в recovery.
Номера SDK резервируются через `patch-reserve --key <этап/правка>` после сверки начального
номера при миграции. Одна задача может резервировать несколько разных правок.

## Пределы

Протокол защищает от ошибок координации между сотрудничающими агентами. Кодекс/Claude hooks
проверяют нативные пути; для произвольного shell-кода проверяется допуск, а точные области
повторно проверяются по diff checkpoint и кандидата на вливание. Прямые обходы инструментов
не являются разрешённым маршрутом. Локальный hook не заменяет защиту удалённой ветки.

Полная спецификация, план, проверки и актуальный статус реализации:
[документ задачи](../../tasks/agent-coordination-protocol/Readme.md).
