# Координация задач и контрактов

Код протокола находится в `F:/UnityProjects/agent-infra`, продуктовый вход —
`python Tools/agents/coordination.py`. Состояние всех linked worktree определяется через
`git-common-dir`: `.agent-state/coordination/` основного checkout.

## Активация и действующий флоу

Пока режим `off` или config отсутствует, действует существующий конвейер AGENTS.md.
Проверенный runtime доставляет сопровождающий собственной заявкой в конце общей FIFO,
без плановой паузы и отмены ожидающих заявок. Во время ремонта действует mode off;
возврат строгого режима — отдельное решение пользователя после завершения off-билетов.
Агенты не меняют режим и общую базу вручную.
Настройку режима выполняет сопровождающий из основного checkout.

Строгий режим требует регистрацию, согласованные контракты из `needs` и допуск этапа перед записью
или запросом Unity worker. Публикация баз worker, finish и recovery принадлежат editor-broker.
Допуск этапа не является Unity-арендой; во время размышлений Unity-аренду не держать.

Задача определяется по корню Git checkout, даже когда shell находится в вложенной
папке reports. Относительные пути вычисляются от фактического cwd. Если нужно
вернуться в корень без допуска или после его истечения, выполнить отдельный
`cd "<абсолютный корень своего worktree>"` либо
`Set-Location -LiteralPath "<абсолютный корень своего worktree>"`.
Это исключение проверяет привязку session и разрешает только существующую папку
того же checkout; не добавлять следующую команду через `&&` или `;`.
Удалять текущую папку для восстановления shell не требуется. Возврат не заменяет
renew/stop/begin; управляющий Python-скрипт из вложенной папки вызывается по
абсолютному пути своего checkout или после возврата в корень.

## Задачи, эксперты и ревью (решение 2026-10-17)

Схема заменяет модель «эксперт = owner, один постоянный worktree эксперта, несколько задач».
Причина: задачи почти всегда межзонные, реальные пересечения файлов редки, а согласование зон,
порядка и контрактов стоило часы-дни. Пользу даёт ревью diff экспертом, знающим инварианты зоны.

**Задача = агент.** Одна задача — один агент — один worktree — одна ветка `task/<task-id>`
от свежей `origin/dev`. Агент задачи сам работает во всех зонах, которые нужны задаче.
Создание (worktree, ветка, регистрация и бриф) — одной командой из продуктового main
`F:/UnityProjects/Vr_Battlegrounds_ai`; сначала прочитай её help:

```powershell
python Tools/agents/coordination.py task-new --help
python Tools/agents/coordination.py task-new --task <task-id> ...
```

После создания агент работает в новом worktree. `task-new` не вызывается из worktree другой задачи.

Постоянные сессии экспертов новых задач не ведут. Существующие expert worktree доводят
текущие задачи до merge; новые задачи — только через `task-new`.

**Новая задача или этап.** Новая задача — своя цель, отдельная приёмка пользователем,
независимое вливание или прямое указание пользователя «отдельной задачей». Этап — шаг к уже
согласованному критерию приёмки этой задачи. Несвязанные цели этапами в существующую задачу не добавлять.

**Бриф задачи** обязателен и актуален: цель, мотивация, план с чекбоксами `[ ]`/`[x]`, текущий
статус; он виден на дашборде. Статус обновлять при каждом переходе этапа и в конце сессии.

```powershell
python Tools/agents/coordination.py task-brief --task <task-id> --owner <owner> --expected-revision <N> --goal "<цель>" --motivation "<зачем>" --plan-file <файл плана> --status "<статус>"
python Tools/agents/coordination.py task-brief-show --task <task-id>
```

**Эксперты = знания и ревью.** `experts/<id>/AGENT.md`, `journal/`, `backlog.md` — база знаний
зоны; общие правила — [experts/COMMON.md](../../experts/COMMON.md). Перед правкой путей из `owns`
в `expert.json` агент задачи читает `AGENT.md` этого эксперта. `expert.json` — карта маршрутизации
ревью, а не запрет на запись; task-id в него ради допуска не добавляется. В конце задачи агент
дописывает короткую запись в `experts/<id>/journal/` каждой существенно затронутой зоны: что
изменено, новые инварианты.

**Ревью перед merge** — по каждой затронутой зоне, субагентом-ревьюером с профилем эксперта:

```powershell
python Tools/agents/coordination.py review-request --task <task-id> --stage <stage> --expert <expert-id>
python Tools/agents/coordination.py review-prompt --request <request-id>
```

`review-request` фиксирует base/candidate SHA, `patch_id` diff и снимок промпта с `prompt_hash`.
Агент задачи запускает read-only субагента с выданным промптом; промпт вручную не редактируется.
Ревьюер читает diff и профиль зоны, в хабе не регистрируется: никаких register, route-publish, begin,
Unity или `awake`. Если запись в хаб разрешена, он выполняет единственную выданную команду
`review-ack` с `--prompt-hash` и сводкой через `--summary` или stdin (`--summary-file -`).

Если запись в хаб недоступна (например, Codex read-only sandbox), ревьюер возвращает выданный
`review-prompt` блок `ZONE-REVIEW-VERDICT`, заполнив вердикт и сводку. Автор задачи или владелец зоны
сохраняет его дословный вывод в UTF-8 файле `.md`/`.txt` в ignored `reports/` своей задачи либо подаёт
через stdin и выполняет из своего продуктового worktree:

```powershell
python Tools/agents/coordination.py review-ack --request <request-id> --reviewer-output <файл.md>
```

`request`, `prompt_hash`, `verdict` и сводка берутся из блока; подменять вывод, вердикт или hash нельзя.
Хаб сохраняет вывод с маскированием секретов и аудит `recorded_by=author|owner`, `prompt_confirmed`,
вызывающий worktree и `spawned_by_task` (если передан). Запись approve автором или self-review дополнительно
уведомляет сопровождающего (`zone_review_self_approved`); это не отменяет независимость ревьюера.

Действует последний раунд по задаче/этапу/зоне. ACK привязан к candidate SHA; после rebase без изменения
diff он сохраняется только при совпадении `git patch-id --stable` относительно базы merge-заявки.
Изменился diff — новое ревью. `changes` и `revoked` блокируют вливание при любой политике зон, включая off;
замечания надо исправить новым коммитом. Повторный запрос на тот же SHA и повторный вердикт делегата
не обходят отказ. Владелец зоны может заменить вердикт делегата своим ревью из worktree своей задачи
или отозвать approve штатной командой:

```powershell
python Tools/agents/coordination.py zone-ack-revoke --task <задача владельца зоны> --owner <expert-id> --target-task <task-id> --target-stage <stage> --reason "<причина>"
```

Approve ревьюера не является приёмкой пользователем и не заменяет проверки в Unity/шлеме.
Ревьюер проверяет diff по разделу «Как использовать этот профиль» в `AGENT.md` зоны и общим пунктам:
нет второго писателя состояния, копии факта, обхода инварианта или существующего владельца; сериализованные
ассеты изменены только по цели задачи, identity цела (GUID/`.meta`, `NetworkIdentity._assetId` в prefab);
заявленные проверки реально выполнены на этом SHA. Замечания `changes` — с конкретными путями.

**Сериализованные ассеты Unity** (`.unity`, `.prefab`, `.asset`, `ProjectSettings/**`, `.asmdef`)
не сливаются: одновременно их правит только один выполняющийся этап. Хаб блокирует только такие
пересечения и только для выполняющихся/проверенных этапов. Код `.cs` сливается обычным git
merge/rebase; конфликт решает тот, кто вливает позже.

**Отменено:** zone-request/zone-ack как условие begin; переговоры о порядке ради объявленных
writes; контракт между живыми экспертными сессиями как обязательный шаг (контракт остаётся
инструментом для долгоживущих межзадачных интерфейсов, но не условием правки чужой зоны);
правило «expert = owner, один постоянный worktree эксперта, несколько задач»; обязательное
добавление task-id в `expert.json` ради допуска.
**Без изменений:** очередь Unity worker/editor-broker (FIFO, аренды), merge-request/merge-execute,
вопросы пользователю (AskUserQuestion), inbox/wait-inbox, запрет на чужие ACK/контракты, SDK-патчи.

**Закрытие задачи.** После завершения приёмки и запланированных вливаний owner обновляет бриф и журнал,
затем из своего worktree закрывает задачу с ревизией задачи из `status` (это не ревизия брифа):

```powershell
python Tools/agents/coordination.py task-close --task <task-id> --owner <owner> --expected-revision <N> --reason "<итог>"
```

Команда допускает закрытие, когда все этапы merged/accepted либо ещё не начинались. Закрытая задача
не принимает register/begin; новая цель оформляется через `task-new`. Закрытие не удаляет старые
worktree, WIP, результаты или историю и не заменяет требуемое вливание.

## Один документ задачи

Канонический путь: `tasks/<task-id>/Readme.md`. Владелец пишет цель, мотивацию, границы,
архитектуру, короткий план, критерии приёмки и следующие действия. Это компактный обзор
для человека и другого агента: ориентир до 400 слов, без JSON, трассировок и истории обсуждений.
Полный текущий анализ — в соседнем `Details.md`; машинный план — только в `plan.json`.
Бриф хаба (`task-brief`, раздел выше) — короткая актуальная сводка для дашборда, не замена Readme.md.
Схема машинного плана:

- `task_id`, `owner` — стабильные идентификаторы; `client` — справочная информация
  (`codex`, `claude` или `other`), а не условие допуска или право владения.
- `session_id` — необязательный подтверждённый ID клиентской сессии для дополнительной привязки.
- `worktree` — абсолютный путь своего checkout; `base_sha` — полный SHA принятой базы.
- `doc_path` — точно `tasks/<task-id>/Readme.md`; `title` — краткое название.
- `stages` — этапы с `id`, `writes`, `after`, `needs`. Worktree и ветка `task/<task-id>`
  принадлежат одной задаче; в каждый момент worktree исполняет один её этап.
- `writes` — точные относительные пути или завершающий `/**`; соседняя `.meta` входит в область ассета.
- `deletes` — необязательный список точных путей только для удаления. Без glob и
  права Add/Edit; используется в том числе для старых файлов Docs/tasks.
- `after` — объекты `{"task":"...","stage":"...","state":"verified|accepted|merged"}`.
- `needs` — объекты `{"contract":"...","revision":1,"aspects":["..."],"readiness":"agreed|active"}`.
  Неизвестное влияние объявляется аспектом `*`.

Для запуска выбирай Codex или Claude по доступной квоте. Прежнее значение `client`
не запрещает чтение, начало работы или обновление собственной metadata и не требует
отдельного client CAS handoff. Проверки owner, worktree, ревизии, спецификаций и leases
сохраняются. Смена семейства не очищает чужую `session_id` и не заменяет опубликованный
маршрут другой сессии: подтверждённая привязка продолжает защищать параллельного писателя.
Межзадачное сообщение всегда записывается в canonical inbox; native-доставка возможна
только внутри одного семейства со свежим discovery и проверкой обоих точных адресов.
Совпадение семейства само по себе не доказывает адрес, чтение сообщения или ACK.

Первичные Readme.md, Details.md и plan.json можно создать до допуска; игровой код на этом
основании не редактируется. Fenced-план в Readme.md поддерживается только для перехода;
при наличии plan.json удалить старый блок, чтобы не было двух источников.
План регистрируется только из своего worktree:

```powershell
python Tools/agents/coordination.py register --document tasks/<task-id>/Readme.md --expected-revision 0
python Tools/agents/coordination.py status
python Tools/agents/coordination.py inbox --task <task-id> --owner <owner> --unread --as "<свой адрес name [ref]>"
```

`--document` — всегда `tasks/<task-id>/Readme.md`, не plan.json: plan.json берётся
из той же папки автоматически. В песочнице Codex register/begin/message, `inbox --unread`
и другие пишущие команды coordination требуют escalation: общий хаб вне writable root.
Ошибка `attempt to write a readonly database` означает «повторить с escalation».

Агент читает сводку других планов и полные документы пересекающихся задач; для Git-документа
ссылка включает ветку `agents/status` либо точный SHA. Основной `dev` может отставать по
документам незавершённых задач. Публикация документов не принимает игровой код.
Хаб хранит ссылки на локальный документ и источник плана. Снимок зарегистрированной ревизии
формируется автоматически: его вручную не редактируют. Изменение локального плана блокирует
начало/продолжение этапа и вливание до обновления регистрации; старый допуск не расширяется.
Остановка этапа и завершение Unity-аренды остаются доступны для безопасного перехода.
При изменении согласованных контрактов требуется обычное согласование ревизии и ACK.

В `agents/status` автоматически публикуются компактный Readme.md, plan.json,
Details.md (если есть), coordination-state.json и общий индекс `tasks/README.md`.
Таблица этапов в обзоре компактная, технические факты и большие структуры вынесены в JSON.

Вспомогательные исходники, архитектурные решения и планы хранятся под Git рядом с
`Readme.md` в `tasks/<task-id>/`. Они входят в `writes` соответствующего этапа;
Readme.md, Details.md и plan.json разрешено обновлять без допуска; исполняемые
вспомогательные исходники требуют допуска этапа. Текущий статус ведётся только в Readme.md.

Материалы задачи: tools/ — временные пробы/утилиты анализа, contracts/ — собственные спецификации,
changelog/<YYYY-MM-DD>-<slug>.md — отдельные записи изменений, reports/ — локальные
сгенерированные/отладочные артефакты вне Git. Шаблоны — [в папке этой задачи](../../tasks/agent-coordination-protocol/templates/Readme.md).

Долгоживущие утилиты обслуживания проекта — в Tools/<категория>/; их создание или
перенос — отдельный пункт с областью записи и проверкой. В задаче остаётся ссылка,
в Tools — единственная поддерживаемая копия. Брокер/прокси/мост по-прежнему в agent-infra.

Собственные обязательства синхронизации — в after/needs локального плана, причины —
в Details.md, важные блокеры — в Readme.md. Хаб хранит подтверждённые контракты/ACK,
допуски, события и очередь вливания, а не вторую вручную редактируемую копию планов.

## Изоляция документов

Задачи не пишут в README.md, Docs/README.md, CHANGELOG.md, Docs/CHANGELOG.md,
Docs/UltimateXR/sdk-patches.md, Docs/Mirror/mirror-patches.md,
Docs/BlazeAI/sdk-patches.md и tasks/README.md. Это также касается новых SDK-журналов
с именем sdk-patches.md / mirror-patches.md в Docs.
Проверка отклоняет эти writes, включая широкие scopes, содержащие общий файл.
Перенести записи изменений в собственный changelog/, номера SDK получать patch-reserve.
Новые материалы задач не создавать в Docs/tasks; чужие папки tasks не объявлять своими.
Старые общие журналы сохраняются как история, их автоматическая консолидация пока не реализована.

Для удаления старого документа объявить точный путь в `deletes`, а не в `writes`.
Механизм общий: имена задач и документов не зашиты в runtime. Общие индексы/журналы
и чужие папки tasks не получают исключения. Сначала проверить сохранность нужного
содержимого и ссылки, затем зарегистрировать новую ревизию плана и получить begin.
Codex может использовать нативный Delete File; для любого клиента предусмотрена
узкая команда `coordination.py delete --token <stage-token> --path <точный путь>`
из своего checkout. Она проверяет допуск и удаляет только объявленный файл,
не каталог. Не заменять её произвольным rm/Remove-Item. Хук различает удаление и Add/Edit/Move;
при вливании Git diff обязан содержать D для каждого пути из deletes.
Пересечения deletes с writes/deletes других этапов требуют обычной координации.
Переносить содержимое отдельной записью в свою папку; переименование старого файла
не заменяет явно согласованное удаление. Deletes не разрешает произвольный shell:
для этапа только с deletes доступен узкий Git checkpoint; обычные этапы с writes
сохраняют прежнюю модель доверия shell, окончательную область проверяет Git diff.

В Docs попадают очищенные действующие требования, принятая архитектура и текущее состояние.
Для переноса из задачи — отдельный этап, без дневника разработки; тематический файл зоны
проверяет ревьюер этой зоны. Одновременную правку блокируют только пересечения
сериализованных ассетов Unity (раздел «Задачи, эксперты и ревью»).

При переносе существующей задачи владелец меняет `doc_path`, пути в `writes` и ссылки,
удаляет общие индексы/журналы из writes, переносит их будущие записи в свою папку,
регистрирует новую ревизию через `--expected-revision <текущая ревизия>`. Старый документ
становится указателем на новый, а не вторым журналом. Чужие документы и ACK не переносить
от имени их владельцев. Обновление runtime выполняет сопровождающий в окно обслуживания.

Промежуточные результаты, отладочные данные, пробы и отчёты сохраняются локально
в `tasks/<task-id>/reports/` своего worktree. Паттерн `/tasks/*/reports/` исключён из Git.
Запись в `reports` своей зарегистрированной задачи разрешена без допуска этапа;
это не даёт права менять код или отчёты другой задачи. В документе задачи остаются
краткие выводы и явно помеченные локальные ссылки на доказательства.

## Этапы и доказательства

`begin --task ... --stage ... --owner ...` возвращает приватный token. В общие документы
и сообщения token не переносится. Перед записью действует PreToolUse; перед worker —
request/begin/guard брокера, ticket закрепляет task/stage/epoch.

`verify --token ... --sha ... --evidence ...` фиксирует фактическую проверку конкретного SHA.
Её выполняют после finish/recovery собственной Unity-аренды. `accept --task ... --stage ...
--owner ... --sha ... --source ...` фиксирует реальное подтверждение пользователя, его нельзя
выдумывать или выводить из успешной компиляции. Rebase требует проверки и приёмки нового SHA.
`stop` требует безопасного завершения worker; истечение допуска само не освобождает область.

## Контракты и новые требования

Контракт — инструмент для долгоживущего межзадачного интерфейса. Правка чужой зоны контракта
не требует: её проверяет ревьюер зоны перед merge. Контракт имеет одного владельца. Инициатор использует `change-request`, указывает исходную
ревизию, требование, минимальную правку, аспекты и цену перехода. Владелец использует
`contract-propose`, остальные — `contract-ack`, владелец завершает `contract-agree`.
ACK относится к точной ревизии контракта и прочитанного плана; отсутствие ACK не является согласием.

Спецификация ревизии содержит `summary`, `motivation`, `transition_cost`, `aspects`,
`compatibility` (`additive`/`breaking`), `providing_stage`. Для `structural: true` нужен
`architecture_decision` с источником отдельного согласования. Предоставляющий этап должен
быть новым запланированным этапом: прежнее вливание не доказывает новую реализацию.

Совместимое расширение сохраняет старые допуски. Несовместимое изменение ждёт безопасной
остановки затронутых исполняемых потребителей и блокирует их прежние требования после
согласования. Незатронутые аспекты продолжают работу. Реализация становится active после
проверенного принятого вливания; при отказе остаётся прежний действующий контракт.

## Общение агентов: принятое правило от 2026-10-09

**Inbox хаба — основной канал общения для всех агентов независимо от вендора.**
Каждый координационный запрос, ответ, решение и блокер записывается адресным `message`.
Штатное сообщение — дополнительный сигнал «прочитай inbox», а не отдельный источник
договорённостей. Сначала записать сообщение в inbox, затем уведомить получателя.
Не обещать универсальную доставку или пробуждение.
Хаб остаётся источником планов, согласованных ревизий/ACK контрактов, допусков,
зависимостей и очереди вливания. Решение из переписки записать в документ задачи
и оформить командами контракта до зависимой реализации. Чат сам не меняет контракт.

Один маршрут для любого адресата:

1. Отправитель записывает адресное сообщение через `message --to <task-id-получателя>`:
   своя задача, ссылка на обзор/спецификацию, точная ревизия, требуемое действие,
   зависимый этап. Не пересылать токены, полный чат и большие отчёты.
2. При доступном штатном общении своего вендора отправитель сам уведомляет адресата:
   «прочитай inbox», task-id и event_id. Для другого вендора или недоступной/неподтверждённой
   штатной доставки передаёт эти данные человеку для ручного уведомления.
   Новый чат ради доставки не создаётся.
3. Получатель читает свой inbox (`--unread`) и необходимые документы, **всегда записывает
   ответ адресным `message`**. Inbox — нотификации, не ACK (ACK — `contract-ack` для контрактов/планов).
   Об ответе уведомляет тем же маршрутом: штатным сигналом либо через человека.
   Если содержательная переписка уже состоялась в штатном канале, её координационные
   запросы, ответы и выводы всё равно записать в inbox до зависимых действий.

```powershell
python Tools/agents/coordination.py message --task <my-task> --owner <my-owner> --to <recipient-task> --kind coordination_requested --body "<краткий запрос и ссылки>"
python Tools/agents/coordination.py inbox --task <my-task> --owner <my-owner> --unread --as "<свой адрес name [ref]>"
```

При каждой проверке `inbox --unread` выдаёт непрочитанное по порядку и сразу помечает
выданное прочитанным; при `pagination.has_more=true` повтори вызов (вывод ограничен
`--limit 50` и `--max-bytes 20000`). Кроме сообщений выдаются только актуальные уведомления:
contract_proposed текущей ревизии всем задачам кроме владельца (пока нет твоего
`contract-ack`), contract_agreed/active/rejected по затронутым/needs контрактам,
contract_acknowledged — владельцу, stage_verified/accepted/merged/stopped этапов из after,
пока свой этап не начат. Остальная служебная история — сводкой в `pagination.system_read`
(recent_ids открываются `inbox --event <id>`). `ack-events` вручную не нужен.
Флаг доступен после развёртывания runtime с `inbox --unread`; проверьте `inbox --help`.

Проверять status, свой inbox и актуальные after/needs/контракты при регистрации/возобновлении,
перед begin этапа, новой заявкой/началом работы Unity worker и заявкой на вливание,
а также после уведомления. Каждый новый опрос начинается без cursor: свежие адресные
события идут первыми, затем broadcast-сообщения и служебная история. `pagination`
показывает pending_total, direct_pending, has_more и next_cursor. При has_more читать
следующую страницу с `--cursor <next_cursor>`; это стабильный снимок, не отметка прочтения.
Новые события попадут в следующий свежий опрос. После native-уведомления можно сразу
прочитать `inbox ... --event <event-id>`, даже если событие далеко в истории.
`inbox` без `--unread` и `wait-inbox` ничего не помечают прочитанным. `watch-inbox` устарел:
ожидание — `wait-inbox` фоновой командой (раздел «Inbox и ожидание событий»).
Активную Unity-операцию не прерывать ради сообщений: после подготовленного пакета
сначала finish, затем разбор координации. Остановку/finish/recovery не задерживать.

Чтение, доставка человеком и ACK сообщения не означают согласия с контрактом или
выполнения запроса. `contract-ack` относится к точной ревизии и выполняется отдельно.
Нет ответа — нет согласия: зависимая работа ждёт, независимая продолжается.
Обязательства отражаются в after/needs, Details.md и кратком статусе Readme.md;
правила допуска проверяет ядро, а не переписка.

### Сообщение сопровождающему worker и инфры

Выявленные проблемы worker, брокера, прокси, хуков координации и agent-infra
оставлять на хабе адресно: `message --to agent-coordination-protocol --kind infra_issue`.
В body явно написать «Для сопровождающего worker и agent-infra», затем симптом,
влияние/блокировку, воспроизведение, task/stage, ticket/event_id, SHA и ссылки на
подходящие логи/отчёты. Не отправлять токены или полный чат. Если воспроизведение
не установлено, пометить гипотезу. Сообщение не оставлять только в разговоре с человеком.
После записи уведомить сопровождающего подтверждённым штатным каналом с task-id/event_id
либо передать эти данные человеку. Пользователь прямо разрешил эти уведомления:
не запрашивать отдельное разрешение на запись infra_issue или native сигнал.
Исправления и обходы инфраструктуры выполняет только явно назначенный сопровождающий;
владелец занятого worker не меняет маршрутизацию, общие guards, runtime или MCP-пакет.

Сохрани worktree, task/stage, ticket, request/job IDs, runtime/VERSION и redacted
ошибку со ссылками на доказательства. Read-only status/log/help разрешены.
При неизвестном исходе Unity-операции не делать retry/replay, clear_stuck или recover
и не освобождать активную операцию через finish. После подтверждённого завершения
своего подготовленного пакета и cleanup сразу выполнить штатный finish; при блокере
передать состояние сопровождающему. Недоступность inbox/native канала сообщить человеку,
инфраструктуру не обходить. Продолжать независимую разрешённую работу, включая
исправления собственной игровой/SDK-задачи и сборки в своём build checkout.
Роль сопровождающего сохраняется при переносе его checkout; адрес task-id остаётся тем же.

### Inbox и ожидание событий

Inbox задачи разбирает ведущая сессия — та, что опубликовала свой адрес через route-publish.
Всегда вызывайте
`python Tools/agents/coordination.py inbox --owner <owner> [--task <task>] --unread --as "<свой адрес из первой строки ListAgents, name [ref]>"`.
Сейчас хаб в режиме warn: вызов без `--as` ещё отмечает события, но возвращает
`binding_warning`. После перевода в enforce (сопровождающий, по решению пользователя) сессии
без `--as` или с чужим адресом получат события задач ведущей сессии только для просмотра:
отметки нет, задача указана в `pagination.view_only_tasks`, повторять бесполезно. Чужой адрес
в `--as` не копируйте. Если ваш адрес сменился — route-publish для каждой своей активной задачи.
`ack-events` за ведущую сессию не используйте; если он вернул `route_warnings`, сообщите ей
task-id/event_id. Новые события ждите фоновой командой (Bash, run_in_background):
`python Tools/agents/coordination.py wait-inbox --owner <owner> --as "<адрес>"`.
Она ничего не отмечает и завершается одной JSON-строкой: `inbox_ready` — выполните команду
из `command_argv` (`instruction` — та же команда строкой для Bash), обработайте события и снова
запустите wait-inbox; `timeout` (через 12 ч) — просто перезапустите; `error` — не перезапускайте
wait-inbox, пока `coordination.py status` не проходит успешно. `watch-inbox` устарел.
Периодические будильники, Monitor-циклы и ScheduleWakeup для проверки хаба не используйте.

### Вопросы пользователю

Вопросы и решения пользователю задаются только инструментом AskUserQuestion, а не обычным
текстом в конце хода. Пока висит AskUserQuestion, ход не завершён: пробуждения встают в очередь,
и вопрос не тонет среди них. Перед вопросом доделать всё, что можно без ответа. Варианты давать
с рекомендацией первым; свободный ответ пользователь даёт через Other. Stop-хук возвращает ход,
если последнее сообщение похоже на вопрос обычным текстом; если это не вопрос — завершить ход
без вопросительной формулировки. Открытые вопросы видны на доске в полосе «Ждут вашего ответа»
и в `coordination.py questions --open`.

Перед AskUserQuestion разобрать inbox: contract-ack и ответы другим агентам. Открытый
диалог замораживает межагентную координацию задачи до ответа человека. Напоминание о старом
неотвеченном вопросе не создаёт новый диалог.

Если на пробуждение (завершилась фоновая команда, уведомление субагента) нечего сообщить —
одна короткая строка или ничего.

Собственные службы доставки/daemon, клиентские адаптеры, управляемые LLM-сессии и автоматическое
межвендорное пробуждение **отложены решением пользователя**. Новые службы и клиентские
хуки доставки не устанавливать в рамках текущего протокола. Пробы сохранены как
исследование, не как рабочий маршрут. [Принятое решение](../../tasks/agent-coordination-protocol/communication-policy.md).

### Адресация штатных уведомлений

task-id, owner, UUID плана и native endpoint — разные идентификаторы. Адрес хранится
отдельно от plan.json/контрактов/допуска: смена сессии не меняет архитектурную ревизию.
При старте/возобновлении **основной агент** читает свежий штатный listing и публикует
только собственный адрес из своего зарегистрированного checkout. Claude: первая строка
ListAgents содержит точный `name [ref]`; имя без ref, сырой ref и UUID плана не подходят.
Подагент видит principal и не публикует его endpoint как собственный адрес другой задачи.

Из status взять native_route.epoch: 0 при отсутствии. Например, после собственного
ListAgents (значения заменить на фактические, чужие адреса не угадывать):

```powershell
python Tools/agents/coordination.py route-publish --task <task-id> --owner <owner> --channel claude-code-peers --address "<name> [<ref>]" --expected-epoch <epoch>
python Tools/agents/coordination.py route-resolve --task <sender-task> --owner <sender-owner> --to <recipient-task>
```

native_candidate содержит адрес-кандидат, обе binding и requires_native_discovery=true.
Это не подтверждение доступности/доставки. Перед SendMessage отправитель получает
свежий **полный** ListAgents и сверяет точное name/ref получателя и собственную первую
строку с sender_binding. При смене своего адреса повторяет самопубликацию. Только после
сверки использует точный `to` в штатном инструменте. Нельзя массово уведомлять похожие имена.
Неполный/неоднозначный список, отсутствующий ref или отказ native resolution требуют
ручного переноса task-id/event_id человеком; событие остаётся в inbox.

manual с reason возвращается для missing/cleared/stale binding, неизвестного адресата,
разных client/channel. Epoch — CAS счётчик записи, updated — её время; произвольный TTL
не заменяет свежий discovery. Дубли client/channel/address разных задач запрещены.
Проверка owner/checkout кооперативная, native identity не аутентифицируется хабом.
При недоступной адресации основной агент из своего checkout очищает маршрут:

```powershell
python Tools/agents/coordination.py route-clear --task <task-id> --owner <owner> --expected-epoch <epoch> --reason "native discovery или адресация этого клиента недоступны"
```

Clear сохраняет tombstone с новым epoch, старый epoch не оживляет адрес. Команды
работают без begin и не меняют plan revision/permit, не публикуют Git-документы и не шлют
сообщений сами. Codex collaboration текущего дерева не является глобальным каталогом
других чатов: `/root` не рекламировать как межсессионный адрес. Inbox остаётся основным
каналом независимо от наличия route; согласование контрактов и ACK по прежним правилам.

## Вливание

Перед заявкой на вливание нужен approve последнего раунда по каждой затронутой зоне для того же SHA
или сохранённого `patch_id` после rebase без изменения diff (раздел «Задачи, эксперты и ревью»).
Изменённый diff требует нового ревью; `changes`, `revoked` и approve другого diff блокируют вливание.
В строгом режиме прямой push заменяется `merge-request --task ... --stage ... --owner ...
--base <полный SHA origin/dev> --sha <принятый SHA>`, затем `merge-execute --request ... --owner ...`.
Брокер сверяет конкретный SHA, контракты, области и реальную ancestry предшественников в
удалённой dev; в каждый момент выполняется один push. Ожидающая зависимая заявка не блокирует
независимую. Перемещение remote требует rebase и новой проверки. Force запрещён.

После неизвестного результата push — только `merge-recover`, без повторного push.
Успешное вливание возвращает `publish_base_required`: тот же агент подаёт долговечный
`python Tools/agents/editor-broker.py request-base --owner <owner> --task <task-id>
--sha <полный принятый SHA> --source-root <свой worktree> --key <уникальный ключ>`.
Это служебный тикет общей FIFO: системный процесс брокера сам выполняет публикацию,
после предыдущих заявок, без LLM и без аренды/действующего этапа у подавшего агента.
Команда проверяет фактически полученную origin/dev и общий Git. Повтор того же key
идемпотентен; уже опубликованный SHA завершается без переключения и отката базы.
Результат приходит в inbox как base_publication_result. QUEUED ещё не означает
опубликованную базу; перед worker проверить DONE и текущую базу.
Maintenance pause, активная аренда, Play/dirty worker блокируют выполнение, не теряя запрос.
Сбой переключения требует штатного recovery сопровождающим. Старый синхронный
publish-base остаётся инструментом сопровождающего.
Отрицательный неопределённый исход сопровождающий разрешает через `merge-resolve` только
после подтверждения завершения операции, с `--expected-remote <наблюдаемый SHA>` и `--source`.
Команда не выполняет push и не может скрыть уже влитого кандидата; при активном процессе
получает отказ. При недостатке доказательств заявка остаётся в recovery.
Номера SDK резервируются через `patch-reserve --key <этап/правка>` после сверки начального
номера при миграции. Одна задача может резервировать несколько разных правок.

## Пределы

Протокол защищает от ошибок координации между сотрудничающими агентами. Кодекс/Claude hooks
проверяют нативные пути; для произвольного shell-кода проверяется допуск, а точные области
повторно проверяются по diff checkpoint и кандидата на вливание. Прямые обходы инструментов
не являются разрешённым маршрутом. Локальный hook не заменяет защиту удалённой ветки.

Полная спецификация, план, проверки и актуальный статус реализации:
[документ задачи](../../tasks/agent-coordination-protocol/Readme.md).


## Аварийный режим PreToolUse с аудитом

Пользователь разрешил временно снимать локальные координационные hook-блокеры под его
ответственность, пока сопровождающий исправляет инфраструктуру. Владелец включает режим
только для своей зарегистрированной задачи и checkout, с конкретной причиной и ссылкой
на infra_issue. Режим действует максимум 3600 секунд; после срока обычный hook возвращается
автоматически. CLI доступен после штатного runtime deployment; сначала прочитай его help.

Решение пользователя от 2026-10-15: прежнее общее разрешение на локальный emergency-hook
не заменяет явного назначения на инфраструктурный ремонт и не разрешает обход
infra-блокера без такого назначения. Режим не даёт права самостоятельно ремонтировать
общий хаб, worker, broker/proxy или MCP. Явные разрешения на собственную игровую/SDK-задачу
и build-исправления сохраняются. Общий mode off также не назначает агента сопровождающим.

```powershell
python Tools/agents/coordination.py emergency-hook-on --help
python Tools/agents/coordination.py emergency-hook-on --task <task-id> --owner <owner> --ttl 3600 --reason "infra_issue <event_id>: точная блокирующая операция"
python Tools/agents/coordination.py emergency-hook-off --task <task-id> --owner <owner> --reason "блокер снят"
python Tools/agents/coordination.py emergency-hook-stats --task <task-id>
python Tools/agents/coordination.py emergency-hook-log --task <task-id> --after 0 --limit 50
```

Если задача закреплена за session, передай её подтверждённый `--session-id`. Режим не
передаёт ownership, не принимает игровую работу и не меняет контракты или ACK. Проверки
чужой сессии/checkout и сетевого push сохраняются. Координационные CLI-проверки, FIFO,
claim/begin/guard/renew/finish worker и Unity MCP proxy продолжают работать; старый
`configure --mode off` для этой цели не использовать.

Журнал фиксирует включение/выключение/истечение и каждую попытку вызова под активным
режимом: task, owner, client/model как метаданные, checkout, session, срок, причину,
tool input с удалёнными секретами, обычное решение hook и фактическое решение допуска.
Это журнал попыток и решений PreToolUse, а не подтверждение выполнения команды.
Без успешной записи аудита emergency-допуск не выдаётся. Сопровождающий разбирает
статистику по задачам, инструментам и причинам отказа и использует её для исправлений.
Токены и необработанные tool input не переносить в inbox или отчёты.

Перед rebase сохраняй актуальный план отдельно: stash может вернуть старую редакцию
`plan.json` и вызвать REVISION. Не регистрируй старый план поверх canonical. Восстанови
только точный актуальный план из проверенного снимка через native apply_patch метаданных,
получи begin своего существующего этапа, сохрани план отдельным metadata commit и затем
выполни обычный rebase. Сохранённый stash не удаляй до проверки возврата изменений/.meta.


## Полное временное отключение coordination gate

По прямому поручению пользователя сопровождающий переключил общий хаб в `mode off`
на время ремонта. В этом режиме локальные PreToolUse и координационный SCOPE/PERMIT
в broker admission отключены; registration/begin ради допуска локального инструмента
не нужны. FIFO, собственная RUNNING-аренда Unity, renew, snapshot/result/recovery,
проверка published B и внутренние проверки coordination CLI сохраняются.

Выключатель общий для всех checkout, включая Codex и Claude, rebase/restart не нужен.
Команда ниже исполняется сопровождающим один раз; повторять выключение не требуется:

```powershell
python Tools/agents/coordination.py --repo "F:/UnityProjects/Vr_Battlegrounds_ai" --state-dir "F:/UnityProjects/Vr_Battlegrounds_ai/.agent-state/coordination" configure --mode off
```

Source-fix `53f6760cb27a5b54e7aee1b8c34e0d98743f5389` добавляет best-effort redacted
аудит каждого вызова hook и его would-block через прежние emergency-hook-stats/log.
После deployment аудит не требует зарегистрированной задачи и не блокирует команду
при ошибке/lock БД; отсутствующий реестр не пересоздаётся. Решение hook не означает,
что команда исполнена. Клиентский sandbox/OS permissions этим режимом не меняются.

Не включайте `enforced` самостоятельно: сначала сопровождающий дожидается завершения
QUEUED/OFFERED/active заявок, созданных в off (они имеют coordination=null), проверяет
актуальность локальных планов и выполняет тот же configure с `--mode enforced`.
Режим off не принимает чужую игровую работу и не меняет ownership/контракты/ACK.
До восстановления enforcement сохраняйте чужие checkout и согласованные границы.
Этот режим заменяет предыдущий запрет на configure off именно по поручению пользователя;
индивидуальный TTL emergency-hook-on остаётся отдельным режимом при enforced.


## Точные неизменяемые input components

Source c72db11a06bb4cfc1d76c4142f692949cf476ab3 добавляет opt-in technical input-grant
и request --input-components/--input-components-sha256. Это отдельный поддерживаемый
контракт, который сохраняет writes/outputs и проверяет чужие байты/GUID/SDK reservation.
Provider может явно выдать grant из PLANNED providing stage своего scope; consumer
ссылается на grant и собственные recorded verified dependencies. Точная инструкция
[immutable inputs](F:/UnityProjects/agent-infra/docs/immutable-input-components.md).

Mode off по поручению пользователя остаётся общим; прежний request без components
работает как прежде. Новые manifests полностью проверяются даже в off. TTL1200,
expiry/revoke запрещают новое admission; RUNNING pinned receipt позволяет безопасно
finish/capture/restore. Полный R/ref сохраняется перед отказом при изменении компонента.
При новом B/revision/epoch нужен новый manifest/input, прежние inbox-разрешения сами
не становятся grants. Публикует grant только владелец; не назначайте себе чужие writes,
ACK или gameplay acceptance. Откат только через текущий deploy preflight совместимости.
