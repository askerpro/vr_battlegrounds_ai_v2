# Правила: Расследование багов (Debugging)

> **Никогда не начинать с открытия кода. Сначала — контекст.**

## Шаг 1 — Читать `known-issues.md` (ВСЕГДА первым)
Проверить, не является ли проблема уже задокументированным поведением SDK.
**Файл:** `Docs/UltimateXR/known-issues.md`
Если проблема там описана — использовать готовое объяснение и решение. Если нет — продолжить.

## Шаг 2 — Прочитать `sdk-patches.md`
Проверить, не было ли уже внесено обходное решение для этой области кода.
**Файл:** `Docs/UltimateXR/sdk-patches.md`

## Шаг 3 — Прочитать архитектуру
Понять контекст компонентов, участвующих в проблеме:
- `Docs/README.md` — ключевые скрипты проекта
- `Docs/UltimateXR/architecture.md` — архитектура UltimateXR

## Шаг 4 — Воспроизвести и локализовать проблему
1. Точно описать симптомы: что происходит vs что должно происходить
2. Определить триггер: когда именно воспроизводится
3. Сузить круг подозреваемых компонентов

## Шаг 5 — Читать код
Только теперь открывать исходники:
- Методы жизненного цикла: `Awake`, `Start`, `OnEnable`, `Update`
- Обработчики событий
- Места инициализации компонентов

## Шаг 6 — Исправить и ОБЯЗАТЕЛЬНО задокументировать
После нахождения причины:
1. Исправить баг
2. **Обязательно** добавить запись в `Docs/UltimateXR/known-issues.md`:
   ```markdown
   ## Issue N: [Название]
   **Компоненты:** `ComponentA`, `ComponentB`
   **Статус:** ✅ Исправлено
   **Дата:** YYYY-MM-DD
   ### Симптом
   [Что наблюдалось]
   ### Причина
   [Почему происходило]
   ### Исправление
   [Что было сделано]
   ```
3. Если исправление затронуло исходники UltimateXR SDK — добавить в `sdk-patches.md`

## Шаг 7 — Сохранить в документацию всё неочевидное из кода
> Если был вынужден читать код для понимания базовой логики — документация была неполной. Зафиксируй логику в `Docs/UltimateXR/<модуль>.md` или `Docs/<система>.md`.
