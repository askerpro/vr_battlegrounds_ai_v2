Сформируй коммит. Порядок строгий.

## 1. Проверь, что коммитить разрешено

Коммит **сразу после написания кода запрещён** — пользователь сначала проверяет изменения
в Unity. Исключение: изменения только в `.md`.

Если в диффе есть `.cs`/`.prefab`/`.unity`/`.asset` и пользователь **явно** не подтвердил, что
проверил в игре, — не коммить. Скажи, что готово к проверке, и перечисли, что именно смотреть.

Аргументы команды: $ARGUMENTS

## 2. Посмотри изменения

```
git --no-pager status
git --no-pager diff --stat
git --no-pager diff
```

Определи характер: `feat` / `fix` / `docs` / `refactor` / `chore`.

## 3. Проверь компиляцию

Через Unity MCP, если он доступен. Если нет — `/unity-check`. Ошибки компиляции в коммит
не уходят.

## 4. Обнови документацию

Обязательный шаг, а не опциональный. Сопоставь содержимое диффа с таблицей:

| В диффе | Обновить |
|---|---|
| Новые классы, скрипты, компоненты | `Docs/README.md` |
| Геймплей, режимы, матч | `Docs/gameplay.md` |
| Менеджеры, поток инициализации | `Docs/game-manager.md` |
| Значимое изменение, фикс, рефакторинг | `Docs/CHANGELOG.md` |
| Баг или неочевидное поведение SDK | `Docs/UltimateXR/known-issues.md` |
| Правки исходников UltimateXR | `Docs/UltimateXR/sdk-patches.md` |
| Архитектура, зависимости | `Docs/UltimateXR/architecture.md` |
| Новые правила агента | `CLAUDE.md` или `.agents/rules/` |

## 5. Закоммить

Разбивай на логические единицы, не сваливай всё в один коммит. Формат сообщения:

```
<тип>: <краткое описание на русском>

<что изменилось и почему>
```

Ветка: работай в текущей, если это не `main`. Если `main` — сначала создай ветку.

`post-commit`-хук дублирует коммит в Plastic SCM — это ожидаемо, см. `Docs/version-control.md`.
