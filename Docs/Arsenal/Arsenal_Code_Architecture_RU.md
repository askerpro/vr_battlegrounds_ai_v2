# Арсенал — Архитектура Кода и Жизненный Цикл

Актуальная конструкция: [задний арсенал, ниши и визуальная граница](common-boundary-wall-2026-10-02.md). Корпус CommonOpenArsenalStation неподвижен. `ArsenalBoundaryWall` (историческое имя) координирует только сетевой прогресс оборудования; `ArsenalDeploymentAnimator` применяет его через `ArsenalEquipmentPoses`. Подъём корпуса, движение ограды и маскирование лазерных граней удалены. Принадлежность станции берётся из зоны её `ArsenalStationAnchor`; `TeamSpawnZone` учитывает несколько коллайдеров игрока. `SpawnZoneBoundaryVisual` рисует переднюю грань игровой зоны. `BoundaryOpening` и `ArsenalWallOpenings` формируют реальные ниши меша и коллайдеров в блочной ограде.

Этот документ описывает техническую архитектуру, ключевые скрипты и весь флоу (взаимодействие систем) арсенала в VR Battlegrounds. Предназначен для быстрого погружения ИИ-помощников в контекст проекта без необходимости читать весь код.

## Выдвижное оборудование (2026-10-02)

ArsenalDeploymentAnimator хранит серверный снимок движения в SyncVar и вычисляет прогресс по NetworkTime. ArsenalEquipmentPoses интерполирует редактируемые закрытые/открытые маркеры на всём диапазоне 0–1; задержки подъёма корпуса больше нет. ArsenalRules.IsDeployed означает предоставленное оборудование, ReadyForAccess допускает торговлю после завершения движения, CanTrade также проверяет фазу закупки. RoundPhases ждёт полного убирания оборудования перед Combat. Разметку личного табло ведёт ArsenalStationAnchor; принадлежность показывает ArsenalOwnerHighlight. Старый StandardArsenalWall и подъёмные прототипы удалены, в игре установлен CommonOpenArsenalStation. Единственный стенд — CommonArsenalReview со стеной и production-пересборкой ниш.

## 1. Базовые данные и структуры

### Canonical target poses: source checkpoint

`ArsenalPresentationStyle` хранит defaults `Pegboard`/`Shelf` и абсолютные исключения по exact `(WeaponInfo, Zone)` в одном ассете. Поля ItemTarget/MagazineTarget обозначают effective SDK `AlignTransform` в slot frame, CardTarget — обычную slot-local позу карточки. Отдельных editable item offsets в styled конфигурации нет; старые поля WeaponInfo относятся только к legacy adapter. `ArsenalPreset.PresentationStyle` выбирает стиль; скрытый `ArsenalStationPresetBinding.PresentationPresetCache` — производная ссылка исходного пресета для prefab, runtime источник остаётся MapData.

`ArsenalPresentationResolver` проверяет зоны, ключи исключений, конечность значений, scale и собственный DropAlign. `ArsenalPresentationApplicator` переносит whole anchor root, компенсируя относительный authored AlignTransform, и выводит root pose предмета из prefab DropAlign без изменения scale. Styled contact не сдвигается повторно в runtime: editor Fit/Bake должен сохранять предложенную позу в тот же canonical target. `ArsenalLegacyPresentationAdapter` централизует прежние offsets/custom-card/fallback; ordinary Ensure/installer custom card pose не сбрасывает.

Каждая опора Style имеет явный `ArsenalSupportAnchorKind` (`Weapon`/`Magazine`). `ArsenalSupportModuleBuilder` сохраняет существующие role objects и создаёт производные `PresentationSupports` и `PresentationReturnHints` в тех же `SupportPose`. Один `ReturnReadyMaterial` принадлежит Style. Сигнал привязан к существующему `ActivateOnCompatibleNear`: его видимостью, совместимостью и занятостью управляет SDK, нового поиска или политики возврата нет. `ArsenalMagazineOffer.RejectManualPlacement` продолжает запрещать возврат в склад; декоративный держатель не обещает приём магазина. Runtime preflight проверяет topology/TRS/material/SDK references; чужую near-подсказку генератор не заменяет. Null-style legacy не меняется.

Текущая проверка source hint-среза: изолированный native стенд RED4 → GREEN14, повтор сохраняет instance IDs и serialized JSON, чужие сцены/материал неизменны, Android gate PASS. Отдельный RED подтвердил порядок записи карточки: `MaterializePresentation(slot, snapshot)` сначала применяет frames, затем карточку, затем опоры и полную валидацию; builder и installer используют один endpoint. Старые public overloads сохранены. Это проверка генерации/связей и существующего запрета stock-return, а не проверка поднесения контроллером в шлеме.

Текущий статус: schema и consumers скомпилированы, Android source gate PASS и console0; nested fixture — 31/31, включая uniform parent scale, authored Drop/Align и actual SDK smooth-return endpoint. `IndustrialPegboardPresentation.asset` адресно сохранён с двумя defaults и двадцатью exact exceptions после ручного просмотра render-only предложений. MIT DDD Quickhook использует собственный общий untextured metal; Style содержит общий ready material. Native batch — 11/11: retained module IDs, scene/material/disk invariants. FullDemo пока не ссылается на Style: Demo/Lobby сохраняют legacy вид. Materialized outputs, actual after/regen фотографии, локальная SDK near eligibility и итоговый Bake остаются незавершёнными.

Ядром системы служат ScriptableObjects, которые отвязывают данные снаряжения от конкретной физической реализации слотов стены или инвентаря игрока.

*   `WeaponInfo` (**ScriptableObject**) — Описание конкретного снаряжения (оружия, гранаты, аптечки).
    *   **Префабы**: `WeaponPrefab`, `MagazinePrefab`.
    *   **Опции спавна**: `MaxMagazineCount` (сколько обойм автоматически выдавать в начале раунда).
    *   **Метаданные**: Цена, иконка, категория (`WeaponCategory`), оффсеты для позиционирования.
    *   Является единственным источником истины при расчете стоимости и спавне предметов.
*   `WeaponComponent` (**MonoBehaviour**) — Компонент, навешиваемый на корневой объект (root) инстанцированного оружия префаба. Хранит ссылку на родительский `WeaponInfo`. Служит мостом для систем инвентаря — если игрок держит объект с `WeaponComponent`, мы сразу понимаем, какое это оружие.
*   `WeaponRegistry` (**ScriptableObject**) — Общий реестр всего доступного в игре оружия (для централизованного поиска и валидации).

### Редактор данных и безопасное превью

Единый вход — [окно «Арсенал»](editor-workbench-plan.md): каталог, станции, сборка, взаимодействие и проверки.
`ArsenalEditorStatus` читает состояние, `ArsenalEditorActions` применяет объявленный план под собственной
арендой, `ArsenalBuildPreflight` проверяет весь выбранный набор до writer. Публичные маршруты builders
сохранены; старые Arsenal menu writers не являются отдельной точкой применения. Чтение/выбор не создаёт
превью и не сохраняет данные. Пресет сохраняет порядок, зоны и сетевые индексы; MapData меняет только ссылку.

`ArsenalSlotPreview` строит временную геометрию только из MeshFilter/MeshRenderer: исходные TRS, материалы
и цепочка activeSelf сохраняются, SDK/physics/runtime-компоненты оружия не клонируются. Превью принадлежит
проверенному якорю своего слота; orphan и reload cleanup не затрагивают persistent assets и helper scenes.
`Ensure` сохраняет неизменное превью, но пересобирает его при изменении fingerprint исходника. Подгонка
смещений WeaponInfo через существующий Inspector сохраняется и действует на все станции предмета.
Исходные три «призрака на полу» на скриншоте не были захвачены диагностикой: подтверждён класс нарушения
владения/жизненного цикла превью, а не точный источник каждого объекта того кадра.

`HandsPackWeapon` и `KinemationWeapon` создают модель в собственной изолированной PreviewScene и очищают
её при исключении/Dispose. Readiness KIN читается без reimport через `ReadableSourcePaths/RequireReadable`;
Read/Write включается только явным импортным writer. Конструкторы отвергают Play Mode до поиска ассетов.

Карточка `ArsenalPriceTag` остаётся в прежнем rect/pose: Normal wrap, auto-size 0,6–1 от базового размера
и Overflow сохраняют длинный заголовок и все строки статистики. Темп карточки показывает фактическую
целочисленную частоту SDK: metadata 400/мин округляется до 7/с, то есть 420/мин.

## 2. Иерархия контроллеров стены арсенала

Сцена арсенала разбита на модульные компоненты-контроллеры для соблюдения SRP.

*   `ArsenalWallController` (**NetworkBehaviour**) — Корень и оркестратор. Владеет состоянием стены (`Closed`, `Opening`, `Open`, `Closing`) — **общим, серверным**, см. [раздел 2.1](#21-стена-общая-состояние-серверное-t-15-находка-net-07). Управляет дочерними слотами. **Конкретных режимов не знает** — исполняет правила активного режима (`MapReferee.Instance.ActiveGameMode`):
    *   `GameMode.ArsenalRules` — состояние, стена сверяется с ним каждый кадр (`ApplyModeRules`): открыта ли (пишет только тот, кто вправе — сервер или стена вне сети, `CanWriteState`; так сохраняется NET-14: незаспавненная стена ведёт состояние сама), нужен ли жетон (каждая машина), заменять ли пропавшее оружие через `_lostWeaponReplaceDelay` (сервер). Elimination отвечает по фазе раунда (открыта только в `Equipment`), лобби (`WarmupMode`) — «открыта всегда, жетона нет, пропавшее заменяется». Режима нет — стена не трогается.
    *   `GameMode.ArsenalRefillRequestedServer` (событие экземпляра режима; стена подписывается в `OnStartServer` и переподписывается по `MapReferee.ActiveGameModeChangedLocal` — режим на карте меняется на месте) — разовое пополнение пустых слотов `ReplenishWeaponsNetwork(false)`; Elimination поднимает его на входе в `Setup`. Событие, а не свойство: `Setup` бывает короче кадра. Серверный канал, а не клиентский обработчик с `if (isServer)` — тот на выделенном сервере не исполнялся никогда (находка NET-06).
*   `ArsenalSlotController` (и наследник `FirearmSlotController` с отдельным MagAnchor) — управляют одной конкретной ячейкой на стене или полке. Запасными настоящими магазинами отдельно владеют `ArsenalMagazineSupply` и `ArsenalMagazineOffer`; сетевой контракт и защита поздней привязки описаны в [магазинах арсенала](arsenal-magazines.md). Слоты отвечают за:
    *   Спавн/Деспавн конкретного `WeaponInfo`.
    *   Блокировку (`Lock`/`Unlock`) возможности взять предмет.
    *   Ответ на вопрос «занят ли слот» — `CurrentItem` / `IsItemPresent`, см. [раздел 2.2](#22-занятость-слота-два-источника-t-15-находка-net-13).
    *   Нотификации о взятии (`OnItemTaken`) и возврате (`OnItemReturned`) предмета для пересчета бюджета (в разработке). **Внимание:** для оружия, выданного по сети, эти события не срабатывают — см. раздел 2.2.
*   `ArsenalAnimator` (**MonoBehaviour**) — Инкапсулирует логику анимации. Обрабатывает плавное поднятие/выдвижение полки и опускание рольставней (шторки) стены. Содержит callback'и `OnOpenComplete` / `OnCloseComplete`. Анимирует только при смене позы: повторное «открыть» открытой стене — пустая команда с немедленным колбэком, смена направления посреди анимации разворачивает её с текущей позы. Триггеры контроллера не подаёт (залежавшийся триггер срабатывал циклом позже) — состояния запускаются через `Animator.Play`. Позы покоя держат `Idle_Closed` (кадр 0 клипа) и `Idle_Open` (последний кадр, Motion Time = `OpenedPoseTime`).
*   `DogTagController` (**MonoBehaviour**) — Отвечает за контроль жетона игрока. Бросает событие `OnTagGrabbed`, которое сигнализирует о готовности игрока завершить стадию prep (досрочно закрыть стену).
    *   Живёт во вложенном префабе `Assets/Prefabs/Arsenal/DogTag/DogTagPanel.prefab`: `DogTagPanel` (контроллер) → `DogTagAnchor` (`UxrGrabbableObjectAnchor`) и `DogTag` (`UxrGrabbableObject`). Префаб — вся панель, а не один жетон: связь `Start Anchor` жетона с якорём должна жить внутри одного ассета, иначе она снова станет переопределением экземпляра.
    *   Закрытая стена запрещает брать жетон через `IsGrabbable = false` (`Disable`), а не выключением компонента: выключенный `UxrGrabbableObject` стирает запись о захвате у того, кто его держит, и отпускание падает с «RuntimeManipulationInfo not found». `ResetTag` возвращает `IsGrabbable = true`.
    *   При старте раунда по таймеру (`RoundStartRule.Timer`, см. [gameplay.md](../gameplay.md#готовность-к-раунду--явное-состояние)) стена зовёт `DogTagController.SetInUse(false)`: жетон и якорь прячутся, панель остаётся активной.
    *   Якорь — отдельный дочерний объект, а не компонент на `DogTagPanel`: его трансформ — точка крепления, которую двигают независимо от панели; на одном GameObject помещается только один якорь, а доска по дизайну рассчитана на несколько крючков; логика контроллера и механика SDK не смешиваются.
*   `ArsenalPurchaseTimerDisplay` (**MonoBehaviour**, на корне `DogTagPanel`) — табло обратного отсчёта закупки на месте жетона. Видно только при `RoundStartRule.Timer` в фазе `Equipment`; остаток берёт из `EliminationMode.EquipmentTimeRemaining` (локальный расчёт от реплицированного старта фазы), по сети ничего не шлёт. Текст, если не назначен, создаёт сам — 3D TextMeshPro шрифтом проекта, лицом в −Z панели (к игроку).

### 2.1. Стена общая, состояние серверное (T-15, находка NET-07)

> **С T-45 у стены есть владелец.** Объект и состояние (открыта/закрыта) по-прежнему общие, но при экономике матча
> покупать со стены может один игрок — тот, за кем она закреплена (`[SyncVar] _ownerSessionNetId`, раздаёт
> `ArsenalOwnershipPolicy` по зоне спавна стены, правило — `ArsenalOwnership`). Подробности — [раздел 6](#6-экономика-и-покупка-t-45).

**Решение: стена общая.** Одна стена — один объект, и все игроки видят её одинаково.
Персональной стены (отдельного объекта на игрока) в проекте нет: с T-45 общая стена лишь закреплена за владельцем-покупателем.

Почему так, а не «у каждого своя»:

*   Стена лежит **в сцене карты** как сетевой объект (`NetworkIdentity` + `sceneId`), а не спавнится под игрока. На `TestMap1` их восемь, и это восемь общих объектов, а не восемь личных.
*   Её **содержимое уже авторитетно**: `ReplenishWeaponsNetwork` спавнит оружие через `NetworkUxrIdentity.SpawnServerObject` и раздаёт его слотам реплицируемым словарём «индекс слота → `netId`». Состояние самой стены было единственным, что осталось локальным, — это выглядело недоделкой, а не замыслом.
*   **Готовность игрока** — отдельное состояние и уже реплицируется правильно: `PlayerSession.HasGrabbedDogTag`. То есть «я готов» и «стена закрыта» — разные вещи, и персональная стена для первого не нужна.

Как это устроено:

| | |
|---|---|
| Источник правды | `[SyncVar(hook = nameof(OnStateSynced))] ArsenalWallController._currentState` |
| Кто пишет | только сервер (`SetState`), у клиента вызов пустой и пишет предупреждение в лог |
| Кто применяет к представлению | `ApplyStateLocal` — анимация, блокировка слотов, жетон |
| Что закрывает стену | **только выход из фазы `Equipment`** (T-29): `EliminationMode.ArsenalRules.IsOpen == false` → `ApplyModeRules` на сервере → `SyncVar` → все |
| Захват жетона | стены не касается: объявляет готовность игрока (`PlayerSession.CmdSetReady`) |
| Поздний клиент | получает актуальное состояние начальным значением спавна |

Три места раздачи и идемпотентность — ровно как у фазы раунда: на выделенном сервере хук
`SyncVar` в сеттере не срабатывает (Mirror зовёт его только при `NetworkServer.activeHost`),
поэтому `SetState` раздаёт вручную; на хосте раздача проходит дважды, и второй вызов обязан
быть пустым. Гашение — по значению, полем `_appliedState`.

Промежуточные состояния (`Opening`, `Closing`) тоже реплицируются: каждая машина проигрывает
свою анимацию, но **объявляет** её завершение только сервер. Иначе слоты разблокировались бы
у каждого в своё время, и стена перестала бы быть общей.

`requiresAuthority = false` у команды не случайность: стена — объект сцены, владельца среди
клиентов у неё нет и быть не может.

### 2.2. Занятость слота: два источника (T-15, находка NET-13)

Предмет попадает в слот двумя разными путями, и учёт у них разный:

| Путь | Кто ведёт учёт | Что видно |
|---|---|---|
| Игрок кладёт предмет руками | `UxrGrabManager` | `UxrGrabbableObjectAnchor.CurrentPlacedObject` |
| Сетевая выдача `AssignNetworkItem` | сам слот, через `SetNetworkAnchor` | то же `CurrentPlacedObject` |

`AssignNetworkItem` перепарентит под якорь объект, уже заспавненный Mirror'ом, и через
`UxrGrabManager` не проходит — а сеттер `CurrentPlacedObject` `internal`, извне его не
выставить. Поэтому опираться только на `CurrentPlacedObject` было нельзя: для **всего**
оружия на стене он оставался null, `IsItemPresent` — false, `NeedsReplenishment()` — true
навсегда. Прогон яруса C показал это прямо: 64 слота из 64 с реально заспавненным оружием,
`IsItemPresent` при этом — 0.

Теперь занятость отвечает `CurrentItem`: сперва `CurrentPlacedObject`, затем — выданный по
сети предмет, **если он жив и всё ещё висит под якорем**. Второе условие обязательно:
при захвате `UxrGrabManager` перепарентит предмет к аватару (`UseParenting` включён по
умолчанию), и слот обязан опустеть. Через `CurrentItem` работают и `Lock()`/`Unlock()` —
до T-15 они молча не делали ничего, потому что искали предмет там же.

С 2026-08-22 сетевая выдача **заводит учёт UltimateXR сама**:
`UxrGrabbableObject.SetNetworkAnchor(anchor)` тихо выставляет `CurrentAnchor` и
`CurrentPlacedObject` — без событий и без канала синхронизации (Патч 6 в
[`../UltimateXR/sdk-patches.md`](../UltimateXR/sdk-patches.md)). Тихо намеренно: публичный
`UxrGrabManager.PlaceObject` обёрнут в `BeginSync` и породил бы на каждую выдачу сетевое
событие, а у клиента — ещё и команду серверу «положи предмет», то есть подмену авторитета.
Благодаря этому `UxrGrabManager` при захвате поднимает у якоря `Removed`, и события
`OnItemTaken` / `OnItemReturned` наконец рождаются — `ArsenalWallController.OnSlotChanged`
жив, будущей экономике есть на что опереться (была находка NET-17).

### 2.3 Что показал настоящий захват (замер 2026-08-22, исправлено в тот же день)

Сценарий яруса C `arsenal-item-grab` берёт оружие по-настоящему —
`UxrGrabManager.GrabObject`, тем же входом, что и рука в шлеме. Замер вскрыл два
независимых отказа; оба закрыты, сценарий зелёный 5 прогонов подряд.

* **Сервер не узнавал о захвате (NET-16).** Событие захвата до сервера **доезжало**
  (канал состояния двусторонний с T-12), но отвергалось: `UniqueId` заспавненного
  в рантайме оружия на сервере и у клиента был **разный**. Пока это было так,
  **ни одно** событие манипуляции (захват, выстрел, магазин) не могло быть
  применено на другой машине — арсенал был лишь первым местом, где это заметили.

  Чинится не в арсенале: идентичность — свойство объекта, а не того, кто его выдал.
  Владелец — `VrBattlegrounds.Network.NetworkUxrIdentity`, он же гасит «Auto Anchor»,
  из-за которого клиентский инстанс рождался внутри лишнего родителя. Стена просто
  спавнит через него вместо сырого `NetworkServer.Spawn`.

* **Слот у клиента не знал своего предмета (NET-23).** `RpcAssignItemToSlot`
  — одноразовое сообщение, и уходило оно в тот момент, когда клиент ещё грузит карту
  и не `isReady`. Замер: 128 строк `Assigned network weapon` в серверном логе, ноль
  в клиентском. Визуально стойки полны, но `IsItemPresent` у клиента `false`, и
  `Lock()`/`Unlock()` его оружие не трогали — закрытая стена не запрещала взять предмет.

  Теперь привязка — **состояние**: `SyncDictionary<int, uint>` на стене, индекс слота →
  `netId` предмета, раздача в `OnStartClient` и по `OnChange`. Переживает и позднее
  подключение, и смену карты. Применяется не сразу: Mirror кладёт объект в
  `NetworkClient.spawned` раньше, чем включает его, а `UxrGrabbableObject.Awake` сбросил бы
  привязку — неприменённые ждут в очереди, пока предмет не станет `activeInHierarchy`.

Стена отдаёт свои слоты наружу через `ArsenalWallController.Slots` — тот же порядок,
которым привязка их адресует, и он одинаков во всех процессах.

**Массив слотов заводит одна точка** — `EnsureSlotArray`, признак — `SlotsInstalled`.
Авторская станция берёт слоты из сериализованного поля или иерархии. Сгенерированная станция
(`ArsenalStationCompositionBinding.Mode == Generated`) иерархию не читает — порядок детей не порядок
манифеста — и ждёт `InstallGeneratedSlots(слоты)`: сборщик вызывает его один раз, в порядке индексов
манифеста; повтор, пустой набор, null или дубль — отказ. До установки привязки по индексу копятся
(спавн и `SyncDictionary` приходят раньше сборки станции); после неё индекс вне массива — именованная
ошибка `GameLog.Arsenal`, а не молчаливая потеря. Склад магазинов (`ArsenalMagazineSupply`) проверяет
индекс по тому же признаку стены.

## 3. Выдача экипировки игроку

Автоматическая выдача боеприпасов перенесена со стены в личный менеджер игрока, чтобы избежать проблем с ownership и RPC, а также корректно сканировать текущий лоадаут (даже если игрок взял пушку из другой слотовой области, не со стены).

*   `PlayerLoadoutManager` (**NetworkBehaviour**, корень аватара) — серверная выдача магазинов в карман своего игрока. Режимов и фаз не знает: у него две операции — `ServerEnsureMagazines(perWeapon)` («досыпь по N к каждому оружию», `0` — по `MaxMagazineCount`) и `ServerClearMagazines()`. Оружие ищет сам: руки и все якоря аватара, где лежит предмет с `WeaponComponent`.
    *   **Решает сервер:** он видит руки и кобуры игрока (захваты реплицирует UltimateXR), команды от клиента нет.
    *   **Карман — состояние:** `SyncList<uint>` с `netId` магазинов; каждая машина прячет их в карман этого аватара сама, в том числе поздний клиент (тот же вывод, что NET-23 у слотов). Убирает магазины только сервер — `NetworkServer.Destroy`.
    *   Сколько выдать и что выкинуть при нехватке места — `MagazineRefillPlanner` (чистая логика, `MagazineRefillPlannerTests`).
*   **Политики — когда пополнять:** `RoundMagazineRefill` на префабе `EliminationMode` — к `Countdown` карман собирается заново; `WarmupMagazineSupply` на префабе `WarmupMode` — раз в 0,5 с по одному магазину к каждому оружию (бесконечный карман).
*   `UxrMagazinePocket` — прячет магазины выключенными. `ForceStoreItem` идемпотентен (на хосте его зовут сервер и клиент одного процесса). Захват спрятанного магазина, пришедший по сети с машины владельца, достаёт его из кармана сам (`Grabbing`); уход магазина из кармана — событие `ItemReleased`, по нему сервер снимает магазин с учёта.

## 4. Полный флоу раунда (Sequence)

Ниже пошагово описано, как работают скрипты от начала фазы подготовки до непосредственной стрельбы.

### Шаг 1: Подготовка (Prep Phase)
1.  **Фаза раунда**: сервер входит в `Setup` — режим поднимает `GameMode.ArsenalRefillRequestedServer`, стена пополняет пустые слоты (`ReplenishWeaponsNetwork(false)`), оружие уезжает клиентам через `NetworkUxrIdentity.SpawnServerObject`, а привязка «слот → предмет» — реплицируемым словарём стены.
2.  **Открытие Стены**: фаза `Equipment` — **сервер** переводит `_currentState` в `Opening`. Клиенты получают состояние `SyncVar`'ом.
3.  **Анимация**: `ArsenalAnimator` отыгрывает открытие на каждой машине. Завершение анимации **объявляет только сервер**: он переводит состояние в `Open`.
4.  **Разблокировка**: состояние `Open` применяется везде — `_allSlots` получают `Unlock()`, жетон сбрасывается `ResetTag()`. До этого момента оружие на стене не хватается: слот применяет блокировку и к предмету, выданному по сети.

### Шаг 2: Взаимодействие игрока (Interaction)
1.  Игрок руками берет Weapon с полки (UxrGrabber захватывает UxrGrabbableObject).
2.  Игрок кладет Weapon в свою кобуру (`UxrGrabbableObjectAnchor` на бедре или за спиной).
3.  **Слот реагирует**: `ArsenalSlotController` фиксирует отсутствие предмета на своем snap-якоре и стреляет `OnItemTaken` и `ItemTakenBy` (с рукой); на сервере стена поднимает `ItemTakenServer`, и касса (`ArsenalCheckout`, T-45) списывает цену с владельца стены или отменяет захват.

### Шаг 3: Готовность (Lock In)
1.  Игрок хватает свой Dog Tag (Жетон).
2.  `DogTagController` отлавливает захват и стреляет `OnTagGrabbed`.
3.  `ArsenalWallController.HandleTagGrabbed` объявляет готовность **своего** игрока: `player.Session.CmdSetReady(true)` плюс `CmdSetDogTagGrabbed(true)` как запись самого жеста. Стену жетон не трогает.
4.  Раунд выходит из фазы `Equipment`, **когда готовы все живые игроки** (`RoundReadiness`) либо когда истёк предел ожидания.
5.  **Сервер** реагирует на смену фазы и переводит состояние стены в `Closing`; оно уезжает всем. Стена закрывается **у всех** одновременно (общая стена — T-15, находка NET-07).
6.  **Блокировка**: при применении `Closing` каждый слот получает `slot.Lock()`. Возвращать оружие на стену больше нельзя.
7.  Запускается анимация закрытия `ArsenalAnimator.PlayCloseSequence`; переход в `Closed` снова объявляет сервер.

> **Почему жетон больше не закрывает стену (T-29, дефект RDY-01).** Правило «взял жетон —
> арсенал закрылся» родилось, когда стена у каждого игрока была своя. После T-15 стена
> одна на всех, и то же правило стало означать другое: первый взявший жетон закрывает
> арсенал **всем**, и второй игрок остаётся без снаряжения. Теперь жетон — жест,
> объявляющий готовность, а закрытие — следствие общей готовности. Разбор готовности —
> [`gameplay.md`](../gameplay.md#готовность-к-раунду--явное-состояние).

### Шаг 4: Старт Раунда (Round Active)
В момент когда гейммод переводит всех в активную стадию (`RoundPhase.Active`), происходят два важных процесса **параллельно**:

**Отложенная очистка стены:**
1. Если стену не закрыли жетоном, её закрывает фаза: в `Countdown`/`Combat` правило режима говорит «закрыта», и `ApplyModeRules` на сервере переводит состояние в `Closing`.
2. ~~Вызываются деспавны (`slot.DespawnItem()`)~~ — **этого в коде нет.** `DespawnItem()` не вызывает никто: оружие, которое игрок не взял, остаётся висеть на стене за закрытыми ставнями. Проверено поиском по `Assets/Scripts` (2026-08-19).

**Магазины (`RoundMagazineRefill` → `PlayerLoadoutManager`):**
1. На сервере `RoundMagazineRefill` ловит `Countdown` и у каждого игрока зовёт `ServerClearMagazines()` и `ServerEnsureMagazines(0)`.
2. Менеджер собирает оружие игрока (руки и якоря аватара, предметы с `WeaponComponent`), по `WeaponInfo` узнаёт `MagazinePrefab` и `MaxMagazineCount`. Одинаковое оружие считается один раз.
3. Магазины спавнятся сервером через `NetworkUxrIdentity` и попадают в `SyncList` кармана — клиенты прячут их у себя.

### ИТОГ: Раунд начался!
У игрока в разгрузке нужные обоймы для выбранного оружия, а стена арсенала закрыта стальными ставнями до следующего раунда — одинаково у всех игроков.

### Вне раунда: лобби

**Слот-дом.** `WeaponComponent.HomeSlot` — слот, выдавший оружие; ставится один раз при выдаче
(`AssignNetworkItem`) и не меняется, какой бы путь ни прошёл ствол. `LooseItemSweeper` в лобби
возвращает оружие, пролежавшее на полу 30 с, домой через `ServerReturnHome`: запись в `_slotItems`
(OP_SET уходит и при том же значении), каждая машина раскладывает ствол сама. Слот пополняется
новым, только если его ствол пропал совсем (`_homeItems[i]` уничтожен) — `ServerReplenishLostSlots`.

**Слот принимает оружие руками.** Якорю слота `Awake` добавляет тег префаба и валидатор «тот же
`WeaponInfo`, стена открыта» (Issue 16 в known-issues), расширяет радиус укладки до висячей позы
плюс 10 см и после укладки возвращает позу из `WeaponInfo`. Повешенный руками ствол сервер
записывает в `_slotItems` (`HandleItemReturned`).

В `Lobby.unity` активен режим `WarmupMode`, и стена исполняет его правила тем же путём, что
на карте: `ArsenalRules` = «открыта, без жетона, пропавшее заменяется». Сервер держит стену
открытой (`ApplyModeRules` открывает её при любом `Closed`/`Closing`) и через
`_lostWeaponReplaceDelay` (2 с) выдаёт замену слоту, чей ствол пропал совсем
(`ServerReplenishLostSlots`). Жетона нет на каждой машине — ответ режима, а не флаг стены.
Разбор — [`gameplay.md`](../gameplay.md#лобби--режим-с-одной-командой-lobbymode).

## 6. Экономика и покупка (T-45)

Покупка — взять ствол со **своей** стены в фазе `Equipment`. Числа и решения — [T-45](../tasks/T-45-economy.md).

| Кто | Что делает | Где исполняется |
|---|---|---|
| `ArsenalOwnershipPolicy` (префаб `EliminationMode`) | стены в зоне спавна команды → игрокам команды по одной → `wall.ServerSetOwner` | сервер, раз в 0,5 с |
| `ArsenalWallController.RefreshOffers` | по деньгам владельца (`MatchEconomy.Current`) раздаёт слотам `SlotOffer` | каждая машина, пустой без изменений |
| `ArsenalSlotController.ApplyOffer` | `IsGrabbable` (только автор мира — сервер, Issue 23); свет, приглушение ствола блоком свойств, ценник `ArsenalPriceTag` | захват — сервер, вид — все |
| `ArsenalGrabRule` (в `GrabRules`) | рука не владельца или без денег ствол со стены не берёт | машина игрока (удобство, не защита) |
| `ArsenalCheckout` (префаб `EliminationMode`) | `ItemTakenServer` → списать (`MatchEconomy.ServerTryPurchase`) или отменить (`ServerRejectTake`: отпустить, `ServerReturnHome`); `ItemReturnedServer` → возврат по чеку этого раунда | сервер |
| `ArsenalWalletDisplay` | табло над панелью жетона: имя владельца, `$деньги`, «+доход» | каждая машина, только чтение |

Без экономики (разминка, Respawn) `SlotOffer.Free`: всё берёт кто угодно, ценники и табло скрыты.
Стартовый пистолет со стены не берётся — он сам ложится в кобуру (`StartingSidearmPolicy`); Viper на полке можно
купить ещё (200).
