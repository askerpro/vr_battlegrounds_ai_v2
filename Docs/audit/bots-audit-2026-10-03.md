## Текущая система

`BotDirector` хранит обычные `PlayerSession` без соединения. `BotMind` переживает смену тела;
директор создаёт исполнителей на новом аватаре. `ServerAuthoredAvatar` переводит существующие
`NetworkTransform` в `ServerToClient`. Это полезная основа для замены боевого поведения.

Цепочка боя сейчас:

1. `BotSenses.NearestEnemy` выбирает ближайшего живого противника из реестра игроков.
2. `BotGunner` отдельно выбирает ближайшего противника до 40 м и проверяет один луч из ствола.
3. `BotOrders` возвращает `Hunt` либо `Engage`.
4. При `Hunt` директор отправляет ноги **в точку под головой врага**; при `Engage` останавливает.
5. `BotNavigator` получает углы NavMesh, а `BotRoute.Step` сам сдвигает `BotBody.Feet` по ломаной.
6. `BotBody` ставит голову и кисти; UltimateXR затем решает IK. Оружие взято настоящим захватом,
   стрельба идёт через `TryToShootRound` с проверкой `StateEventAuthority`.

В коде нет приказа «идти в центр карты». Схождение к центру — ожидаемое следствие взаимной
погони за ближайшими противниками с разных баз. Для конкретной карты это нужно подтвердить траекториями.

## Находки

| Приоритет | Нарушенное допущение / класс проблемы | Подтверждение и следствие |
|---|---|---|
| P1 | Маршрут считается достаточным для безопасного движения среди игроков | `BotNavigator.Update` вызывает `BotRoute.Step` и `WalkTo`. В этой цепочке нет `NavMeshAgent`, локального избегания, проверки капсулы или разрешения встречного движения. Аватары исключены из источников сетки. Радиус сетки помогает обходить статическую карту, но не разводит ботов. |
| P1 | Преследование заканчивается в координате врага | `BotDirector.Think`, ветка `Hunt`: `GoTo(BotSenses.FeetOf(enemy))`. Нет минимальной боевой дистанции, свободного места рядом с целью или разных подходов союзников. Если луч не разрешает стрельбу, бот продолжает сближаться вплотную. |
| P1 | Конец любого маршрута считается достижением цели | `BotNavMesh.TryPath` принимает всё, кроме `PathInvalid`, включая `PathPartial`. Конец частичного пути может быть далеко от врага. После `_arrived=true` `BotNavigator.GoTo` не пересчитывает почти прежнюю цель: `same && _arrived` даёт ранний выход. Это подтверждённый механизм вечной остановки у недоступной цели. |
| P1 | Ошибка навигации разрешает движение без препятствий | При отсутствии сетки/пути `BotNavMesh` возвращает прямой отрезок. Исполнитель не проверяет геометрию перед шагом. Ошибка первого построения также не повторяется на той же сцене: `EnsureBuilt` выходит по `_sceneHandle`. Нужны явный отказ и восстановление, а не небезопасный запасной маршрут. |
| P1 | Видимый враг автоматически делает стояние правильной тактикой | В Combat у `BotOrders.Decide` только Hunt/Engage; `Engage` всегда останавливает ноги. Нет укрытия, смены позиции под огнём, отхода, обхода, прикрытия союзника или удержания направления. Улучшение точности не добавит эти решения. |
| P1 | Произвольные координаты кисти заменяют оружейную позу | `BotBody.CaptureHands` запоминает положение кистей из префаба; левая рука всегда возвращается туда. `BotGunner` берёт оружие только правой рукой, точка хвата 0. Правая рассчитывается из положения ствола в 0,55 м от условной груди, без проверки длины рук и опоры левой кисти. Общая поза не различает пистолет и винтовку. |
| P2 | Ближайший противник равен воспринимаемой и пригодной цели | `BotSenses.NearestEnemy` знает позиции всех живых врагов независимо от зрения/слуха. Не хранит последнюю видимую позицию. Ближайший скрытый враг может вытеснить более дальнего видимого: видимость проверяется после выбора, альтернативная цель не выбирается. |
| P2 | Один луч в центр тела описывает огневую позицию | `BotGunner.Sees` проверяет только центр общих bounds твёрдых дочерних коллайдеров. Частично открытый противник может считаться скрытым. Навигация и стрелок выбирают цели независимо; `SeesTarget` — результат отдельного Update. Нет единого снимка «цель → восприятие → позиция → разрешение выстрела». |
| P2 | Пустой магазин не должен менять поведение | `BotGunner` мгновенно вызывает `SetAmmoLeft(capacity)` перед выстрелом. Нет времени перезарядки и связанного с ним выбора безопасного места. Это действующее упрощение, не полноценная механика перезарядки. |
| P2 | Отсутствие Rigidbody означает неподвижность | `BotNavMeshSources` не исключает геометрию с одним `Animator` или `NetworkIdentity`. Такая геометрия может попасть в однократную сетку; динамические изменения окружения не обновляются до смены сцены. |

### Почему именно «лбами стоят» пока нельзя свести к одной причине

Сближение без дистанции и избегания подтверждено. Остановка возможна по разным причинам:
конец частичного пути, точка под врагом достигнута при запрещённой стрельбе, неверная/перекрытая
линия ствола или отказ стрельбы настоящего оружия. При живом повторении нужен один снимок пары:
`Feet`, расстояние, приказ, выбранная цель, `SeesTarget`, путь/его статус и конец, `Arrived`,
положение/направление ствола, первый коллайдер луча, ammo/CanUse/authority. Без этого точная
причина наблюдаемой остановки остаётся гипотезой.

В текущей ветке `Assets/Art/Animations/Locomotion` отсутствует. `BotBody`/`BotGunner` не подключают
эти клипы. Первой целью анимационного пилота должны быть Rifle_IdleAiming, Rifle_WalkForward,
Rifle_WalkLeft/Right, Rifle_IdleCrouchingAiming и PistolIdle, а не весь набор сразу.

**Предлагаемый способ для пилота:** отдельный анимационный риг бота получает базовую позу из
немаскированных клипов, затем прицеливание и опора второй руки корректируют цели кистей.
Один исполнитель передаёт итоговые голову/кисти существующему UltimateXR и их сетевому каналу.
Это сохраняет контракт неподвижного корня аватара. Способ требует визуальной проверки:
передача трёх целей не гарантирует полного сохранения силуэта клипа после VR-IK.

У UltimateXR уже есть `SolveBodyIK`, а у текущего LegsAnimator-моста — восстановление таза в
позу префаба. Поэтому подключать Animator, FinalIK и старую постановку кистей одновременно
нельзя без договора о том, кто и на какой стадии пишет каждую кость/цель. Обычный NPC с
полной анимацией тела — возможная альтернатива, но потребует отдельного решения для
сетевой позы, хитбоксов и замены тела; для первого пилота это больший объём работ.

## План пилота без разработки своих «мозгов»

1. **Один NPC и одна небольшая карта.** Импортировать выбранный пакет в изолированную работу;
   сначала прогнать его штатную shooter-демо и удостовериться, что нужное поведение действительно есть.
2. **Развести владельцев.** Директор проекта ведёт сессию, фазу, закупку и замену тела;
   пакет решает боевое движение/укрытие; единственный игровой исполнитель ведёт позу и стрельбу.
   Старая ветка Hunt/Engage не должна одновременно назначать боевой маршрут.
3. **Подключить перемещение.** Пакету нужен движущийся агент в точке `Feet`, а корень VR-аватара
   сейчас неподвижен. Проверить возможность отдельного навигационного агента с передачей результата
   в тело. Не добавлять второй независимый движитель и не объявлять связь готовой до проверки.
4. **Подключить бой через адаптер.** Цели/команды и живость — из `PlayerSession`/`PlayerController`;
   выстрел — через настоящее оружие, `CanUse`, ammo и `StateEventAuthority`. Урон — только штатный
   путь попадания. Боевой AI работает на сервере; клиент воспроизводит позу. Если API выбранного
   пакета не позволяет такую границу, пересмотреть пакет до большого переноса.
5. **Подключить Rifle/Pistol-позы.** Базовая анимация → прицел → обе кисти/хваты → существующая
   репликация. Учесть реальную длину оружия и рига, а не общую фиксированную точку ствола.
   Смерть, смена скина и оружия освобождают старые ссылки и подключают новое тело.
6. **Согласовать укрытия с игрой.** `CoverClass.Hard` останавливает пули; Soft простреливается,
   Visual закрывает обзор, но не защищает. Обычный collider/слой пакета не гарантирует защиту.
   Позиции выбирать по настоящим секциям геометрии и доступности; разметку выводить из
   существующих данных карты, а не вручную назначать независимые теги.

Пилот должен доказать применимость пакета. Увеличение точности или добавление случайного
движения в `BotOrders` не заменяют этот этап.

## Приёмка пилота и последующая проверка

| Сценарий | Наблюдаемый результат |
|---|---|
| Два встречных бота в проходе; бот и человек | Разводятся или уступают, сохраняют проходимую дистанцию; не стоят друг в друге и не проходят стены. |
| Недоступный враг / частичный или отсутствующий путь | Есть явное восстановление/другой подход; нет вечного Arrived и движения напрямик через препятствие. |
| Видимый дальний враг, ближний скрыт | Выбирается воспринимаемая пригодная цель; нет слежения за невидимой актуальной позицией без причины. |
| Бой у Hard/Soft/Visual, высокое и низкое укрытие | Бот использует действительную защиту и выходит для стрельбы; меняет позицию под давлением, не объявляет сетку бронёй. |
| Rifle/Pistol, ходьба/страф/приседание | Обе кисти имеют осмысленный хват, локти не выворачиваются, ствол направлен в цель, руки не уезжают за пределы рига. |
| Смерть, призрак, респавн, смена карты/скина/оружия | Сессия и счёт сохранены, старое тело/оружие не остаются авторами, новые ссылки восстановлены. |
| Хост и отдельный клиент | Один выстрел и одно попадание; клиент видит ту же позу, не принимает свои тактические решения. |
| ПК-хост и Quest-хост, несколько ботов | Замерены первый bake, CPU решения/навигации/IK, GC и кадровое время; выводы принимаются по измерениям. |

После подтверждения механики пользователем закрепить принятую логику тестами. Текущие
`BotOrdersTests` фиксируют Hunt/Engage; их ожидания придётся пересмотреть при замене Combat-политики.
`BotRouteTests` проверяют шаг и отбор источников, но не взаимное избегание и восстановление после
`PathPartial`; `BotAuthorityTests` проверяет расположение проверки автора в исходнике, а не два клиента.
Проверки сессий, фаз, закупки и авторства следует сохранить. При правках состава аватаров обновить
`AvatarLoadoutTests` и `PrefabCompositionTests` вместе с принятой конфигурацией.

В этом аудите тесты новой механики не создавались и существующие ожидания не переписывались.
