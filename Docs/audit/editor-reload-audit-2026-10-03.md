Дата: 2026-10-03. Unity: 6000.4.1f1. Текущее состояние: применены upstream discovery-фиксы
MCP 10.2.0 и выключена встроенная интеграция UVCS на этой машине после подтверждения
10-секундного таймаута. Два итоговых обычных Domain Reload: **4,749 / 4,819 с**.
Ниже сначала приведены исходный аудит и диагностический профиль, затем итоговая
проверка фиксов. Прежняя многосекундная стоимость Mono.JIT и повторные reload внутри

## Проверенные гипотезы и оставшиеся кандидаты

### 1. Полные обходы типов в пакете MCP

Исходный пакет 10.1.2: `Library/PackageCache/com.coplaydev.unity-mcp@8bd91ce7bd3a/`.
После обновления этот cache Unity удалила; текущая версия находится в embedded-папке.

- `Editor/Services/Transport/TransportCommandDispatcher.cs`: статический конструктор
  вызывает EnsureInitialised и регистрацию команд.
- `Editor/Tools/CommandRegistry.cs`: AutoDiscoverCommands перечисляет все сборки,
  вызывает GetTypes и дважды фильтрует типы через GetCustomAttribute.
- `Editor/Services/ToolDiscoveryService.cs`: после TypeCache выполняет полный
  AppDomain-обход безусловно и объединяет результаты. Комментарий называет его
  fallback, но он выполняется и при успешном основном поиске.

Класс потенциальной проблемы: общий eager-поиск всех типов вместо одного
индекса метаданных на домен. Предпочтительное направление при подтверждении
стоимости — общий индекс на TypeCache; fallback только при доказанном пропуске
сборок с сохранением пользовательских MCP tools. Просто удалить fallback нельзя:
он добавлен для состояний перезагрузки, в которых TypeCache пропускает типы.
На этапе исходного аудита пакет не патчился. TransportCommandDispatcher занял 2,432 с в диагностическом
цикле, включая 0,859 с Mono.JIT и большое число аллокаций. Это измеренная стоимость,
но она существенно меньше нескольких встроенных Unity callbacks. Отдельный
ToolDiscoveryService и обычный непрофилированный цикл ещё не измерены.

### 2. GitHooksInitializer

`Assets/Editor/VR_Battlegrounds/VersionControl/GitHooksInitializer.cs:9` запускает
`git config core.hooksPath .githooks` при каждой перезагрузке и вызывает
WaitForExit без таймаута на основном потоке.

Класс проблемы: внешняя синхронная настройка среды в повторяемом lifecycle callback.
Предпочтительное направление — отдельная проверка настройки один раз за сессию,
ограниченное ожидание и наблюдаемый отказ.

Контрольное чтение `git config --get core.hooksPath` пять раз: 25,208–34,091 мс,
среднее 27,532 мс. Это другая команда: замер не доказывает время записи из
конструктора, но оснований приписывать Git многосекундную задержку сейчас нет.
Во внешнем снимке процессов активного git.exe не найдено. В подробном
контролируемом цикле весь GitHooksInitializer занял 62 мс: он не является
основным источником задержки этого цикла.

### 3. Восстановление редакторских объектов

- `ArsenalSlotEditorBase.OnEnable` выполняет AssetDatabase.FindAssets для реестра
  и ArsenalSlotPreview.Ensure для выбранного слота.
- `ArsenalSlotPreview` после каждой перезагрузки ставит EnsureAll в delayCall;
  тот обходит загруженные сцены и стадию префаба. Это отложенная работа, её нельзя
  автоматически включать в замер статического конструктора.
- `BlockoutPainter.OnEnable` читает реестр через AssetDatabase.LoadAssetAtPath.
  В просмотренной реализации сам по себе не запускает создание всего реестра.

Подробный профиль показывает большую стоимость встроенных DockArea/SceneView,
TextMeshPro, URP и UxrAvatar.OnValidate. BlockoutPainter занял 8 мс.
Отложенный ArsenalSlotPreview.EnsureAll отдельно не измерен.
Большинство собственных InitializeOnLoad-конструкторов, просмотренных в аудите,
подписывают события или устанавливают delegates; массовых FindAssets в них не найдено.
SDK locators UltimateXR перебирают сборки при поиске типов; обновление symbols в
UxrSdkManager защищено флагом updated. Из этого кода не следует бесконечная
перекомпиляция при каждом запуске.

## Процедура при повторном замедлении

Получены подробный диагностический цикл и обычный цикл после перезапуска.
Следующая проверка нужна при повторении симптома; дополнительные принудительные
циклы без нового симптома не требуются. Бинарную запись не загружать. В исходном
аудите закрытие окон и изменение пакетов не выполнялись; применённые позже фиксы описаны ниже.

1. При повторном замедлении зафиксировать обычный цикл, состояние очереди,
   возраст процесса, нагрузку и изменения файлов до любых вмешательств.
2. Сравнивать обычные циклы с одинаковым состоянием кода/сцены и отдельно учитывать
   ожидание запуска, число перезагрузок и время одной перезагрузки.
3. При необходимости повторить EnableDomainReloadTimings без бинарной записи;
   его подробное дерево уже работает в локальной 6000.4.1f1. Не вызывать
   constructors повторно вручную. После замера восстановить настройки.
4. Проверить причины стоимости Mono.JIT и отдельно отложенные callbacks.
   Не удалять Input System или Multiplayer Play Mode на основании одного
   диагностического профиля без проверки используемых функций и контрольного замера.
5. В контролируемой серии сравнить сборку после одного сохранённого пакета с
   повторными запросами. Сохранить причины запросов и число reloads на Refresh.
6. Менять только подтверждённого виновника и повторять тот же замер. Уменьшение
   числа циклов и уменьшение времени одного цикла учитывать отдельно.

Источник механизма markers:
[Unity EditorAssemblies.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Editor/Mono/EditorAssemblies.cs).
Локальная 6000.4.1f1 подтверждает наличие переключателя и подробного дерева
в Editor.log. GetDiagnosticSwitch имеет непубличную видимость; для временного
диагностического вызова использована reflection.
