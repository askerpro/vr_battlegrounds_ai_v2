## Единый реестр метрик по приоритету проверки

Приоритет задаёт порядок технического ревью, а не важность эмоций или художественных целей.
P0 — физические инварианты; P1 — возможность играть задуманные контакты и маршруты;
P2 — настройка характера карты. Наличие измерения не означает, что задан допустимый порог
или что карта прошла проверку. Статус относится к реализации инструмента, результат конкретной
карты хранится в её паспорте.

| Статус | Единое значение |
|---|---|
| Есть | Механическая проверка или измерение реализованы для явно указанной области применения |
| Частично | Есть ограниченная выборка/эвристика; оставшаяся часть требует ревью или доработки |
| Можно автоматизировать | Технический критерий сформулирован, действующей проверки ещё нет |
| Ручная оценка | Решение принимается человеком; числовая метрика не доказывает качество |

Обязательные пункты с частичной проверкой остаются обязательными: автоматический отчёт
не заменяет недостающую ручную часть. Возможность автоматизации — очередь работ, а не обещание
существующей проверки. Алгоритмы и пороги сверять с `LevelDesignRules`; новое правило добавлять
по [контракту развития метрик](map-rule-development.md).

## Общий вход и смысл результата

`MapEvaluation.Evaluate(map, built, layout, profile)` использует MapAnalyzer,
MapFeedbackRules и PositionImpactAnalysis. MapPrinciplesReport и PositionImpactReport
получают общий результат через MapEvaluationScene; сетка и Visibility строятся один раз.
Генератор должен вызывать это же ядро, а не собственную копию критериев.

Результат разделён на нарушения, непроверенные обязательные пункты, измеренные
контакты/маршруты и диагностические замечания. Неизвестный профиль, отсутствие JSON,
ошибка входных данных или исчерпание бюджета не подтверждают готовность.
`measurementsComplete` относится к запрошенным контактам/маршрутам и D/C:
оно не доказывает полноту контактов всей карты. Недоступный заявленный маршрут — нарушение;
нулевой контакт пары оценивается относительно замысла паспорта.

`readyForPlaytest` не становится true автоматически: сохранение ручных подтверждений
в оценщике не реализовано. Ревью записывается в паспорт конкретной версии геометрии.
После изменения размеров алфавита старые отчёты сцен требуют повторного замера.

В сцене измерения используют реальные коллайдеры; искусственные тестовые карты —
пролёты сетки. Выборочные лучи не доказывают отсутствие всех щелей, всех поз
и всех незаявленных контактов. Шаг блокаута 0.3 м и шаг анализа 0.1 м имеют разные задачи;
клеточная разметка не отменяет проверку реальной геометрии.

Клеточная стена должна предоставлять настоящий замкнутый collider, сохраняющий
Hard/Soft/Visual исходного укрытия. Секции одного объекта не должны создавать
дублирующие объёмы и искусственно увеличивать число пробитий из-за разбиения.
ShotLine использует текущий WallPenetration. Входы сортируются по расстоянию;
после пробития Soft луч продолжается за выходной гранью с тем же ExitOffset,
поэтому вложенный физический столб внутри пройденного объёма не считается
новой Hard-преградой. Отдельный Hard за выходом по-прежнему блокирует прострел.
Обратный поиск выхода требует
отдельной проверки диагональных стыков. Приёмка редактора не означает подтверждённое
пробитие каждой формы и каждым оружием.

Занятость для строительства и для навигации имеет разные вертикальные диапазоны.
Перемычка может быть допустима для строительства и не мешать проходу;
запрет строительных пересечений не заменяет измерение clearance тела.
LD-50 остаётся эвристикой AABB: общий прямоугольный габарит ступенчатой стены
не позволяет достоверно найти её остаточные щели.

## Две независимые пространственные характеристики

`MapSpatialMetrics.Measure` возвращает версию 1, точность и число реальных LOS-запросов.

**D — плотность преград для перемещения:** число `Blocked` клеток вне баз / все клетки вне
баз. Свободная доля равна `1-D`. Это объединение клеток, а не число ассетов: перекрытие не
удваивается. Пол, Vaultable и верхние пролёты вне полосы тела не входят. Это не полная
проекция декорации, не число позиций и не размер самой большой свободной площадки.
Учитывается существующая сетка MapGridBuilder без отдельной копии геометрии.
В сцене Blocked получается из общего MapCellFootprint: проверяется пересечение
настоящего коллайдера с объёмом клетки в полосе тела. Частично задетая клетка
учитывается целиком, поэтому D — консервативная клеточная оценка, зависящая от
шага сетки; это не точная площадь мешей. Результат сохраняет cellStep и
occupancyMode. Пересечения нескольких объектов не удваивают площадь.

Для резервирования выращивателем тот же снимок содержит Touched — след всех
препятствий над полом, и Owners — все связанные с клеткой блоки. Touched может
быть true при Blocked=false: например, верхняя перемычка или перешагиваемый
объект. Клетки не задают толщину материала: LOS и ShotLine остаются запросами
по настоящим коллайдерам. После изменения игровых коллайдеров на арт-пассе
снимок и измерения пересчитываются.

**C — закрытость горизонтального обзора:** образцы доступной боевой зоны с радиусом 0.5 м,
шаг по сетке около 0.5 м, 16 равномерных направлений. Для каждого луча расстояние до
границы прямоугольной сетки — `Dedge`, до первого перекрытия обзора — `Dvisible`.
Вклад `1-min(Dvisible,Dedge)/Dedge`; C — среднее по направлениям и точкам.
Отдельно измеряются глаза стоя 1.7 м и присев 1.1 м. Пустой интерьер имеет C=0;
C=1 — предельное полное закрытие, не цель здоровой проходимой карты.

Луч заканчивается на 0.001 м внутри границы пола. Сначала проверяется LOS до края;
для закрытого луча бинарным поиском ищется первый блок до точности 0.1 м.
LOS префикса монотонен: найденное пересечение остаётся на каждом более длинном префиксе.
Погрешность расстояния не больше половины конечного интервала, относительная погрешность
вклада зависит от Dedge. Между направлениями возможны пропущенные щели/оси; это выборочное
измерение, не непрерывная геометрия обзора. Внутренняя стена у самого края учитывается;
только внешняя геометрия за границей исключается. Прямоугольная граница соответствует
имеющейся модели MapGrid; сложный контур площадки потребует другой модели края.

Применяется существующий LOS: физические столбы, Soft/Visual перекрывают видимость;
фон за пределами пола не входит. Плотность и закрытость не складываются в score.
Много Low может дать высокое D и низкое C стоя, немного длинных Tall — низкое D и высокое C.
Нет боевой площади или доступных образцов — `complete=false`, а не «открытая карта».

Стоимость: два луча на направление (две высоты); открытый луч — один LOS, закрытый —
ещё порядка log2(Dedge/0.1) запросов. Для 500 точек и 16 направлений примерно 16 тыс.
начальных запросов плюс поиск закрытых лучей; это не квадратичное сравнение всех точек.
Visibility для тепловой карты всё ещё использует существующие парные вычисления.

Паспорт явно выбирает Open/Closed; в JSON `profile`: 1 Open, 2 Closed, 0 Unspecified.
Индекс C и D — свидетельства для ревью этого выбора. Универсальные границы Open/Closed
не утверждены: автоматического классификатора и численного подтверждения профиля нет.

## Запуск и совместимость

Существующие меню сохранены. MapPrinciplesReport.Run принимает необязательные layoutPath
и profile. Без пути ищется `Docs/level-design/maps/<точное имя сцены>-positions.json`; отсутствие файла
даёт честный неполный отчёт. Явно переданный профиль имеет приоритет над полем JSON.
PositionImpactReport.Run(scene, layoutPath) получает профиль из JSON и тот же общий результат.

Результаты в `Temp/LevelDesign/` игнорируются Git. Основной отчёт сохраняет прежние txt/png
и добавляет json. `<map>_position-impact.json` теперь содержит общий результат: прежний
PositionImpactResult вложен в `contacts`; это изменение формата для внешних потребителей.
Исходная разметка по-прежнему сохраняется в `_input.json`.

Независимая проверка: `dotnet run --no-restore --project Tools/LevelDesign/PositionImpactHarness`.
Это чистые математические тесты; компиляцию Android и Unity EditMode запускает основной агент
под общим замком. Проверка математического ядра не подтверждает актуальную геометрию сцен.

## Проверка реализации

Для математического ядра есть PositionImpactTests, MapFeedbackRulesTests,
MapEvaluationTests и MapGridBuilderTests. Регрессии фронтальной защиты сравнивают
продольную стенку, фронтальную защиту и угловую группу. D/C проверяются на пустой арене,
перекрывающихся препятствиях, разных высотах и отсутствии доступной боевой площади.

Наличие тестов не означает зелёный результат на текущих сценах. Новые размеры/поведение
сначала подтверждаются пользователем в Unity/шлеме; затем принятая логика закрепляется тестами.
Результаты конкретных карт и остающиеся проверки — в [паспортах](README.md#левел-дизайн-от-замысла-к-проверке).
