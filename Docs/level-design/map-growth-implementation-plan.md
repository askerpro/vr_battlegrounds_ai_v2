# План реализации выращивателя карт

> **Для исполнителя:** выполнять по этапам через `superpowers:executing-plans`; `superpowers:subagent-driven-development` использовать только после разрешённого делегирования. Шаги отмечаются флажками. AGENTS.md имеет приоритет над общими инструкциями навыков.

**Цель:** в едином редакторе блокаута задавать желаемые позиции, парные контакты и проходы, получать несколько вариантов геометрии из реестра блоков и сравнивать их через общий оценщик.

**Архитектура:** BlockoutMarkup хранит авторский замысел, адаптер строит вход общего MapEvaluation, а независимые кандидаты поиска работают с копиями числовых данных. Unity-объекты, точные физические проверки и применение выбранного результата остаются на главном потоке; параллельные клеточные расчёты не меняют сцену. Замысел, измеренные результаты и ручная приёмка хранятся раздельно.

**Технологии:** Unity 6000.4.1f1, C#, существующие BlockoutBlockRegistry/BlockoutRegistryFactory, MapCellFootprint, MapEvaluation и PositionImpact; ограниченный пул Task для чистых данных, затем отдельный адаптер пакетных RaycastCommand. ECS, Burst и собственная физика для первого среза не требуются.

**Спецификация:** [выращивание карты](map-growth.md), [редактор](blockout-editor.md), [сетка](blockout-grid.md), [единая оценка](map-evaluation.md), [формат измерителя](position-impact-mvp.md). Этот план уточняет последовательность реализации обсуждённого флоу; он не означает, что выращиватель уже существует.

## Общие ограничения

- Блок — геометрия; позиция — независимая область. Блок может обслуживать ноль, одну или несколько позиций.
- Шаг размещения 0.3 м, повороты 15°, область позиции по умолчанию 1.5×1.5 м; сетка анализа по умолчанию 0.1 м. Размеры и начало координат читаются из существующих настроек/арены, а не из имён объектов.
- Low/Mid/Tall — 1.2/1.6/2.5 м. Корень блока сохраняет нижний центр. Три секции имеют независимые Hard/Soft и щели.
- Реестр — единственный источник форм, размеров, возможностей и исходной геометрии. Нет копии палитры или поиска по словам «столб», «ящик».
- Клеточный след не превращается обратно в меш. Общая клетка двух объектов — повод точной проверки, а не доказательство коллизии. Касание допустимо, пересечение объёмов кандидата недопустимо.
- Touched, BodyBlocked и Owners различаются. Физические маркеры арены резервируют движение и место строительства, но не становятся дополнительными преградами пули. Неперешагиваемая игровая защита столба фиксируется независимо от Hard/Soft; высота не выше Tall.
- Фиксированные элементы, подтверждённые области позиций, пол, физические препятствия и якоря не перемещаются поиском. Незаданные дополнительные позиции автоматически не объявляются подтверждёнными.
- Контакт и физический проход независимы. Контакт пары хранится один раз; преимущество A/B/не задано выбирается одним полем для одинаковых условий. Без откалиброванного критерия преимущество остаётся ручным пожеланием.
- Все Editor-классы — `Assets/Editor/VR_Battlegrounds/LevelDesign/`. Весь UI — текущий BlockoutPainter; новых разрозненных пунктов меню нет. Логи только GameLog с конкретным ID/действием/причиной.
- Новая игровая логика: до принятия пользователем в Unity/шлеме постоянные тесты не добавлять и не переписывать. Сначала существующие регрессии, компиляция и временные воспроизводимые проверки; после принятия закрепить постоянными тестами. Ниже перечислены будущие тесты и их точные ожидания.
- Открытие сцен, импорт/компиляция и Unity-тесты — в своей аренде editor-broker (request/claim/begin/guard/finish). Worker получает точный SHA агента; root и сессию сверять по guard, другое состояние не доказывает результат ветки.
- Коммиты кода только после пользовательской проверки соответствующего среза. Git — явные пути; Plastic — отдельная scoped-синхронизация. Создание плана не запускает реализацию, тесты или публикацию.

## Главные риски для ревью

1. Переименование/удаление позиции или Undo оставляют осиротевшие состояния и связи: валидатор указывает точную ссылку, ID не зависит от подписи; проверка этапов 1–2.
2. Частично задетые клетки диагоналей и верхние перемычки дают ложную коллизию/непроходимость: маска — предварительная проверка, геометрия и высотная проходимость проверяются раздельно; этапы 3–5.
3. Позы привязаны к одному профилю, а расчёт запущен с другим либо профиль демонстрационный: результат помечается неполным, нет утверждения полной защиты тела; этапы 1, 3 и 10.
4. Параллельные кандидаты делят буфер попаданий, Random или Unity-объекты: независимые буферы/seed и числовые снимки, проверки сопоставимости 1/N потоков; этапы 4, 7–8.
5. Cancel, domain reload или изменение карты во время поиска оставляют preview/потоки либо применяют устаревший результат: отмена, освобождение собственных ресурсов и сверка версии входа до Apply; этапы 5, 7 и 9.

Второй: этапы 4–6 и минимальное сравнение/Apply из этапа 9 — работает последовательный выращиватель. Третий: этап 7, затем этап 8 по профилю затрат. Этап 10 выполняется для каждого среза, а не только в конце.

## Критерии готовности первого прототипа

- [x] Один редактор: позиции/позы/контакты/проходы задаются визуально и сохраняются с Undo.
- [x] Противоречивый запрос отклонён до поиска с точной причиной; неизвестные/непроверенные данные видны отдельно.
- [x] Последовательный поиск получает отличающиеся варианты из реестра с фиксированными позициями/ареной/ручной геометрией; невозможный запрос завершается в бюджете.
- [x] Клетки используются для поиска/маршрутов; настоящая геометрия — для пересечений/обзора/прострела. Секции, диагонали и цилиндры не теряют исходную форму.
- [x] Вариант можно сравнить, принять одной Undo-операцией, довести вручную и использовать как вход нового поиска.
- [x] После этапа 7 результаты 1/N потоков сопоставимы, UI имеет прогресс/Cancel, end-to-end времена измерены. На коротком корпусе убедительного выигрыша нет; полный сравнительный benchmark остаётся отдельным незавершённым пунктом. Экспериментальный этап 8 сохраняет прострел в общем синхронном ядре.
- [x] AndroidCompileGate Passed=true/Errors=[]; 32 существующих метода с [Test] без параметров вызваны временным reflection-harness и зелёные. Это не полный NUnit-прогон. Пользовательская приёмка и последующие постоянные тесты новой логики записаны отдельно.

## За пределами этого плана

Автоматическое обнаружение всех новых фактических позиций, универсальный критерий доминирования, вероятность победы/эмоции, обучение на телеметрии, многопроцессный парк Unity, собственная физика, ECS/Burst-переписывание и подбор art-pass ассетов. Локальное обновление footprint/контактов — последующая оптимизация после профилирования; их полная корректная версия в первом прототипе обязательна.
