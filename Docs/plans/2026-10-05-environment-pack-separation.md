# Отделение полного каталога окружения — план реализации

> **Для исполнителя:** применять `superpowers:executing-plans` последовательно. Субагенты не запрошены. Перенос выполнен в сокращённом срезе; следующие этапы относятся к оставшейся адаптации инструментов.

**Выполнено:** Unity-сверка зависимостей, SHA-256 копии полного каталога, сохранение 16 используемых ассетов, перенос стенда в архив, очистка игры, проверка GUID/зависимостей и Android PASS. Каталог импортирован: 7933 GUID и 24 SceneAsset подтверждены, Industrial preview открыт без Missing Script. Источник актуального состояния — [контракт](../level-design/environment-pack-policy.md); детали — [локальный отчёт](../tasks/report/environment-pack-separation-2026-10-05/).

**Осталось:** постоянный универсальный аудит, адаптация Unity-сканера/разметки/галереи и сборщиков, восстановление собственного стенда из `Archive`, внешний поиск по экспортированным измерениям. Старые Unity-инструменты помечены как неадаптированные; их запуск на неполном наборе в игре ограничен.

**Цель:** сохранить выбор моделей и запуск демо во внешнем каталоге, оставив в игре только выбранные элементы и необходимые зависимости.

**Архитектура:** Python строит индекс использования и выполняет поиск по измерениям. Unity отдельного проекта импортирует полные паки, измеряет ассеты и рендерит превью. В игру переносится замыкание выбранных зависимостей с сохранением GUID.

**Технологии:** Python 3.12, стандартная библиотека, существующий Pillow для контактных листов; установленная версия Unity и URP проекта. Новые FBX-библиотеки не требуются.

**Контракт:** [политика каталога](../level-design/environment-pack-policy.md).

## Общие ограничения

- Не удалять и не перемещать `Assets/env_packs` до проверенной полной копии и Unity-сверки.
- Файлы поставщика переносятся вместе с `.meta`; исходники и импортные настройки сохраняются.
- Не переносить настройки каталога в игровой `ProjectSettings`/`Packages`.
- Общий редактор — только под `unity-lock`; отдельный Unity не открывает путь игровой рабочей копии.
- Полные отчёты — в `tmp`; вывод — статус, счётчики, до 10 примеров и путь.
- Новые тесты игровой механики не писать. Для файлового инструмента использовать синтетические фикстуры; код/ассеты не коммитить до пользовательской Unity-проверки.
- Чужие изменения сохраняются. Новый каталог размещается вне игрового репозитория по явно выбранному абсолютному пути; разрешения среды проверяются до создания.

## Особое внимание при проверке

1. Демо и собственный стенд удерживают почти весь пак: отделять их от игровых корней.
2. Importer `.meta` и вложенные префабы удерживают зависимости, которых нет в простом grep игровых сцен.
3. Бинарные `.asset` и динамические загрузки нельзя объявлять безопасными только по отсутствию текстового GUID.
4. GUID установленной копии может отличаться от исходного архива; повторная распаковка не восстанавливает автоматически текущее состояние.
5. Каталог, отдельный Unity и игровой проект должны работать с одинаковой версией источника; устаревший отчёт не должен разрешать копирование или очистку.

## Этап 1. Воспроизводимый аудит без Unity

**Файлы:** создать `Tools/AssetCatalog/audit_pack_usage.py`, `Tools/AssetCatalog/tests/test_audit_pack_usage.py`; обновить тематическую документацию.

**Интерфейс:** `python -X utf8 Tools/AssetCatalog/audit_pack_usage.py --project <root> --pack-root Assets/env_packs --output <report-dir>`.

Результат: `usage.json`, `usage.csv`, `summary.md`. JSON содержит `schemaVersion: 1`, `inputFingerprint`, `scope`, `uncertainties`, `roots`, `assets`, `externalConsumers`, `packs`. Ассет: `guid`, `path`, `pack`, `fileBytes`, `metaBytes`, `sha256`, `metaSha256`, `reasons`, `witnessChains`, `dependencies`. Категории причин — из контракта. Один GUID может иметь несколько причин.

- [ ] Написать отрицательные контроли: цикл префаб→материал→префаб; зависимость только через importer `.meta`; строковый путь JSON/редакторского кода; reference только из review; отсутствующий `.meta`; дубль GUID; бинарный TerrainData; изменение источника; карта по `sceneName` вне включённых сцен.
- [ ] Проверить отказ/неопределённость каждого опасного входа до реализации соответствующей обработки. Fixture без ссылок остаётся `no_detected_reference`, никогда `safe_to_delete`.
- [ ] Реализовать индекс GUID/путей и граф зависимостей; не читать бинарные текстуры/меши целиком ради текстового поиска. Текстовые файлы анализировать однократно; `.meta` учитывать отдельно.
- [ ] Добавить корни: включённые сцены, `MapRegistry` и строки `MapData.sceneName`, `Resources`, конфигурация Addressables при наличии. Остальные собственные ассеты сохранять отдельной консервативной категорией.
- [ ] Учесть `Tools/AssetCatalog`, редакторские рецепты и строковые пути. Исключённые SDK/неизвестные загрузки отразить в `scope`/`uncertainties`; не выдавать полный охват.
- [ ] Запустить `python -X utf8 -m unittest discover -s Tools/AssetCatalog/tests -p test_audit_pack_usage.py -v`: все контроли PASS.
- [ ] Выполнить аудит рабочей копии; сохранить точные цепочки, размеры и перечень неопределённостей. Сверить примеры с файлами и исключить влияние self-GUID из `.meta`.

## Этап 2. Сверка зависимостей через Unity

**Файлы:** создать `Assets/Editor/VR_Battlegrounds/LevelDesign/PackUsageVerification.cs` и `.meta`.

**Интерфейс:** `PackUsageVerification.Run(string fileReportPath, string outputDirectory)` возвращает только `passed`, счётчики и путь JSON. Не сохраняет сцены и ассеты. Для серийной обработки — cancellable операция по ограниченным порциям.

- [ ] Сначала подготовить пакет операций: загрузить корни файлового отчёта, вызвать `AssetDatabase.GetDependencies(roots, true)`, проверить каждый GUID/путь и сравнить с файловым графом. Учитывать бинарные сериализованные ассеты; нерешённые источники выводить отдельно.
- [ ] Под Unity-замком выполнить сверку, дождаться окончания и следующим шагом освободить замок. Расследовать ошибки уже без замка.
- [ ] Проверить на отдельной фикстуре, что зависимость, пропущенная файловым проходом, делает сверку неполной; зелёный результат требует отсутствия необъяснённых расхождений.
- [ ] Составить `retention-manifest.json`: объединение оснований сохранения, хеши файлов/метаданных, версия Unity/URP, нерешённые вопросы. Манифест не выполняет удаление.

## Этап 3. Подготовка полного внешнего каталога

**Файлы:** создать `Tools/AssetCatalog/stage_installed_catalog.py` и тесты; изменить `prepare_catalog.py` только для явно выбранного режима проекта просмотра. Старый режим измерений сохраняется.

**Интерфейс:** staging принимает `--project`, `--destination`, `--usage-report`, `--dry-run`; по умолчанию только dry-run. Копирование — отдельный явный режим `--copy`; существующие файлы не перезаписываются.

- [ ] Зафиксировать абсолютный путь назначения вне игрового репозитория. Проверить конечный путь, отсутствие пересечения с исходным `Assets`, симлинки/reparse points и разрешения среды. Тесты должны отвергать назначение внутрь игры и совпадение источника/назначения.
- [ ] Построить полный список: установленные паки, текущие `.meta`, исходные демо, собственный стенд и его зависимости, рецепты/метки, эталоны и минимальные инструменты. Независимые игровые адаптации остаются в игре; их копии для просмотра явно отмечаются.
- [ ] Проверить GUID/conflicts и SHA-256 каждого файла до и после копирования. Изменившийся источник останавливает staging; повторный запуск не подменяет готовую копию.
- [ ] Создать настройки нового проекта отдельно, ориентируясь на фактические Unity/URP версии. Недоступные скрипты демо/шейдеры фиксируются как ограничения, а не заменяются молча.
- [ ] В отдельном Unity проверить импорт, исходные демо и собственный стенд. По каждой демосцене — статус открытия, отсутствующие скрипты/материалы и визуальная проверка. Копия без этой проверки не разрешает очистку игры.

## Этап 4. Поиск вне Unity по экспортированным измерениям

**Файлы:** изменить `Tools/AssetCatalog/AssetCatalogBatch.cs`, `rank_candidates.py`, `build_review.py`; при необходимости выделить общий формат в `Tools/AssetCatalog/catalog_schema.py`. `FolderCandidateScanner` пока остаётся Unity-инструментом.

**Интерфейс:** Unity `AssetCatalogBatch.Run` читает JSON задания с `roots`, `outputDirectory`, `schemaVersion: 1`. Метаданные измерения дополняются GUID/хешами/зависимостями; прежние `models`/`blocks` сохраняются для рейтинга.

- [ ] Убрать обязательный Industrial-корень и фиксированный путь результата; старый запуск сохранить совместимым. Не применять Unity-скрипт прямо из `Tools` в игровой сборке.
- [ ] Экспортировать геометрию/LOD0 и превью в отдельном каталоге; каждый ассет имеет `measured`, `unsupported` или `failed`, с причиной. Не выдавать неполный проход за готовый каталог.
- [ ] Снять Industrial-эталон до изменения; после изменения сравнить размеры, число объектов и силуэты при одинаковых входах. Ошибочный/неподдержанный объект должен оставаться видимым в отчёте.
- [ ] `rank_candidates.py` читает только файловый экспорт и политику; `build_review.py` убирает жёсткие числа 201/18 и обрабатывает выбранные наборы, сохраняя проверки полноты.
- [ ] Проверить поиск при закрытом Unity по готовому экспорту. При несовпадении исходных хешей показывать устаревший статус; перенос не разрешать.

## Этап 5. Очистка игры по проверенному манифесту

Это отдельный этап исполнения после проверенного каталога и рассмотренного отчёта. В подготовку не входит.

- [ ] Сформировать точный список сохранения, переноса инструментов и удаления; собственные карты/реестры и строковые сборщики не должны потерять источники. Не оставлять прежнее Auto Mark Pack меню рабочим на отсутствующих полных паках: перенести его в каталог или явно направить пользователя в каталог.
- [ ] Проверить каждый удаляемый путь и хеш против замороженного манифеста; чужие изменения исключить. Подготовить восстановление из проверенной копии.
- [ ] Под общим Unity-замком выполнить согласованный пакет файловых изменений, единый Refresh и дождаться импорта. Не удерживать замок на проектировании или ожидании пользователя.
- [ ] Подготовить и выполнить отдельный пакет проверки: Missing GUID/Script, зависимости игровых корней, загрузка собственных префабов и AndroidCompileGate. Освободить замок сразу после окончания.
- [ ] Дать пользователю конкретный перечень игровых карт и адаптаций для проверки в Unity. После подтверждения — коммит только собственных путей, по правилам Git/Plastic проекта.

## Подготовленные результаты и пределы

Одноразовый файловый probe находится в `tmp/environment-pack-audit/`; он не является постоянным аудит-инструментом. Его контроль проверяет циклы, importer-ссылки, пути рецептов, разделение review и неизменность исходников. Подготовительный аудит и манифесты переноса находятся в [локальном отчёте](../tasks/report/environment-pack-separation-2026-10-05/).

Оценка исполнения: постоянный аудит и сверка — небольшой первый срез; перенос каталога/универсализация измерений — отдельный срез с импортом и визуальной проверкой. Время копирования/импорта и экономия `Library` определяются фактической поставкой и пробным импортом, не процентом числа моделей.
