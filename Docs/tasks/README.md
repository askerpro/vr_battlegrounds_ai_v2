## Правила для агента, который берёт задачу

1. **Проверь, что задача разблокирована** — в колонке «Блокирована» таблицы ниже все
   перечисленные задачи должны быть `✅ готово`. Если нет — не брать, взять другую.
2. **Читай только свой файл задачи** и то, на что он ссылается. Весь аудит читать не нужно.
3. **Не выходи за границы задачи.** В каждом файле есть раздел «Границы» — там написано,
   что трогать нельзя. Соседние баги в том же файле — чужие задачи.
4. **Проверь сам.** Протокол — в [`../../CLAUDE.md`](../../CLAUDE.md), раздел «Самопроверка».
   Минимум для любой задачи, трогающей код:
   ```
   execute_code: VrBattlegrounds.EditorTools.AndroidCompileGate.Run()   → PASS
   run_tests(mode="EditMode", assembly_names=["VrBattlegrounds.Tests.EditMode"])
   get_test_job(job_id=..., include_failed_tests=true, wait_timeout=60) → 0 failed
   ```
   Нечем проверить — сделать проверялку частью задачи. «Пусть пользователь посмотрит» —
   не результат.
5. **Тест должен быть красным до правки.** Иначе неизвестно, проверяет ли он что-нибудь.
6. **Не коммить** без явного разрешения. Исключение — задачи `только доки`.
7. **Обнови статус** в таблице ниже и допиши строку в [`../CHANGELOG.md`](../CHANGELOG.md).
   Если проверка вскрыла, что находка неверна, — исправь и
   [аудит](../audit/network-audit-2026-08.md). Так уже было с MATCH-04.

Статусы: `⬜ не начата` · `🔧 в работе` · `✅ готово` · `⏸ отложена`

## Как выполнять: модель делегирования

**Решение: последовательные субагенты с чистым контекстом, общее дерево, без воркри.**

Каждую задачу берёт свой субагент: читает только свой файл задачи, правит код, сам
проверяет через харнесс, отчитывается. Оркестратор держит статусы и порядок, но не
детали кода — иначе его контекст переполняется на пятой задаче и начинает вытеснять
раннее.

**Строго по одному за раз.** Рабочее дерево и редактор Unity — общие синглтоны:
два агента, одновременно правящих код, гоняют перекрёстные рекомпиляции и портят друг
другу прогоны тестов. Параллелить можно только задачи, не трогающие `.cs` (правки
документации, исследования T-23/T-24).

**Что делает это возможным.** Харнесс самопроверки: ворота компиляции под Android
и EditMode-тесты. Без них субагент не может доказать свою работу, и делегирование
производит непроверяемый код. Поэтому проверялки и стоят первыми в очереди —
до них делегировать было нельзя.

Что давать субагенту в задании:

- путь к файлу задачи и указание прочитать раздел «Самопроверка» в `CLAUDE.md`;
- точные вызовы MCP для проверки (он их сам не найдёт) — см. пункт 4 правил выше;
- явные границы: что не трогать, и что тесты править нельзя;
- запрет коммитить и запрет менять этот файл (статусы ведёт оркестратор, иначе конфликт);
- требование не подгонять код под тесты: отрицательный результат с разбором лучше,
  чем зелёный любой ценой.

### Почему не отдельные worktree

Это решение остаётся в силе — оно про изоляцию файловой системы, а не про контекст:

1. **Unity Library.** Каждый worktree требует своего `Library/` — полный реимпорт
   1383 сторонних скриптов, FBX-аватаров и текстур. Десятки минут и гигабайты на копию.
2. **Один редактор — один MCP.** Unity MCP цепляется к одному экземпляру редактора.
   Агент в отдельном worktree не сможет проверить свою работу вообще, а сетевой код
   без запуска не проверяется никак. Это главная причина: worktree лишает субагента
   именно того, ради чего он и нужен, — способности себя проверить.
3. **T-05 конфликтует со всем.** Переделка логгера трогает ~200 мест почти во всех файлах.
4. **Ядро линейно по существу.** T-11 → T-12 → T-13 — одна и та же зона кода,
   разрезать её на параллельные ветки нельзя без переделки одного и того же дважды.

**Где параллель оправдана.** [T-23](T-23-decision-lag-compensation.md)
и [T-24](T-24-decision-projectile-simulation.md) — исследовательские задачи, производящие
документ, а не код. Их можно отдать параллельно с любой другой работой.

### Поправки к плану от 2026-08-17

Первый же прогон проверок изменил картину. Что уточнилось:

- **T-07 не была заблокирована T-05.** Заявленный блокер — «`GameSettings.Instance`
  не работает в EditMode-тесте» — оказался выдумкой: `Resources.Load` в редакторе
  работает, проверено через `execute_code`. Тестовая сборка поднята без переделки логгера.
  T-05 остаётся полезной, но больше ничего не блокирует.
- **MATCH-04 в исходной формулировке не воспроизвелась.** Подсчёт победителя верен;
  реальная проблема оказалась другой — поиск команды через глобальный `TeamRegistry`
  вместо переданного массива. T-08 переформулирована.
- **Найдена новая находка MATCH-06** (задача T-25): `SetManager` вызывает
  `_roundManager.StartNextRound()` вместо своего одноимённого метода, из-за чего счётчик
  раундов не растёт. Чтением кода это было пропущено.
- **Порядок волн изменён.** Проверялки идут первыми: без них агент не может закрыть
  задачу, а не «человеку будет удобнее». T-06 и тестовая сборка сделаны до правок логики.

### Статус кода

| Задача | Чем подтверждено |
|---|---|
| T-01 | Ворота Android: FAIL с возвращённым багом (`CS0246: Codice`), PASS без него |
| T-06 | Проверены в обе стороны — красный и зелёный |
| T-07 | 6 тестов гоняются за ~5 с; 3 зелёных, 3 красных на реальном баге |
| T-02, T-03, T-04 | Только компиляция. Логика не проверена — нужны T-09 (для T-02), уровень 2 (T-04), шлем (T-03) |

`T-02` отдельно: двойная подписка живёт в `[Server]`-методе `EliminationMode`, а вне
сервера Mirror такие методы заглушает — обычным юнит-тестом не достаётся. Закрывается
харнессом яруса A из [T-26](T-26-network-test-harness.md), который поднимает Mirror
сервером без сокета.

### Проверяемость сетевого кода

Ключевое ограничение, обнаруженное экспериментально: `[Server]`-методы вне активного
сервера Mirror **молча заглушает**. Обычный тест вызывает такой метод, тот ничего не
делает, тест зеленеет и не проверяет ничего.

Отсюда три яруса сетевых тестов — рецепты и разбор в
[`../testing.md`](../testing.md#как-тестировать-сетевую-логику):

| Ярус | Что это | Закрывает | Задача |
|---|---|---|---|
| A | Mirror сервером без сокета (`NetworkServer.listen = false`) | T-02 | [T-26](T-26-network-test-harness.md) |
| B | + локальный клиент (`NetworkClient.ConnectHost()`) | T-04, T-11 | [T-26](T-26-network-test-harness.md) |
| C | два процесса, вердикт пишет сценарий в файл | T-12, T-13, T-14 | [T-27](T-27-two-process-e2e.md) |

T-26 стоит делать перед волной 3: без неё ядро сети (T-11 → T-12 → T-13) придётся
принимать на веру.
