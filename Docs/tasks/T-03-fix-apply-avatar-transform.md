## Что делать

`Assets/Scripts/PhysicalSpaceUtils/PhysicalSpaceSyncManager.cs:429`:

```csharp
// сейчас — Y умножается на Y
newPosition = Vector3.Scale(newPosition, new Vector3(1, UxrAvatar.LocalAvatar.transform.position.y, 1));
```

`Vector3.Scale` перемножает компоненты покомпонентно. При `y = 0` (аватар на полу —
обычный случай) высота обнуляется, при `y = 2` получается 4.

Судя по соседнему коду, замысел был «оставить Y как есть». Тогда:

```csharp
newPosition.y = UxrAvatar.LocalAvatar.transform.position.y;
```

**Перед правкой убедись, что замысел именно такой.** Метод вызывается после калибровки
по двум якорям (`RegisterCalibrationPoint` → `CalculateTransform` → `ApplyAvatarTransform`),
а `_realToVirtualOffset` считается по всем трём осям. Возможен и вариант «Y должен браться
из offset» — тогда строка просто удаляется. Выбранный вариант описать в комментарии.

## Границы

Только эта строка и комментарий к ней. Логику `CalculateTransform` и калибровку роста
(`ApplyScale`, `ApplyHeightDelta`) не трогать — там своя находка VR-01, задача
[T-14](T-14-sync-calibration-scale.md).

## Как проверить

Только в шлеме. Пройти калибровку по двум якорям, затем посмотреть, встал ли аватар
на правильной высоте. До правки при аватаре на полу телепорт уводил в `y = 0` независимо
от результата калибровки.

Если шлема под рукой нет — сформулировать пользователю пункт для чек-листа уровня 5.

## Готово, когда

- Y после калибровки по якорям не обнуляется и не удваивается.
- Выбранный вариант поведения зафиксирован комментарием в коде.
