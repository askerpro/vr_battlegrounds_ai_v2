## Зачем

Три находки не воспроизводятся нигде, кроме конфигурации «сервер, не являющийся
клиентом»:

- **NET-01** — `_initialStateLoaded` статический: второй клиент применяет state-sync
  до получения глобального состояния;
- **NET-06** — `ClientRpc` в режиме `ServerOnly` локально не исполняется, поэтому арсенал
  на выделенном сервере не пополняется;
- **VR-01** — расхождение масштаба видно только между двумя разными клиентами.

Ни ярус A, ни ярус B, ни Multiplayer Play Mode их не поймают. При этом это самые
дорогие в отладке баги проекта — плавающие рассинхроны.

## Ключевое требование

**Вердикт выносит сценарий, а не человек.** Уровень 4 в `Docs/testing.md` описан как
ручной прогон «смотреть в два окна». Так агент задачу закрыть не может. Нужно, чтобы
каждый процесс сам проверял утверждения и писал машиночитаемый результат.

## Что делать

### 1. Сценарии внутри билда

Компонент, который по CLI-аргументу (`-e2eScenario <имя>`) проигрывает один сценарий
и пишет вердикт в файл:

```
-e2eScenario avatar-swap-death-replication -e2eResult C:\path\result.json
```

Формат результата — простой и стабильный:

```json
{
  "scenario": "avatar-swap-death-replication",
  "role": "client-2",
  "passed": false,
  "checks": [
    { "name": "смерть игрока 1 дошла до клиента 2", "passed": false,
      "detail": "IsAlive остался true через 5 с после смерти" }
  ]
}
```

Сценарий должен иметь таймаут и писать файл **всегда**, даже при падении — иначе агент
не отличит «провалилось» от «не запустилось».

### 2. Скрипт-дирижёр

PowerShell (Bash-инструмент изолирован от сети — см. `CLAUDE.md`):

1. собрать плеер, если билд устарел;
2. запустить сервер с `-batchmode -nographics`, дождаться готовности;
3. запустить клиентов с нужными сценариями;
4. дождаться всех файлов результатов или таймаута;
5. свести в один отчёт и вернуть код возврата.

### 3. Первые сценарии

| Сценарий | Что проверяет | Находка |
|---|---|---|
| `dedicated-server-arsenal` | оружие появляется в слотах на выделенном сервере | NET-06 |
| `second-client-initial-state` | нет `UxrComponentNotFoundException` при подключении второго клиента | NET-01 |
| `avatar-swap-death-replication` | после смены скина смерть доезжает до всех клиентов | NET-02 |
| `calibration-scale-agreement` | рост игрока совпадает в чужом окне | VR-01 |

`avatar-swap-death-replication` — самый ценный: он про то, как ломается основной путь
доставки здоровья.

## Границы

Только харнесс и сценарии. Игровой код не менять — найденное записывать в аудит.

Не строить полноценный CI: задача — дать агенту способ прогнать e2e локально одной
командой. Интеграция в CI, если понадобится, отдельно.

## Риски

- **Долго.** Сборка плеера — минуты. Предусмотреть переиспользование билда, если код
  не менялся.
- **Хрупко.** Процессы могут зависать. Таймауты и принудительное завершение обязательны,
  иначе висящий процесс заблокирует следующий прогон.
- **Диагностируемость.** Если сценарий упал, агент должен понять почему из файла
  результата, не открывая логи руками. Detail-строки писать содержательно.

## Как проверить

Сломать что-нибудь заведомо и убедиться, что сценарий это ловит — как с воротами
компиляции. Для `dedicated-server-arsenal` это бесплатно: NET-06 в коде уже есть,
поэтому сценарий должен быть **красным сразу**, до всяких правок. Если он зелёный —
сценарий ничего не проверяет.

## Готово, когда

- Один прогон одной командой даёт машиночитаемый отчёт.
- `dedicated-server-arsenal` красный на текущем коде (NET-06 не исправлена).
- Способ запуска описан в [`../testing.md`](../testing.md).
