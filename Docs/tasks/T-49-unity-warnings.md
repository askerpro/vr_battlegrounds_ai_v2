# T-49 — Исправление предупреждений Unity

**Цель:** устранить воспроизводимые предупреждения текущего проекта без изменения принятой игровой механики и без глобального подавления диагностики.

**Архитектура:** исправлять классы причин: жизненный цикл компонентов, выбор контекста сессии, идентичность объектов и совместимость API. Сначала отделить предупреждения рабочего запуска от сообщений временных тестовых стендов и старых компиляций; у каждого оставшегося сообщения должен быть источник и проверяемый сценарий.

**Стек:** Unity 6000.4.1f1, URP, UltimateXR, Mirror, Quest 2/3.

**Источники:** AGENTS.md, Docs/troubleshooting.md, Docs/UltimateXR/known-issues.md; текущий Editor.log и read_console от 2026-10-04. Статус ведётся только в README очереди.

## Исходные факты и пределы

При чтении MCP-консоль содержала 0 warning и 9 служебных Log. Editor.log размером около 106 МБ содержит историю сессии, включая несколько компиляций и прогоны проверок. Это не доказательство, что все перечисленные предупреждения сохраняются на текущем коде.

Сохранён перечень 209 различных строк компилятора: `tmp/unity-warnings-2026-10-04.txt`. Различие позиции строки создаёт дополнительные записи одного предупреждения; это не число независимых дефектов. Распределение: Scripts — 83, Editor — 67, Tests — 7, UltimateXR — 32, остальные сторонние ассеты — 12, Packages — 8. Коды: CS0618 — 193 строки, CS0114 — 5, CS0414 — 5, CS0219 — 3, CS0067/CS0108/CS0252 — по одной.

Контекст runtime-предупреждений сохранён в `tmp/unity-runtime-warnings-2026-10-04.txt`. Это эвристическая выборка строк перед LogWarning, содержащая также соседние информационные сообщения; при реализации проверять точный блок в Editor.log и стек, а не считать каждую строку warning.

## Ограничения

- Работать в своём linked worktree. Unity-компиляция, тесты, Play Mode и открытие сцен — в постоянном worker через editor-broker request/claim/begin/guard/finish; освобождать аренду сразу после завершения подготовленного пакета.
- Не прерывать пользовательский Play Mode, не очищать консоль ради доказательства исправления. Учитывать, что MCP test runner сохраняет dirty-сцены.
- Логи только GameLog; SDK-патчи документировать в соответствующих реестрах.
- Не отключать CS0618 глобально, не добавлять `new` или `pragma` только ради исчезновения сообщения.
- Новые тесты изменённой механики — после проверки пользователем; до этого компиляция, существующие проверки и список проверки в Unity/шлеме. Изменения аватаров согласовать с обязательными AvatarLoadoutTests и PrefabCompositionTests после приёмки.
- Коммит кода только после проверки пользователем в Unity.

## Фокус проверки

Порядок поиска объектов и inactive-аватары; сохранность идентичности после scene/domain reload; базовый lifecycle затвора; fallback игрока без команды и доступность меню; различие Unity fake-null и обычного reference equality. Каждый пункт проверять в соответствующем этапе, а при изменении механики — закрепить после приёмки.

## Критерий готовности

Свежий реестр разобран полностью; подтверждённые причины исправлены либо явно классифицированы как штатная диагностика/внешнее окружение. Компиляция Editor/Android и существующие проверки зелёные; изменённое игровое поведение принято пользователем. До выполнения этих условий задача остаётся открытой.
