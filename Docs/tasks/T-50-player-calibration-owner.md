## Зачем

До T-50 калибровка игрока (пол, рост, выравнивание по якорям, признак «откалиброван») не имела владельца. Одни и те
же значения жили в нескольких местах и применялись к аватару несколькими писателями, часть — **относительными
сдвигами** (`+= delta`, умножение на `new/old`). Результат зависит от числа вызовов и их порядка, а порядок при
смене аватара, смене карты, переподключении и на хосте не определён. Найденный баг B1 (двойной сдвиг пола после
смены аватара: руки выше реальных на величину сдвига) — один экземпляр этого класса; временный фикс закрывает только
его.

**Класс ошибки:** несколько писателей одного производного состояния аватара, применение дельтами, владение по
гоночному признаку (`UxrAvatar.LocalAvatar` при смене аватара ещё указывает на старый).

## Целевая архитектура

**Один источник — абсолютные значения игрока в метрах; один применитель на каждый аватар; применение идемпотентно.**

```
Процедура калибровки (PSM: фазы, замеры, якоря)
        │  результат замера (абсолютные значения)
        ▼
PlayerCalibration  — данные игрока, владелец PlayerSession (сервер решает, клиент предсказывает свои)
  floorOffset (м) · eyeHeight (м, рост глаз игрока) · isCalibrated · anchorPose (этап 4)
        │  событие «изменилось» + чтение текущего значения
        ▼
AvatarCalibrationApplier — компонент на каждом аватаре, единственный писатель его производного состояния
  пивот камеры   = база префаба + floorOffset
  Dummy Forward  = eyeHeight / EyesBaseHeight этого аватара
  поля BodyIK    = базовые значения × масштаб (база снята при появлении, не new/old)
  смещение рук   = floorOffset (только у своего аватара; трекинг есть только у него)
```

- **Абсолют вместо дельт.** Применитель ставит значения от базы префаба. Повторный вызов из любого места и в любом
  порядке даёт тот же результат — исчезают `_appliedHeightOffset`, проверки «свой/чужой» и порядок «хук раньше спавна».
- **Одни правила для своего и чужого аватара.** Различие только в том, что трекинг рук есть у своего.
- **Рост в метрах, а не в долях модели.** Масштаб считается для каждого аватара по его собственному `EyesBaseHeight`.
- **Сервер — единственный судья.** Ограничения (±1,5 м, 0,5–1,5) и запрет в бою — в одном месте. Клиент применяет свой
  результат сразу (предсказание) и откатывается к значению сервера при отказе — тем же применителем.
- **PSM остаётся процедурой.** Фазы, замеры, якоря, подсказки UI; к аватарам он больше ничего не применяет и своих
  накопленных копий не хранит.
- **Снимок сессии хранит всю калибровку.** Клиент без данных (перезапуск) ничего не публикует поверх снимка; публикует
  только явное действие калибровки.

## Риски

- **Сетевой формат.** Меняются SyncVar сессии (рост в метрах вместо отношения) — все клиенты одной сборки, совместимость
  не нужна, но E2E-сценарии и тесты репликации переписываются.
- **База полей BodyIK.** Снимать её при появлении аватара до любого масштаба; читать через ту же рефлексию, что сейчас
  (поля задокументированы в `sdk-patches.md`).
- **Ноги** читают масштаб через `Dummy Forward.lossyScale` — поведение не меняется, но смена `EyesBaseHeight`-логики на
  этапе 2 меняет фактический масштаб при калибровке на одной модели и игре на другой (это и есть исправление).
- **Правило «тесты на подтверждённую логику».** Механика калибровки существующая и принятая; тесты этапа 0 фиксируют её
  принятое поведение и найденный класс отказов, а не новую механику.

## Проверка человеком (шлем)

Для каждого этапа 1–3: калибровка (пол + рост) → смена аватара (Cyborg ↔ MEF ↔ Heavy) → смена карты → выход и вход.
Руки совпадают с контроллерами, высота глаз и ноги — как у себя; второй клиент видит игрока на той же высоте и в том же
масштабе. Хост — отдельно.

### Границы доказательств

EditMode-фикстура вручную создаёт BodyIK/Dummy Forward и имитирует обработчик старта PSM:
она доказывает порядок входов и идемпотентность калибровки, не запуск готовых префабов в XR.
Отказ в бою имитируется ответом сервера; настоящие GameMode → команда → сериализация номера ответа → откат
на отдельном owning client не прогонялись. Совместная доставка снимка и номера при нескольких ожидающих
запросах, реальный reconnect и транспорт между процессами остаются в пользовательской проверке.
Поза по якорям (этап 4), качество IK и физические замеры в шлеме отдельно не оценивались.
