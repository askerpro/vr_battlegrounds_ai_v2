# Поштучное заряжание трубчатых дробовиков — исследование

Дата: 2026-10-04. Только чтение исходников и сериализованных полей. Изменений SDK, игрового кода, префабов, WeaponInfo, тестов и состояния Unity нет. Механика пользователем ещё не принята. Ниже подтверждённое устройство проекта отделено от предлагаемого контракта.

**Актуальное поручение пользователя 2026-10-05:** реализация поштучной перезарядки запущена сейчас; пользователь проверит её вместе с остальной оружейной работой. Старое условие ожидания полного завершения `weapon-readiness-feedback-design.md` отменено. [Прогресс реализации](../../tmp/shotgun-per-shell-implementation-progress.md). Исследование ниже предшествует нынешнему SDK readiness ledger: предложенный отдельный game-owned счётчик не является действующим контрактом; боезапас и патронник должны использовать единственного SDK владельца.

## Подтверждённая причина

Класс ошибки — физическая единица боеприпаса и контейнер всего запаса представлены одним объектом. `UxrFirearmWeapon` не владеет счётчиком трубки: `GetAmmoLeft()` возвращает `Rounds` объекта в `AmmunitionMagAnchor`, `SetAmmoLeft()` записывает туда же (`Assets/ThirdParty/UltimateXR/Runtime/Scripts/Mechanics/Weapons/UxrFirearmWeapon.cs:138–184`). Ёмкость также берётся из вставленного объекта (`:115–127`). Вставленная физическая гильза потому является полноценным съёмным магазином.

`UxrFirearmMag.Rounds` лишь ограничивает значение диапазоном `0..Capacity`; ни суммирования, ни отдельного состояния патрона в патроннике нет (`UxrFirearmMag.cs:21–49`). `MagTarget_Placed` отключает коллайдер и при заданном флаге сбрасывает готовность ручного досылания, но не добавляет патрон (`UxrFirearmWeapon.cs:640–661`). Новый объект становится источником всего запаса.

## Кто сейчас чем владеет

- Боезапас хранит `UxrFirearmMag` физического вставленного предмета. SDK выстрел уменьшает его на один (`UxrFirearmWeapon.cs:246–248`).
- Удалённый replay основного `Shoot` тоже уменьшает копию на один; дополнительная дробь этого не делает (`UxrWeapon.Custom.cs:106–131`, особенно `:122–126`). Нельзя добавлять ещё один расход через `ProjectileShot`/`ProjectileShotReplayed`: получится двойной расход.
- `HasReloaded` — готовность ручного цикла, а не учтённая физическая камера: `Reload()` только ставит true (`UxrFirearmWeapon.cs:74–91`), Start первоначально ставит true (`:388–391`). ManualReload сбрасывает готовность по нажатию до результата `TryToShootRound` (`:503–509`).
- `UxrShotgunPump.Update` зовёт Reload после пересечения обратного порога (`UxrShotgunPump.cs:70–114`). Отдельного движения боеприпаса из трубки в камеру и выброса живого патрона/стреляной гильзы здесь нет. Отсутствие собственного guard автора у этого вызова — известная граница для будущего среза; relay фильтрует рассылку, но это не повод добавить второй автор.
- `MagazineEject` находит **любой** `UxrFirearmMag` в якорях оружия и вызывает синхронизируемый Remove после проверки автора (`Assets/Scripts/Weapons/MagazineEject.cs:32–58`). Значит кнопка сейчас выбрасывает физическую гильзу вместе со всем запасом.
- `WeaponInternalAmmoAlignment` отделяет наружный `DropProximityTransform` от внутреннего `AlignTransform`, сохраняет включённый Renderer и делает безопасную `EjectionPose` (`Assets/Editor/VR_Battlegrounds/Gameplay/WeaponInternalAmmoAlignment.cs:20–69,159–169`). Это исправление позы, не новая механика заряжания.
- `WeaponInternalAmmoEjection` подписывается на вложенный `UxrFirearmMag` и смещает его перед включением динамики; специально применяется и при silent replay (`Assets/Scripts/Weapons/WeaponInternalAmmoEjection.cs:39–72`). Это следствие Remove, не источник нового сетевого действия.
- Автор действия удерживаемого предмета — автор аватара, вне рук — сервер/офлайн-машина (`Assets/Scripts/Network/StateEventAuthority.cs:53–77`). `NetworkUxrIdentity.Align` выравнивает идентичности по netId (`NetworkUxrIdentity.cs:194–212`); не переносить вставленную сетевую гильзу в другой identity и не переиспользовать её как следующий запас.
- `UxrFirearmMag.StateSave.cs:15–21` сохраняет rounds, `UxrFirearmWeapon.StateSave.cs:15–23` — runtime trigger. Late join получает snapshot через `NetworkStateRelay.cs:306–333`. Новые game-owned поля должны быть в этом же согласованном восстановлении либо в явно выбранном единственном Mirror snapshot-пути.

## Рекомендуемый контракт

Для FABARM и Herrington добавить небольшой игровой владелец `ShotgunTubeAmmo` и отдельную роль физического `ShotgunShell`. Состояние владельца — одно место для общего накопленного боезапаса, ёмкости и учтённой операции приёма. Если принимается физическая камера, туда же входят tubeCount и chamberState; нельзя держать независимый расходуемый int в UI, SDK магазине и компоненте дробовика.

Термин пользователя «в стволе» предлагается показывать как общий доступный запас оружия. Технически трубчатый магазин и патронник различаются. Для первого среза сохранить нынешние пределы **общего** запаса 8/7 и ручную готовность как отдельное состояние. Это не даёт молча увеличить баланс до 8+1/7+1. Настоящую отдельную камеру и выброс живого патрона можно принять отдельным решением, синхронизировав его с исследованиями затвора.

Одна принятая физическая гильза даёт ровно `+1`, затем перестаёт быть доступной единицей боезапаса. Подача в трубку не вызывает Reload и не сбрасывает уже готовый патронник: дозарядка 3→4 сохраняет возможность стрельбы. После пустого оружия приём гильзы и ручное досылание — два разных перехода. Помпа FABARM и затвор Herrington сохраняют свои выбранные циклы; автоматическое досылание по спуску относится к отдельной политике на модель.

### Узкая граница интеграции с SDK

SDK getter/setter ammo и `UxrFirearmMag.Rounds` **не virtual**. Поэтому отдельный game-owned int нельзя прозрачно подключить наследованием: SDK продолжит расходовать свой объект. Рекомендуется минимальный opt-in ammo-provider мост, дающий SDK чтение capacity/amount, авторский расход и применение replay в игровой владелец. При отсутствии provider текущий магазинный путь целиком остаётся прежним. В мост также входит `HasMagAttached`/готовность подсказки: сейчас `NeedsManualChambering()` требует физический объект в anchor (`UxrWeapon.Custom.cs:59–67`), поэтому просто обнулить anchor нельзя — там GetAmmoLeft превращается в int.MaxValue.

Это небольшой SDK extension point с документированным патчем, **не** перенос правил дробовика в SDK. Вся политика совместимости, заполнения, consumption, отображения, отказа и пределы остаётся в `Assets/Scripts/Weapons`. Не копировать целиком `UxrFirearmWeapon`, не переписывать триггеры и не вводить общий рефактор оружия.

Более узкая альтернатива без SDK-правок: постоянный невытаскиваемый внутренний `UxrFirearmMag` является единственным хранилищем всего запаса, а внешние гильзы входят в отдельный intake anchor; игровой компонент выполняет только поштучное пополнение этого **единственного** store. Тогда game int не нужен, firing/replay/snapshot остаются SDK. Но придётся исключить store из MagazineEject, отделить визуальные гильзы от магазина, явно синхронизировать пополнение и отдельно решить chamber state. Этот компромисс пригоден для «+1 без новой камеры», однако закрепляет абстракцию скрытого магазина. Если требуется полноценная физическая трубка+камера, предпочтителен provider.

Ещё одна альтернатива — внедрить per-shell/reload mode прямо в SDK firearm/trigger/mag. Она разносит игровые правила по SDK и увеличивает риск регрессии обычного оружия; не рекомендована.

### Транзакция приёма

Предлагаемый порядок: внешняя точка приёма → проверка shell type и свободного места → авторский `AcceptShell(shellId, operationId, expectedRevision)` → ровно один `+1` и запись consumed → освобождение приёмника → серверное удаление/деактивация сетевой гильзы. UI и внешние Renderer применяют принятое состояние, не исправляют счётчик.

- Валидатор `AddPlacingValidator` уже есть (`UxrGrabbableObjectAnchor.cs:318–363`); при полном оружии приёмник отвергает гильзу до её отпускания/защёлкивания. При отказе патрон остаётся физическим и доступным руке. Итоговая авторская проверка обязательна даже после preview validator: запас мог заполниться между preview и commit.
- Приёмный anchor нельзя оставлять занятым каждым принятым патроном: иначе второй патрон не войдёт. Внутренний показ последних/распределённых патронов — отдельное косметическое представление состояния, не один из расходуемых объектов.
- Не начислять ammo из общего `ObjectPlaced`: он не вызывается при `propagateEvents=false` (`UxrGrabManager.cs:541–550`). `PlaceObject` допускает swap существующего occupant (`UxrGrabManager.Manipulation.cs:180–200`) и сам не является атомарной ammo-транзакцией. Начисление внутри SDK callback без отдельной транзакции ломается на silent replay/restore, повторной вставке и разрушении объекта. Не удалять объект реентерабельно посреди Place; завершение по принятой транзакции и после завершения SDK операции.
- Авторскую команду создаёт только разрешённый автор оружия. Remote/silent replay лишь применяет уже принятую операцию и визуал; не повторяет Add/Remove/Destroy. Для сетевого despawn нужен сервер, а не локальный Destroy у владельца. Кто может заряжать оружие чужого игрока — отдельная политика; либо владелец оружия принимает запрос загрузчика, либо первый срез явно ограничен своим удерживаемым оружием.
- shellId/netId и operationId нужны для идемпотентности: повтор place, пакет replay, старый callback после cancel/disable и смена владельца не дают второй +1. Snapshot содержит revision и результат consumption; late join не возобновляет физическую гильзу, уже превращённую в запас.
- Во время передачи оружия прекращаются локальные pending attempts предыдущего автора; готовый запас передаётся как состояние без Reset/Refill. Частично вставленный непринятый патрон остаётся физическим, принятый не превращается обратно в переносной магазин.
- Spawn стартового оружия — явные initial ammo/loaded settings. Нынешний вложенный объект с rounds=8/7 нельзя считать пользовательской вставкой и повторно добавлять при Awake/LoadState.

## Изменения конфигурации при будущей реализации

Два оружейных префаба: явный opt-in reload style, capacity, initial ammo, acceptance anchor, тип shell, internal visual pose, отдельные chamber/cycle policy. Внешние shell prefabs больше не содержат rounds=capacity оружия: одна физическая штука имеет ценность 1. Изменять SDK MagShotgun/sample нельзя: Herrington наследует его, а футуристическое оружие использует его по своему прежнему пути.

Обязательно поправить **генераторы**, иначе rebuild вернёт старую механику:

- `HandsPackWeaponBuilder.cs:925–927` создаёт rounds=capacity каждого ammo prefab.
- `HandsPackWeaponBuilder.ShotgunReal:103–123` имеет исторический default capacity=6, но текущий legacy rebuild сохраняет capacity=8 immutable донора (`HandsPackLegacyRebuild.cs:213–220`), а balance применяет 8. Не принять 6 за фактическую ёмкость.
- `KinemationWeaponBuilder.cs:197–203` задаёт Herrington MagazineCapacity=7 и MagazineIsInternal.
- `WeaponBalanceApplier.cs:175–180` заново пишет rounds/capacity внешнего prefab равными WeaponInfo.MagazineSize. Требуется различать ёмкость оружия и ценность ammo item по принятому reload style.
- `MagazineEject` не должен видеть tube inventory как съёмный магазин. Кнопку для трубчатого оружия предлагается оставить без эффекта; ручной выброс chambered/live shell или spent case — самостоятельные действия, без удаления всего tubeCount. Предвычисленная EjectionPose полезна для реальных выбрасываемых тел, но нынешний Remove-физической гильзы не является выбросом стреляной гильзы.

## Арсенал и выдача — обязательная смежная граница

Сейчас ArsenalMagazineSupply выдаёт один настоящий `WeaponInfo.MagazinePrefab` на отдельном stock anchor (`ArsenalMagazineSupply.cs:146–166`) и пополняет только пустые anchors по запросу режима (`:131–142`); взятие само по себе не спавнит новый патрон. Lost replacement зависит от режима и исчезновения ранее выданного identity (`:169–184`). Если каждый новый shell будет удаляться при загрузке, правило replacement нельзя случайно превратить в бесконечную выдачу в бою.

`ArsenalMagazineOffer.AllowsGrab` считает боеприпасы бесплатными, но проверяет доступность стены и её владельца (`:54–65`). Поштучность не разрешает обходить владельца/закупку и не должна вводить цену за патрон без отдельного решения.

`PlayerLoadoutManager.ServerEnsureMagazines` считает количество объектов по `MaxMagazineCount` и лимиту кармана (`:197–206`), затем спавнит MagazinePrefab (`:300`). `MagazineRefillPlanner` считает штуки, а `UxrMagazinePocket.PerTypeLimit` — лимит штук данного типа, не запас в патронах. Оба WeaponInfo имеют MaxMagazineCount=3 и ReserveAmmo=32; одна текущая выдача означает 3 полных магазина по 8/7, после смены semantics это стало бы **всего 3 патрона**. ReserveAmmo — балансное поле, не доказательство runtime выдачи 32 патронов.

Нужно согласовать запас и его физическое предъявление: россыпь shell с отдельным лимитом либо пачка/держатель, из которого в руку выдаётся один физический shell. Рекомендация — сохранить расчёт резерва в единицах патронов и выдавать в руку по одному, избегая десятков активных Rigidbody; конкретный маршрут снабжения входит в отдельный ограниченный срез и не должен менять magazine-путь остальных стволов. До этого «+1» технически можно проверить, но штатная дозарядка арсеналом будет неполной.

## Приёмочные сценарии после реализации

1. Пустое оружие: первый принятый shell меняет общий запас 0→1, второй 1→2. Третий не стирает предыдущие. Просто поднести/забрать/отменить — 0 изменений.
2. Частично заряженное 3→4: остаток сохраняется, готовность chamber не сбрасывается и не выставляется автоматически из вставки. При сохранённой готовности можно прервать дозарядку и стрелять.
3. Full: 8/7 достигнуты точно; следующая гильза остаётся физической, не исчезает и не увеличивает запас. Race двух попыток на последнее место принимает одну.
4. Один successful shot расходует один патрон при 9/6 дробинах, у хозяина/хоста/наблюдателя одинаковый остаток. Dry fire не расходует shell; shot replay и ammo resync не уменьшают ещё раз.
5. FABARM: после принятого shell в пустое оружие нужен выбранный полный pump cycle; один цикл не создаёт ammo. Herrington: закрывание/досылание по отдельно принятому контракту, без автоматического нового Reload из каждого shell.
6. Повтор того же place/operation, silent replay/restore, переподписка OnEnable, cancel, разрушение/смена аватара — один или ноль commit, без второго +1 и без висящего приёмника.
7. Late join, передача другому игроку, выброс/возврат оружия, новая половина/раунд — правильный запас и consumed state. Смена владельца не пополняет оружие.
8. MagazineEject на этих двух оружиях не выбрасывает весь трубчатый запас; обычный съёмный магазин других стволов и SDK Shotgun работает прежним путём.
9. Приём/отказ/case ejection не пересекает корпус; загрузочная область остаётся внешней, внутренний визуал остаётся внутри и не блокирует следующий shell.
10. Серверная выдача боеприпасов, лимит кармана, фазовый допуск и владелец стены не создают потерю резерва либо бесплатный бесконечный refill вне выбранных правил.

До пользовательского принятия механики не писать/переписывать её тесты. После принятия: чистые тесты invariant/transition/idempotency и реальный SDK/network harness для accepted shell, firing replay, snapshot и authority; затем закрепить фактическое prefab composition. AndroidCompileGate и существующие проверки запускать только под Unity lock, без вмешательства в human Play.

Устаревшие ожидания заранее известны: `WeaponBalanceTests.cs:273–276` требует внешний MagazinePrefab с UxrFirearmMag и rounds/capacity=MagazineSize; это прямо конфликтует с новым shell prefab. `WeaponFeedbackTests`, `AnchoredItemGrabTests`, `AvatarLoadoutTests`/`PrefabCompositionTests`, `MagazineRefillPlannerTests` и проверки кармана должны быть просмотрены на assumption «ammo object = съёмный магазин», но не ослаблены до принятия. Тест дроби остаётся с прежним инвариантом один патрон на залп.

## Решения, которые нельзя незаметно выбрать реализацией

- Первый срез хранит общий запас 8/7 + readiness или вводит настоящую tubeCount+chamberCount и общую ёмкость 8+1/7+1? Рекомендация первого среза — общий предел 8/7, новый баланс не выводить из бытового слова «ствол».
- Можно ли заряжать оружие чужого удерживающего игрока? Это влияет на протокол acceptance и authority, а не только UX.
- Сколько патронов даёт карман/арсенал и как предъявляет физический shell? Текущее MaxMagazineCount=3 нельзя переиспользовать как 3 shell молча.
- Какая политика живого патрона и стреляной гильзы при ручном цикле? Текущий SDK HasReloaded этого не моделирует; нынешняя EjectionPose — не подтверждение уже существующего механизма case ejection.
- Заряд стартового оружия и chamber state после spawn/refill требуют явных defaults. Для первого прототипа рекомендуется нынешний исходный запас, но после user test закрепляется один принятый контракт.

Итог исследования: корень подтверждён исходниками и реальными prefab полями. Предпочтительная долгосрочная граница — игровой владелец tube ammo с минимальным SDK provider; если пользователь хочет только узкий +1-срез без физической камеры, внутренний постоянный SDK store и отдельный intake являются допустимым более коротким вариантом. Ни один вариант не реализован и не проверен в Unity этим исследованием.
