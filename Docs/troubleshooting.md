# Симптом → причина

> **Читать первым при расследовании любого бага.** Индекс по тому, как проблема
> выглядит со стороны игрока, а не по номеру находки. Если симптом здесь есть —
> ответ уже известен, повторное расследование не нужно.
>
> Не нашёл симптом — дальше: [`UltimateXR/known-issues.md`](UltimateXR/known-issues.md)
> → [`UltimateXR/sdk-patches.md`](UltimateXR/sdk-patches.md) → команда `/debug`.
> Полный список находок — [`audit/network-audit-2026-08.md`](audit/network-audit-2026-08.md).

Обновлять при каждой находке, у которой есть внятное внешнее проявление.

## Стрельба и попадания

### «Пули не попадают» · «Попадания не засчитываются» · «Стреляю в упор, здоровье не убывает»

Три разные причины, проверять в этом порядке.

**1. Скин жертвы не имеет хитбоксов — WPN-02, НЕ ИСПРАВЛЕНА.**

У четырёх скинов из шести **нет ни одного непроходного коллайдера**, только триггеры.
А `UxrWeaponManager` трассирует с `QueryTriggerInteraction.Ignore` — значит поразить
их нельзя **ни при какой настройке оружия**.

| Скин | Непроходных коллайдеров |
|---|---|
| `PlayerBase` | 5 |
| `PlayerControllersCyborgAvatar` | 5 |
| `Heavy_Soldier_Base_Avatar` | **0** |
| `MEF_Base_Avatar` | 7 (капсулы на костях) |
| `Military_Cap_Base_Avatar` | **0** |
| `Military_Soldier_Base_Avatar` | **0** |
| `Spy_Base_Avatar` | **0** |

Хитбоксы (`MeshCollider`) исчезли вместе со старой геометрией, когда из `PlayerBase`
делали варианты с новыми моделями.

**Скин по умолчанию у Counter-Terrorists — `Heavy_Soldier_Base_Avatar`**, то есть
в типовой игре половина команды непоражаема. Если жалоба звучит как «по одному игроку
попадаю, по другому нет» — это оно.

Проверить за секунду:
```csharp
var go = UnityEditor.AssetDatabase.LoadAssetAtPath<GameObject>("Assets/Prefabs/Player/<скин>.prefab");
int solid = 0; foreach (var c in go.GetComponentsInChildren<Collider>(true)) if (!c.isTrigger) solid++;
// solid == 0 → поразить нельзя
```

**2. Маска слоёв оружия — WPN-01, исправлена 2026-08-23 (T-28).**

У `M16_Rifle_prefab` и `Gun_real` `_collisionLayerMask` была нулевой, а `Physics.Raycast`
с нулевой маской не проверяет ни одного слоя. Если симптом вернулся — проверь маску,
должна быть `Default | Ground` (9).

**Ловушка: имя слоя `Player` обманывает.** Игрок поражается благодаря `Default` —
на `Player` и `SpawnZone` лежат только триггеры. Переедут хитбоксы на `Player` —
маску придётся менять.

**3. Билд плеера устарел.** При проверке на ярусе C свежесть меряется по
`Build/e2e/VrBattlegrounds_Data/Managed/VrBattlegrounds.dll`, **а не по `.exe`** —
последний это лаунчер и при инкрементальной сборке не переписывается. На этом уже
один раз построили ложную тревогу.

Сторож: сценарий `weapon-hit-damage` (`Run-E2E.ps1 -Scenario weapon-hit-damage -Clients 1`).
Он же содержит контрольный опыт с эталонной маской — если красная проверка падает,
а контроль зелёный, причина именно в настройке оружия.

## Взаимодействие с предметами

### «Оружие в арсенале не видно» · «Стойки пустые у клиента»

**NET-22, исправлена.** Префабы оружия и магазинов не были зарегистрированы
в `NetworkManager.spawnPrefabs`: сервер спавнил успешно и молча, у клиента
не появлялось ничего — 128 строк `Failed to spawn server object` в клиентском логе.

Если вернулось: проверь `spawnPrefabs` на префабе `--- MANAGERS ---`. Кнопка
«Validate NetworkManager Prefabs» в инспекторе `WeaponRegistry` **эту работу
не делает** — она зовёт `RecordPrefabInstancePropertyModifications`, предназначенный
для инстансов, а не для префаб-ассетов.

Сторож: тест `NetworkSpawnableRegistrationTests`.

### «Взял предмет, у других не видно» · «Захват не реплицируется»

**NET-16, исправлена.** `UniqueId` рантайм-объектов различался на машинах, поэтому
канал состояния UltimateXR отвергал **все** события манипуляций — захват, выстрел,
вставку магазина. В логе: `UxrComponentNotFoundException ... TryGetComponentById`.

Выравнивает `NetworkUxrIdentity` через `CombineUniqueIds(netId)` на обеих сторонах.
Если вернулось — проверь, что префаб предмета попадает под спавн-обработчик
из `GameNetworkManager.OnStartClient`.

### «Брошенное оружие проваливается сквозь пол» · «В логе клиента бесконечные `UpdateRigidbody(...)`»

**PHY-01, исправлена.** В логе `ExecuteStateSyncEvent ... Method call UpdateRigidbody` с
огромной отрицательной Y и скоростью — это не дрожание лежащего предмета, а вечное падение.
После отпускания UltimateXR у отпустившего игрока шлёт позицию, пока rigidbody не заснёт
(`UxrGrabbableObject.RegularPhysicsSyncCoroutine`); падающий в бездну не засыпает никогда.

Найдено три причины: у `Gun_real` не было коллайдеров вовсе; выпуклый коллайдер корпуса
`Machinegun`/`Shotgun` охватывал вставленный магазин, и тот выталкивал оружие под пол даже
при падении с места; `Discrete` у магазинов и оружия пробивал плоский пол при броске.
Исправлено коллайдером, `AnchoredItemCollisionIgnore`, `Continuous` и `FloorThickness`
(BoxCollider 1 м под полом в `Environment.prefab`). Страховка — `OutOfWorldGuard`.
Если вернулось — `WeaponDropPhysicsTests` назовёт префаб.

### «Не перезаряжается: затвор тяну до упора, а перезарядка не засчитывается»

**Исправлено 2026-09-27 (`Gun_real`).** Длина хода для порога задавалась в
`AutomaticWeaponSlideFeedback` отдельно (`Local Slide Reference Offset`) от `Translation Limits`
граббабла затвора. У `Gun_real` эталон 6 см был скопирован с M16 при реальном ходе 1.89 см:
максимум 31% против порога 85.5%. Теперь ось и длина хода берутся только из `Translation
Limits` затвора (`TryGetSlideTravel`), ход настраивается в одном месте. Если перезарядка
снова не срабатывает — у затвора не `Restrict Local Offset` или нулевые лимиты: об этом
предупреждает инспектор, `GameLog.WeaponSystem` в `Awake` и `WeaponSlideTravelTests`.

### «Вторая рука перехватывает оружие вместо поддержки» · «Не взять двумя руками»

**Исправлено 2026-09-27.** Две причины: UltimateXR делал дополнительную точку недосягаемой,
если место ладони на ней ближе 5 см к занятой (снято [патчем SDK 11](UltimateXR/sdk-patches.md)),
и выбирал ближайшую точку, даже занятую другой рукой (снято `TwoHandGrabPolicy`). Если симптом
вернулся — сначала `GunTwoHandGrabTests`: красный первый тест значит, что патч 11 потерян при
обновлении SDK. Иначе смотреть `Allow Multi Grab` у предмета и `Max Distance Grab` у
дополнительной точки. Разбор — [known-issues, Issue 13](UltimateXR/known-issues.md).

### «Подношу руку к лежащему пистолету — активен затвор» · «Взял оружие за затвор»

**Исправлено 2026-09-27.** Деталь без `GrabOnlyWhenParentHeld` UltimateXR выбирает наравне с
рукоятью. Новая деталь оружия без компонента — `WeaponPartGrabTests` назовёт её. Если компонент
стоит, а деталь всё равно берётся — проверить, что галочка `Require Parent Held` включена.

### «Лежащий пистолет берётся хватом поддержки» · «Взял пистолет за additional-точку»

**Исправлено 2026-09-29 (`Gun_real`).** Точка поддержки в 2 см от рукояти, UltimateXR выбирает
её наравне с основной. `SupportGripRequiresMain` на корне оружия пускает к дополнительным точкам,
только когда основную держит другая рука того же игрока. Новый пистолет без компонента —
красный `SupportGripTests` (кейсы — оружие с точкой поддержки ближе 10 см к основной).

### «Кладу вторую руку на поддержку — пистолет поворачивается»

**Исправлено 2026-09-27 (`Gun_real`).** UltimateXR при хвате двумя руками доворачивает предмет
ко второй руке, настройки против этого нет. На оружии, где вторая рука только поддерживает,
нужен `MainGripAimLock` — он держит позу по основной руке. Новый пистолет с дополнительной
точкой без этого компонента будет крутиться так же. Разбор — [known-issues, Issue 14](UltimateXR/known-issues.md).

### «Затвор щёлкает, а оружие не стреляет» · «Магазин не вставляется»

**Исправлено 2026-09-27 (`Gun_real`).** Выстрел берёт патрон из магазина, а якорь магазина
`Gun_real` принимал только тег `M16_Mag` (скопирован с M16), тогда как арсенал выдаёт к нему
`MagGun`. Магазин не вставлялся, патронов 0 — после затвора звучал щелчок «пусто». Якорь
теперь принимает `MagGun`. Проверка — `WeaponSlideTravelTests.ArsenalMagazine_FitsWeaponMagAnchor`
сверяет магазин из `WeaponInfo` с `Compatible Tags` якоря оружия.

Второе: `Gun_real` лежал на стене **без магазина**, а взять его было негде — магазин у
слота декоративный (`FirearmSlotController`), запасные выдаёт только `PlayerLoadoutManager`
в начале раунда, а его нет на аватарах. Теперь в `MagAnchor` вложен родной магазин
`Gun_real_mag` (`Assets/Prefabs/Weapons/GunReal/`), как `M16_Magazine` у M16: без
`NetworkIdentity`, `Start Anchor` = `MagAnchor`. Его же выдаёт `Gun_Weapon`. Проверка —
`WeaponSlideTravelTests.ArsenalFirearms_ComeLoaded`: вложенный магазин из того же префаба
(или его базы), что выдаёт `WeaponInfo`.

Порядок у UltimateXR при `Use Has Reloaded For Semi And Full Auto`: **сначала магазин, потом
затвор.** Вставка и извлечение магазина сбрасывают «патрон дослан».

### «Оружие можно взять из закрытого арсенала»

**NET-13, исправлена.** `Lock()`/`Unlock()` искали предмет в `CurrentPlacedObject`,
который для выданного по сети оружия всегда пуст — то есть молча выключали и включали
`null`. Занятость слота теперь считается через `ArsenalSlotController.CurrentItem`.

**«Оружие не берётся, а затвор — берётся». Исправлено 2026-09-27.** Блокировка выключала
только корневой `UxrGrabbableObject`, а затвор, цевьё и вставленный магазин — отдельные
grabbable на дочерних объектах. Теперь `SetItemGrabbable` проходит по всей иерархии
предмета и ставит `IsGrabbable`, не выключая компонент: выключение ломало бы захват,
начатый до закрытия стены (как у жетона). Проверка — `ArsenalSlotOccupancyTests`.

### «Жетон на стене арсенала при старте сцены падает на пол» · «Предмет в якоре падает сразу после загрузки»

**Исправлено 2026-09-27.** UltimateXR ставит grabbable в якорь и делает его тело kinematic
в `UxrGrabbableObject.Awake`, только если заданы **оба** поля: `Start Anchor` и
`Rigid Body Source`. У `DogTag` в `StandardArsenalWall` не было ни того ни другого — это
было просто тело с гравитацией рядом с якорем. Попутное следствие: событие якоря `Removed`
не приходило никогда, и объявить готовность жетоном было нельзя. Та же ловушка грозит
любому предмету, который кладут в якорь в редакторе, а не через `PlaceObject`.
Если вернулось — `DogTagSetupTests` назовёт префаб или сцену.

### «RuntimeManipulationInfo not found for object …» при отпускании предмета

**Исправлено для жетона 2026-09-27.** Предмет выключили (`enabled = false` или
`SetActive(false)`), пока он был в руке: UltimateXR на выключение молча стирает запись о
захвате (`UxrGrabManager.GrabbableObject_Disabled`), и отпускание её не находит. У жетона
так было, когда время закупки истекало в руке и стена закрывалась (`DogTagController.Disable`).
Запрещать захват нужно флагом `IsGrabbable = false` — SDK читает его только при поиске
нового захвата и текущий не трогает. Сторож — `DogTagHeldDisableTests`.

### «Тянусь за пистолетом в кобуру — достаю магазин» · «Вторая рука на пистолете хватает магазин» · «Магазин вынимается из лежащего оружия»

**Исправлено 2026-09-27.** Магазин в рукояти ближе к ладони, чем прокси кобуры, рукоять и точка
поддержки, и UltimateXR выбирал его. Правило `AnchoredItemGrabRule` (в `GrabRules`): предмет,
вставленный в якорь другого предмета, рукой не берётся вовсе — магазин выходит только кнопкой
выброса A/X (`MagazineEject`). Сторож — `AnchoredItemGrabTests`. Если симптом вернулся — проверить, что `PlayerGrabManager` на аватаре
(он ставит `CanGrabDelegate`) и что правило не выпало из `GrabRules`.

### «Карман не вибрирует» · «Вибрирует, а предмет не встаёт»

Вибрацию даёт `PocketHaptics` на корне аватара (`AvatarLoadoutTests.На_корне_есть_хаптики_карманов`),
только у своего аватара, один импульс на вход в готовый карман (не всё время, пока рука в нём). Готовность решает сам UltimateXR (`PocketReadiness`), поэтому
расхождение «вибрирует, но не кладёт/не достаёт» — повод смотреть на то, что изменилось между
решением и действием (другая рука взяла предмет, карман заняли). Молчит у кармана с предметом
в руке — см. симптом ниже: скорее всего не выполнено условие укладки.

### «Подношу оружие к карману, отпускаю — падает на землю» · «Пистолет не встаёт в кобуру»

UltimateXR кладёт предмет в карман только в момент отпускания и только если одновременно
(`UxrGrabManager.TryRelease`):

1. предмет держит **одна** рука — при хвате двумя отпускание первой ничего не кладёт;
2. точка укладки предмета (`DropProximityTransform`) не дальше `Max Place Distance` от точки
   укладки кармана (у карманов с прокси — сама прокси);
3. тег предмета есть в `Compatible Tags` кармана, карман свободен.

Самое частое в шлеме — пункт 2: тела не видно, рука тянется к настоящему бедру, а виртуальная
кобура ниже или в стороне. Разбор: включить `Tools/VR Battlegrounds/Debug/Anchor Zones In Headset`
— зона кармана вспыхивает, когда предмет в руке до неё достаёт, а при неудачном отпускании в
консоль пишется причина (`AnchorZonesDebugView`):
`'Gun_instance' отпущен у 'Anchor_Hip_R', но не встал: далеко: 0,50 м при радиусе укладки 0,30 м`.
Лечение — увеличить `Max Place Distance` или сдвинуть якорь с прокси прямо в Play Mode, затем
`Tools/VR Battlegrounds/Avatars/Save Pocket Zones To Prefab`.

### «Не могу повесить оружие обратно на стену арсенала»

**Исправлено 2026-09-27.** У якорей слотов был пустой `Compatible Tags`, а UltimateXR понимает
пустой список как «только предметы без тега» ([known-issues, Issue 16](UltimateXR/known-issues.md)).
Теперь слот сам настраивает якорь по своему `WeaponInfo`: принимает оружие только своего типа
и только на открытой стене. Радиус укладки слот расширяет так, чтобы ствол вставал, когда его
подносят туда, где он висел (у M16 точка укладки в висячей позе в 19 см от точки якоря), а после
укладки возвращает позу свежего предмета. Если снова не встаёт — `Anchor Zones In Headset`
рисует свободные слоты голубыми сферами и пишет причину отказа в консоль.

## Матч и раунды

### «Раунд не начинается» · «Все стоят в зоне, а отсчёт не идёт»

**RDY-02, исправлена.** `ServerResetRoundReadiness` существовал, но его не звал никто:
готовность прошлого раунда доживала до следующего.

Смотреть: `EliminationMode.PendingReadiness` — состав неготовых реплицируется,
его видно у клиента. Предел ожидания 45 с настраивается в инспекторе режима.

### «Режим без команд» · «В разминке игрок остался без команды» · `Teams.Length == 0` у режима на сервере

`GameMode.Awake` подписывает колбэк `SyncList` команд, а `MapReferee` инициализирует режим
**до спавна** (`isServer` ещё `false`). Колбэк на `Clear` пересобирал `_teams` из пустого списка
посреди `Initialize`, и команды режима пропадали — только в Play mode: в EditMode Unity `Awake`
не зовёт. Исправлено: колбэк молчит при `NetworkServer.active`, `Initialize` перебирает свою копию.
Проверка — `MatchFlowTests` (фабрика режимов зовёт `Awake`, как игра).

### «NullReferenceException в `MapReferee.StartMatch` / `get_isServer` при загрузке карты»

«Начать матч» пришёл из `Awake` оркестратора (автостарт `DebugOrchestrator` по
`SubscribeToInstance`), когда `NetworkIdentity` ещё не связала компоненты. Исправлено: запрос
до `OnStartServer` откладывается флагом и выполняется после разминки; проверка — не `isServer`.
Тест — `MatchFlowTests.Начать_матч_до_спавна_карты_выполняется_после_разминки`.

### «После «Продолжить» матч начался с первого раунда» · «Пауза потеряла счёт»

`EliminationMode.Begin` зовёт корутина старта базового режима кадром позже спавна, а
`ServerTick` к этому моменту уже поднял продолженный сет. Сброс в `WaitingForPlayers` начинал сет
заново. Исправлено: `Begin` ничего не меняет, если матч уже идёт. Тест —
`MatchPauseTests.Поздний_старт_режима_не_сбрасывает_продолженный_матч`.

### «При смене режима / паузе игрока выкинуло из игры» · `Disconnecting connection … CommandMessage … NullReferenceException` в `UxrMirrorAvatar.CmdRequestAuthority`

Захват предмета шлёт `CmdRequestAuthority`; если сервер тем временем уничтожил предмет
(`EquipmentStrip`), ссылка приходит null, SDK падал, Mirror рвал соединение (на хосте — свой
клиент). Патч SDK 13. Тест — `AuthorityRequestForDestroyedTests`.

### «Первый игрок закрыл арсенал всем» · «Не успел взять оружие»

## Сеть и подключение

### «После разрыва не могу переподключиться» · «Помогает только перезапуск игры»

**NET-20, исправлена.** Загрузка `Offline` уничтожала `NetworkManager`, который её
начал, и `NetworkClient.isLoadingScene` навсегда оставался `true` — при взведённом
флаге клиент не разбирает входящие сообщения вовсе.

Если вернулось: смотри, не зовёт ли кто-то `Destroy(gameObject)` на корне ветки
`--- MANAGERS ---`. Отсев дубликата делает `PersistentRoot` в `Start`, и это
принципиально: к `Start` все `Awake` сцены отработали.

### «После переподключения потерял счёт и позицию»

**ARCH-01, исправлена.** `SessionRecoveryManager` не был размещён **нигде** —
ни в одной сцене, ни в одном префабе, поэтому `Instance` всегда был `null`,
а все вызовы обёрнуты в проверку и молча не выполнялись.

Сторож: `PrefabCompositionTests` — он ловит весь класс «компонента просто нет
в проекте». Сценарий: `session-recovery-on-reconnect`.

### «В Multiplayer Play Mode сыпется `UxrComponentNotFoundException`» · «Хост и клиент MPPM не видят компоненты друг друга»

**MPPM-01, исправлена 2026-09-27 (патч 7 в [sdk-patches](UltimateXR/sdk-patches.md)).**
Виртуальный игрок MPPM перевыдавал `_uxrUniqueId` ассетам у себя в памяти через
`NotifyOnValidate` — у 1389 из 1943 UXR-компонентов флаги `__isInPrefab`/`__prefabGuid`
не совпадают с фактическими. Симптомы: на хосте `IsGrabbable`, `SetAvatarRenderMode`
не находят компонент, на клиенте `LoadStateChanges(): Cannot deserialize a component`.

**MPPM-02, исправлена 2026-09-27.** Та же картина после патча 7, особенно при смене скина
на ходу, — у хоста id случайные, у клона файловые. Причина — неверные флаги
`__isInPrefab`/`__prefabGuid` на диске: основной редактор перевыдаёт id при реимпорте
префаба и не сохраняет ([known-issues #11](UltimateXR/known-issues.md)). Неверные флаги
приносит **Apply to Prefab** со сцены. Их чинит постпроцессор `UxrUniqueIdPersister` сразу
после сохранения префаба. Если `UxrUniqueIdOnDiskTests` всё же красный (правка шла в Play Mode
или из клона) — `Tools/VR Battlegrounds/VersionControl/Persist UltimateXR Unique Ids`, затем
перезапустить Play Mode, чтобы клон перечитал префабы.

**Сначала прочитай хвост сообщения.** С патча 8 отправитель из редактора или development-
сборки кладёт в ссылку путь и тип компонента: `… Id is ae118e67-…. Sender: ArsenalWall (2)/…
[UxrGrabbableObject]`. Это сразу называет предмет, и перебор id по префабам не нужен.
Хвоста нет — отправитель собран как release.

Как отличить от других причин: id на хосте должны быть ровно `Combine(id с диска, netId)`.
Если так, а клиентский id не выводится ни из одного префаба, — расходится клон.

**Если id из ошибки — исходный id префаба** (есть в `.prefab` как `_uxrUniqueId`), это
**NET-26**: событие аватара сериализовано до `CombineUniqueId`. Так было с
`OnControllerInputChanged` при подключённом шлеме на клиенте: Mirror создаёт аватар
в порядке `Awake` → `OnStartClient`, а id выравниваются только во втором. Исправлено
2026-09-27: `NetworkStateRelay` придерживает такие события в `AvatarStateEventGate`
и сериализует их после выравнивания. Сторож — `AvatarStateEventGateTests`.

### «Порт для сервера уже занят» · `SocketException: … только одно использование адреса сокета` при `StartHost`

**Исправлено 2026-09-27, [патч 1 Mirror](Mirror/mirror-patches.md).** Порт 7778 или 47777
держит **Unity.exe**, хотя сервер остановлен. Причина — дочерний процесс редактора,
запущенный посреди Play Mode (так было с MCP-сервером): он унаследовал сокеты, и после
остановки Mirror порт остался за ним. Владельцем Windows показывает родителя — не верь этому.

Если вернулось: дерево потомков Unity (`Get-CimInstance Win32_Process`, фильтр по
`ParentProcessId`) — кто из них стартовал во время сессии. Убить его дерево или
перезапустить MCP. Сторож — `SocketInheritanceTests`.

### «На выделенном сервере не работает то, что работает на хосте»

Общее правило, а не одна находка. **Host-режим маскирует целый класс дефектов:**
`NetworkClient.OnHostClientSpawn` кладёт в `NetworkClient.spawned` ссылку на тот же
объект из `NetworkServer.spawned` — сериализации нет вообще, «клиент» читает серверные
поля напрямую.

Так прятались NET-04, NET-06, NET-15. Проверять такое **только ярусом C**
(два процесса) — см. [`testing.md`](testing.md).

Второе следствие: `[ClientRpc]` в режиме `ServerOnly` локально **не исполняется**.
Если серверная реакция подвешена к клиентскому событию — на выделенном сервере
её не будет.

## VR и калибровка

### «Другие игроки не того роста» · «Стреляю в голову, а попадаю мимо»

**VR-01 и VR-08, исправлены.** Масштаб и смещение высоты калибровались локально
и не реплицировались: у `Dummy Forward` нет своего `NetworkTransform`, а он вообще
создаётся SDK в рантайме. Теперь оба едут `SyncVar` на `PlayerSession`.

Ловушка: у всех `NetworkTransform` в проекте `coordinateSpace = Local`,
то есть синхронизируется `localPosition` **того объекта, где висит компонент**.
`ApplyHeightDelta` двигает родителя камеры, а на нём компонента нет.

### «Аватар появился в углу карты» · «Заспавнился внутри ящика»

**WPN-03.** `AvatarManager.ChangeAvatar` точками спавна не пользуется — берёт позицию
старого аватара, а после смены карты его уже нет, поэтому выходит `(0,0,0)`.
Статус смотреть в [`tasks/README.md`](tasks/README.md).

### «Чёрный экран после телепорта» · «После смены скина экран погас и не проявляется» · «Поворот с затемнением оставил темноту»

**Исправлено 2026-09-27.** Аватар уничтожили, пока его руки что-то держали (смена скина или
команды, отключение игрока). Рука UltimateXR при уничтожении ничего не отпускает, в
`UxrGrabManager` оставался захват мёртвой руки, и первый телепорт или поворот с
`UxrTranslationType.Fade` бросал `MissingReferenceException` в `UxrAvatar_GlobalAvatarMoved`
уже после затемнения — `UxrCameraFade` оставался с альфой 1 (`IsFading=True`).
Разбор — [known-issues, Issue 17](UltimateXR/known-issues.md).

Теперь сервер освобождает аватар до уничтожения (`AvatarTeardown.ReleaseBeforeDestroy`: руки
отпускаются, оружие из кобур выпадает, магазины кармана убираются через сеть), а SDK
вычищает осиротевшие захваты сам (патч 12). Сторож — `AvatarTeardownTests`. Если симптом
вернулся: в логе UltimateXR `Removed N grab(s) whose object or grabber was destroyed` —
значит, появился новый путь уничтожения аватара в обход `AvatarTeardown`; нет патча 12 —
красный `Перемещение_аватара_не_бросает_на_захвате_мёртвой_руки`.

### «Руки других игроков не двигаются» · «Пальцы шевелятся, а кисть стоит» · На хосте всё в порядке, по сети — нет

**Исправлено 2026-09-28.** `NetworkTransform` на кистях стоял в `coordinateSpace = Local`, а IK руки
(`UxrArmIKSolver`) после решения возвращает кисти её мировую позу — локальная позиция кисти
относительно предплечья всегда равна длине кости. По сети шла константа, у принимающей стороны
кисть садилась на своё же предплечье, и IK не двигал руку. Теперь на кистях `World`, как у самого
UltimateXR (`UxrMirrorNetwork.SetupAvatar`); у `Heavy_Soldier_Base_Avatar` их не было вовсе.
Сторож — `PrefabCompositionTests.У_каждого_аватара_кисти_несут_NetworkTransform`. Разбор —
[known-issues, Issue 21](UltimateXR/known-issues.md).

### «Вижу свою голову изнутри» · «Перед глазами текстуры лица, очков, шлема»

Камера по замыслу UltimateXR стоит в глазах модели (`EyesForwardOffset` = кость глаза + 2 см,
кнопка SDK «Use Avatar Eyes»), то есть внутри головы. Меши головы своего аватара выключает
штатное поле **`UxrMirrorAvatar` → `Local Disabled Game Objects`** на корне игрового префаба
(`Assets/Prefabs/Player/<Model>_Base_Avatar.prefab`); у чужих аватаров они остаются.
Пустой список — причина симптома. Заполнение — скилл `/setup-avatar`, `game-variant.md`, раздел 3а.

У Heavy и старых Military список пуст, голову уводили подкруткой `EyesForwardOffset` до ~0.11 —
это обход, тело сдвигается назад от реальной головы игрока.

### «Голова вдавлена в плечи» · «Тело выше, чем надо, ноги висят над полом»

**Исправлено 2026-09-28.** Голова стоит правильно (глаза в камере), а таз уехал вверх, и
UltimateXR, держа шею у камеры, сдвинул саму кость шеи вниз — ключицы оказываются выше шеи.
Причина — Legs Animator без анимации. Он каждый кадр берёт текущий таз за «кадр анимации» и
добавляет свою поправку высоты. Позицию таза сбрасывает только режим `FixedCalibrate`, да и тот
при выключении/включении плагина запоминает уже сдвинутый таз (+14 см за раз). Второй источник —
плагин, выключенный в префабе и включённый позже: он запоминал опорную высоту таза из позы под
камерой. Решение: `LegsAnimatorUxrBridge` каждый кадр возвращает таз в позу префаба, плагин и мост
включены в префабе с самого старта, `Calibrate = FixedCalibrate`. Сторожа —
`LegsGroundingTests.Мост_возвращает_таз_в_позу_префаба` и
`AvatarLoadoutTests.Legs_Animator_настроен_на_своих_костях`.

Постоянный подъём ровно на 15 см — поправка таза Legs Animator (`_LastAppliedHipsFinalOffset`)
равна `footHeightOffset` моста. Причина — нулевой `Legs[i].AnkleToHeel`: плагин не знает высоту
лодыжки, мост поднимал пол, плагин поднимал под него тело. Решение — `AnkleToHeel` вычислен
(`RefreshLegAnkleToHeelAndFeet` в позе префаба), `footHeightOffset = 0` (2026-09-28).

Вернулось после перекомпиляции скриптов в Play Mode (Preferences → General → Script Changes While
Playing = Recompile And Continue Playing)? Unity при перезагрузке домена сохраняет приватные поля
только сериализуемых типов: поза таза в мосте обнулялась, ссылка на кость выживала, и мост ставил
таз в (0, 0, 0) — тело подскакивало на метр. Исправлено 2026-09-28 (`BoneLocalPose` сериализуемая,
незахваченная поза не применяется), сторож — `LegsGroundingTests.Поза_кости_переживает_сериализацию`.
Перекомпиляция в Play ломает и остальную игру (статики вроде `AvatarManager.Instance` сбрасываются) —
ставить Recompile After Finished Playing.

### «В зеркале я без головы»

**Исправлено 2026-09-28.** SDK прячет свою голову выключением объектов (см. выше), а выключенный
объект не рисует и камера зеркала. `LocalHeadMirrorVisibility` включает их обратно на слое
`LocalHead`: своя камера этот слой не рисует, зеркало (`UxrPlanarReflectionUrp`, маска «всё, кроме
Water») — рисует. Симптом вернулся — проверить, что слой `LocalHead` есть в Tags and Layers (иначе
в логе `Player` ошибка `Нет слоя 'LocalHead'`) и что код не перезаписывает маску своей камеры
целиком (`cullingMask = …` вместо `&=`/`|=`). Сторож — `LocalHeadMirrorVisibilityTests`.

### «Режим отрисовки аватара не совпадает у игроков»

**NET-24, исправлена (2026-09-27), подтверждено прогоном хост + клиент MPPM: 0 сетевых ошибок.**
`SetAvatarRenderMode` шлёт по сети **список включённых контроллеров** ссылками по id.
Без шлема включён только `UxrDummyControllerInput`, а если его нет в префабе, SDK
добавляет его в рантайме с id, своим на каждой машине, — событие отвергается целиком.
Теперь dummy лежит в корне каждого аватарного префаба; сторож —
`PrefabCompositionTests.У_каждого_аватара_на_корне_лежит_dummy_ввод_с_id`.
Если симптом вернулся — посмотри, какой компонент стоит за id из ошибки: включённые
контроллеры аватара даёт `UxrControllerInput.GetComponents(avatar)`.

Практическое правило, шире этой находки: **события с ссылками на компоненты
не переживают сеть.** Передавать значения. `Shoot(int, Vector3, Quaternion)` доезжает,
`SetAvatarRenderMode(modes, List<UxrControllerInput>)` — нет.

## Выделенный сервер

### «Сервер завис, память растёт на сотни МБ в секунду» · «Куклы замерли, потом всё встало» · Ошибки `UxrCameraFade … shader` на каждом спавне

Прогрев UltimateXR (`UxrManager.PrecacheCoroutine`) на машине без графики. Он стартует, когда включается
единственный `Local`-аватар; на сервере каждый спавн аватара (игрок, кукла) в момент `Instantiate` ещё

`HeadlessPrecacheGuard` (выключает прогрев без графики). Проверка — в логе сервера строка
`[HeadlessPrecacheGuard] … прогрев UltimateXR выключен`; число детей `UxrManager` не растёт. Сервер для
расследования запускать через `Start-Server.cmd` — лог в `Build/Server/Logs/`, консоль хранит только хвост.

### «Клиент стресс-теста отключается от сервера» · В логе клиента `handling a message of type StressTestStatusMessage caused an Exception`

Исключение в обработчике сообщения Mirror отключает клиента. Причиной был общий `perf.log`: сервер и
клиент на одном ПК делят `persistentDataPath`. Каталог прогона теперь `<время>_<роль>_<номер>`, обработчик
ловит исключения.

## Сборка и инструменты

### «В редакторе компилируется, под Quest падает»

Editor-only код в рантайм-сборке. Ловится воротами уровня 0:
```
execute_code: VrBattlegrounds.EditorTools.AndroidCompileGate.Run()
```
Так были найдены BUILD-01 (`using static Codice...` из Plastic SCM) и целая папка
Editor-скриптов внутри `Assets/Scripts/`.

### «Красная ошибка `X requires a NetworkIdentity` в консоли редактора»

`NetworkBehaviour` без `NetworkIdentity` на себе или у родителя — Mirror пишет это
из `OnValidate` при каждой загрузке объекта. Тест
`PrefabCompositionTests.У_каждого_NetworkBehaviour_в_префабах_есть_NetworkIdentity`
назовёт префаб. Так было с заброшенной `Arsenal/ArsenalWall.prefab` (NET-25, удалена).

Не путать с `SpawnObject probe_weapon_instance ... has no NetworkIdentity` во время
прогона тестов: это `NetworkSpawnableRegistrationTests` проверяет отказ намеренно
(в обрамлении `IgnoreFailingMessages`).

### «Объект есть в сцене, но Mirror его не спавнит»

Нет `sceneId`. Так было с четырьмя стенами арсенала на `TestMap2` (NET-14) —
карта была неработоспособна и в билде под Quest.

**Пересохранения сцены недостаточно**, если объект — инстанс префаба: `sceneId`
живёт как переопределение и в файл не попадает без явной записи модификаций.
Нужен проход по всем `NetworkIdentity` с
`PrefabUtility.RecordPrefabInstancePropertyModifications` + `SetDirty`.

### «В диффе префаба `_assetId: 0` или чужое число» · «Разойдётся ли assetId у клиента и сервера?»

Не баг и не расхождение. Mirror (`NetworkIdentity.SetupIDs`) при **каждой загрузке**
префаба в редакторе пересчитывает `_assetId` как хеш GUID самого префаба из `.meta`,
и в сборку уходит пересчитанное значение, а не число из файла. Клиент и сервер из
одной ревизии получают одинаковый id: GUID один и тот же.

Проверено 2026-09-27 прямым замером, а не чтением кода: AssetBundle из `PlayerBase`
и `M16_Rifle_prefab` (на диске 0), а также вариантов `Military_Cap_Base_Avatar` и
`MagGun` (на диске id базового префаба) разобран через `WebExtract` + `binary2text`.
Во всех четырёх лежит хеш собственного GUID. На диске «неверный» id лежит у 11
префабов, и сеть с ними работает.

Откуда берётся: сохранение через `PrefabUtility.LoadPrefabContents`/`SaveAsPrefabAsset`.
В изолированной сцене Mirror не узнаёт префаб и пишет 0, а варианту — id базы. А Mirror
при обычной загрузке префаба пишет канон и помечает префаб грязным — и число скакало
в диффах туда-обратно.

**С 2026-09-27 шум устранён.** `NetworkAssetIdNormalizer` (постпроцессор импорта) после
импорта сетевого префаба с неканоническим числом правит одну строку в файле, и на диске
всегда лежит канон. Если `_assetId` всё же поменялся в диффе — скорее всего, постпроцессор
не отработал (Play Mode, виртуальный игрок MPPM): прогони
`Tools/VR Battlegrounds/VersionControl/Normalize Network Asset Ids`. Сторож —
`NetworkAssetIdOnDiskTests`.

**Не чинить через `SaveAssetIfDirty`.** Первая версия нормализатора сохраняла префаб
средствами Unity — и вместе с `_assetId` на диск ушли перевыданные UltimateXR
`_uxrUniqueId` оружия ([known-issues #11](UltimateXR/known-issues.md)). Только текстовая
правка строки.

Побочный эффект такой проверки: любая сборка, включая `BuildAssetBundles`, заставляет
URP переписать префильтрацию шейдеров в `Assets/URPDefaultResources/*.asset`. После
замера этот файл нужно откатить.

### «Прогон яруса C то зелёный, то красный»

Нестабильных сценариев быть не должно — мигающие ворота хуже отсутствующих.
Был один случай (TEST-01): гонка шла не с таймаутом, а **со временем жизни серверного
процесса** — сервер писал вердикт и звал `Application.Quit` раньше, чем состояние
возвращалось клиенту.

Лечить не увеличением таймаута, а `E2EWait.Until` с `abortIf` — он отличает
«условие не наступило» от «наблюдать стало нечем». Новый сценарий проверять
**не менее 5 прогонов подряд**.
