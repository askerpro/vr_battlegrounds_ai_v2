# Архитектура UI меню (планшет)

Внутриигровое меню — VR-планшет. Как оно выглядит и из чего собирается (раскладка, токены,
набор элементов, превью, проверки) — [`ui-design-system.md`](ui-design-system.md). Здесь — кто
чем управляет и что делает каждый экран. Шрифты и кириллица — [`ui-fonts.md`](ui-fonts.md).
Новый экран — скил `/add-menu-screen`.

## Общая схема

### Глобальные компоненты (DontDestroyOnLoad)

1. **`MenuController`** — синглтон на всё время работы.
   - Открыть/закрыть планшет: ставит его перед лицом игрока (`OpenMenu`), прячет (`CloseMenu`).
   - **Навигация — стек** (`MenuNavigation`, чистый класс): раздел колонки — корень стека
     (`OpenTab`), вложенный экран — `Push`, «Назад» — `Back` (сначала шаг внутри экрана
     `MenuScreen.HandleBack`, потом стек; на корне — закрыть меню). `SwitchTo` — совместимость:
     раздел → `OpenTab`, иначе `Push`.
   - Раз в 0,5 с, пока меню открыто, пересчитывает видимость разделов по правам; раздел стал
     недоступен (сняли админа, выключили отладку) — уводит на раздел по умолчанию.
2. **`MenuPrefabRegistry`** (`Assets/Data/UI/Menu/MenuPrefabRegistry.asset`) — какой префаб
   планшета для устройства и контекста: `DeviceType (VR / Tablet) → Offline / Lobby / InGame →
   режим => префаб`. Сейчас везде `Tablet.prefab`.

### Локальные компоненты

1. **`LocalMenuManager`** — при загрузке сцены определяет контекст (Offline / Lobby / InGame по
   именам сцен `GameNetworkManager`), берёт префаб из реестра, инстанцирует выключенным и
   отдаёт `MenuController.Initialize(MenuView)`.
2. **`MenuView`** — корень префаба планшета: `MenuRoot` (канвас), `Frame` (каркас),
   `Tabs` (разделы колонки), `DefaultScreen` (раздел при открытии — «Обзор»). В инспекторе —
   превью экранов на образцовых данных.
3. **`MenuFrame`** — каркас: левая колонка (разделы, «Назад/Закрыть»), прокручиваемая область
   контента (`ScrollRect` → `Viewport` с маской → `Screens`), полоса главного действия.
   Строится кодом по токенам темы; `MenuStickScroll` на нём листает контент стиком любой руки,
   пока меню открыто, и на это время выключает телепорт (он тоже на стике).
4. **`MenuScreen`** — экран: только содержимое в `Content`, строится через `MenuKit`. Главное
   действие — `SetPrimary`, вложенный экран — `Push`, внутренний шаг назад — `HandleBack` +
   `HasInnerBack`, превью — `BuildPreview`, перестроение «раз в 0,5 с и только при
   изменении» — `RefreshDue`.

Префабы: `Assets/Prefabs/UI/Menu/Tablet/` (`Tablet_Base` — каркас, `Tablet` — вариант с
экранами) и `Assets/Prefabs/UI/Menu/Screens/` (`Screen_Base` + варианты). Раскладку генерирует
`Tools/VR Battlegrounds/UI/Rebuild Menu Frame`.

## Касание пальцем и диагностика попадания

`Tablet_Base` использует `UxrCanvas` в режиме `FingerTips`, обе руки разрешены.
`UxrFingerTipRaycaster` проверяет UI математическим лучом из позиции `UxrFingerTip`
вдоль его `transform.forward`. Наведение начинается при расстоянии до плоскости
элемента вдоль луча не больше 0,05 м; угол между направлением кончика и
`Canvas.transform.forward` не должен превышать 65°. Это проверка направления
служебного объекта, а не соприкосновения меша пальца с кнопкой.

Камера UI при `AutoAssignEventCamera` берётся из `UxrAvatar.LocalAvatarCamera`.
Патч SDK обновляет автопривязку до обработки fingertip/laser-ввода при смене
локальной камеры; спавн временно локального бота или чужого игрока её не заменяет.
Обновляются и выключенные XR-канвасы, ручная камера при отключённом автоназначении
сохраняется. Подробности — [патч 41](UltimateXR/sdk-patches.md#патч-41-камера-ui-не-переходит-к-временно-локальному-сетевому-аватару).

У трёх зарегистрированных игровых аватаров по два включённых `UxrFingerTip`,
на указательных пальцах действующего `UxrAvatar`-рига, без выключенных предков
в префабе. Направление и положение в сохранённой позе различаются:

| Аватар | Отклонение луча от направления концевой кости | Локальный сдвиг кончика |
|---|---|---|
| `Optimized_MEF_Player` | ≈ 0° | 0 |
| `Optimized_MEF_Player_Black` | ≈ 0° | 0 |
| `PlayerControllersCyborgAvatar` | ≈ 30° у обеих рук | 3 мм по локальной Y |

Таким образом, у киборга направление видимого пальца и луча проверки различаются.
Само это различие не доказывает причину пропущенного клика. Существующая проверка
`AvatarLoadoutTests.Кончики_пальцев_для_UI_смотрят_вдоль_пальца` проверяет наличие
обеих сторон и допускает отклонение до 60° от кости; она не проверяет касание
в движении, угол относительно планшета или прохождение событий UI.

`UxrPointerInputModule` формирует нажатие при переходе кончика с передней стороны
плоскости UI на заднюю. Первое наблюдение положения относительно элемента только
инициализирует состояние: если кончик уже за плоскостью, само это положение не
создаёт нажатие. Поэтому для диагностики важны кадры подхода к кнопке, а не только
кадр визуального касания.

Дополнительно `UxrStandardAvatarController.CanHandInteractWithUI` проверяет состояние
руки. Для обычного контроллера UI запрещён при `IsGrabbing` — это состояние жеста
захвата, не только факт удержания предмета. Для ввода с `TrackedHandPose` используется
направление указательного пальца относительно кисти, если доступны нужные кости.
В прокручиваемом `ScrollRect` клик требует нажатия и отпускания над тем же
обработчиком кнопки; вне области, требующей прокрутки, SDK вызывает клик при нажатии.

У SDK нет встроенного отображения луча или точки касания `UxrFingerTip`. В `PlayerBase`
есть отдельные `StandardLaserPointerLeft/Right`: они используют направление
контроллера и не визуализируют проверку пальца. При `UseControllerForward` начало
и направление берутся из `Forward` активной модели контроллера. При dummy-вводе
или отсутствии активной модели используется собственный Transform лазера,
размещённый под `ForwardLeft/ForwardRight` кисти; это не `UxrFingerTip`.
Положение первого сегмента `LineRenderer` рассчитывается из того же `LaserTransform`.
Само наличие видимого лазера не подтверждает попадание пальца или приём лазерного
ввода канвасом: режимы `FingerTips` и `LaserPointers` используют разные raycaster.
`UxrGlobalSettings.LogLevelUI`
на уровне `Relevant` выводит события Press/Release/Click/Drag, но не причины
отклонения касания по углу или состоянию руки. Для установления причины пропуска
нужен снимок позиции и направления кончика, найденного UI-элемента, стороны
плоскости, допуска руки и событий нажатия/отпускания в момент пропуска.

### Проверка пропуска в шлеме

1. Записать скин, руку и кнопку. Отпустить кнопки захвата; подвести палец с расстояния
   больше 5 см почти перпендикулярно планшету, медленно пересечь плоскость кнопки
   и отвести палец обратно. Повторить той же рукой на кнопке раздела и в контенте.
2. В прокручиваемом контенте проверить полный цикл: нажать, затем отвести палец
   перед планшетом, сохраняя наведение на ту же кнопку. Сравнить с боковым отводом
   и с касанием при нажатой кнопке захвата.
3. При повторяемом пропуске сравнить наклоны кисти, особенно у киборга. Зафиксировать
   наличие наведения, звука клика и действия кнопки: это разные этапы обработки.

### Лучи пальцев UI

Проектная интеграция `DebugFingerTipRays` включает SDK API
`UxrFingerTip.RayVisualizationEnabled` только у кончиков текущего локального аватара.
Отрисовка принадлежит патчу `UxrFingerTip.RayVisualization.cs`; игровой компонент
управляет переключателем, подложками и логами. Включение на шлеме:
оба стика 2 с → планшет → «Отладка» →
«Показать лучи пальцев UI». В редакторе — галочка
`Tools/VR Battlegrounds/Debug/UI FingerTip Rays`, доступная и до Play Mode.
Настройка редактора хранится в `SessionState`; на шлеме переключатель живёт только
до завершения запуска. Выключение режима отладки скрывает лучи.

Тот же переключатель создаёт `DebugFingerTipSurface`: прозрачную подложку на весь
канвас, первым дочерним объектом под существующими кнопками. Пустой
`IPointerDownHandler` делает свободный фон интерактивным по штатному
`UxrPointerInputModule.IsInteractive`, не выполняя игрового действия. Выключенный
`UxrControlInput` на подложке подавляет стандартную вибрацию SDK; его обработчики
и drag не участвуют во вводе. Подложка исключена из layout. При выключении
диагностики, закрытии канваса и смене сцены созданные объекты удаляются;
префабы и обычный фон планшета не пересохраняются.
Чтобы штатные изображения фона не перекрывали подложку, у графики без обработчиков
SDK или клика временно выключается `raycastTarget`; исходное значение восстанавливается
при выключении/удалении подложки. Кнопки и области прокрутки сохраняют свои обработчики.

Метки появляются при наведении на **весь экран**, а не только на кнопку, когда
поверхность находится в пределах `UxrCanvas.FingerTipMinHoverDistance` (у планшета 5 см).
Это единый источник дальности fingertip-ввода и его визуализации:
луч пальца должен пересекать прямоугольник
активного канваса `FingerTips`, разрешённого для этой руки. При промахе, закрытии
экрана, выключении `Canvas`/`UxrCanvas` или запрете UI через `CanvasGroup` метки скрыты.
Штатное попадание `UxrFingerTipRaycaster` сохраняет метки при заходе пальца за
плоскость, включая канвасы без предварительного автоматического показа, пока
точка контакта находится в пределах того же порога наведения от кончика.

В SDK `UxrPointerInputModule.DoesAutoEnableLaserPointer` включает только
`UxrLaserPointer` на канвасах `LaserPointers`. Публичный `IsInteractive` ищет
обработчики `IPointerDownHandler`/`IDragHandler` в иерархии до `UxrCanvas`;
фон экрана не обязан иметь такой обработчик, поэтому он добавляется временной
подложкой только на время диагностики. Для предварительного показа луча компонент
берёт fingertip-порог канваса, отдельно проверяет геометрию экрана и не переключает его режим.
`AutoEnableLaserPointer` и `AutoEnableDistance` относятся только к лазерам из руки;
сохранённые в префабе 5 м не участвуют во fingertip-вводе или показе его луча.
В пределах общей дальности угол больше 65° и запрет жестом захвата не скрывают
предварительный луч: они нужны для диагностики жёлтого/красного состояния.

`UxrFingerTipRaycaster.FingerTipMinHoverDistance` делегирует чтение и запись
`UxrCanvas.FingerTipMinHoverDistance`, поэтому изменение настройки канваса сразу
влияет на ввод и показ. Сериализованный порог raycaster используется только
без `UxrCanvas`. `SetupCanvas` переносит начальную настройку модуля в канвас,
в том числе до создания raycaster. Независимого `UxrFingerTip.MaxRayLength` нет.

В исходном SDK визуализатор встроен в `UxrLaserPointer`, но у `UxrFingerTip` его нет.
Подключение второго лазерного указателя создало бы другой поток ввода и потребовало бы
режима `LaserPointers` у канваса. Патч расширяет существующий `UxrFingerTip`: имена
`CurrentRayLength`, `RayWidth`, `RayHitSize` и цветов соответствуют
API лазера. Настройки доступны из кода, включение по умолчанию выключено и не
сериализуется. Обновление идёт через штатное `UxrManager.AvatarsUpdated`, после позы
и IK; как у лазера, читается готовое событие `UxrPointerInputModule`, без `RaycastAll`.
Описание и перенос при обновлении SDK — [патч 40](UltimateXR/sdk-patches.md#патч-40-визуализация-луча-uxrfingertip).

Сфера 4 мм стоит в `UxrFingerTip.WorldPos`, предварительный луч идёт по `WorldDir`
и появляется только когда уже достаёт до экрана, в пределах fingertip-порога канваса (5 см).
До штатного наведения он обрезается
ближайшей пересечённой плоскостью экрана. При попадании `UxrFingerTipRaycaster`
конец луча и сфера 3 мм используют **один `pointerCurrentRaycast.worldPosition`**,
без продолжения за точкой контакта. Если контакт уже позади кончика или совпадает
с ним, отрезок скрывается (`CurrentRayLength = 0`), а обе метки остаются для
диагностики проникновения. Дальность ввода и показа задаётся одним порогом канваса;
при штатном попадании в его пределах приоритет имеет точная точка контакта. Размеры меток не
зависят от масштаба костей. Метки видны сквозь руку и UI: используется штатный
шейдер UltimateXR без проверки глубины из `Resources`. Объекты и материал
освобождаются при выключении, деактивации и уничтожении кончика.

| Цвет | Данные диагностики |
|---|---|
| Жёлтый | Нет попадания штатного raycaster в UI |
| Зелёный | Raycaster нашёл UI-элемент; это ещё не подтверждение клика |
| Голубой | Есть `PressedThisFrame` или удерживается `pointerPress` |
| Красный | `CanHandInteractWithUI` запрещает взаимодействие либо ввод руки не готов |

Компонент читает готовые данные `UxrPointerInputModule`, не запускает дополнительный
`RaycastAll`, не вызывает события UI и не меняет позиции пальцев. При смене аватара
и выключении кончика метки прежнего рига удаляются; у меток нет активных физических
коллайдеров, материалы освобождаются при выключении визуализации.
Нажатия и отпускания записываются в `GameLog.UI.Info` с префиксом `[FingerTipRays]`:
рука, UI-объект, допуск, сторона плоскости, `eligibleForClick` и перетаскивание.
Попадание и pressed-состояние читаются только пока штатный модуль и EventSystem
активны и SDK обрабатывает пальцы локального аватара. Иначе остаётся предварительное
геометрическое наведение, без сохранённой метки и повторных логов старого нажатия.

Изолированные preview-прогоны текущего контракта: **84/84 PASS** — 17 проверок единого
порога, 15 геометрии/границы/движения, 24 доступности экрана, 15 подложки/кнопок
и 13 привязки камеры. Камера бота и реальный SDK-raycast кнопки показали отказ до
исправления и успех после него. Основная сцена и реестры восстановлены после прогонов.
Свежий `AndroidCompileGate`: **PASS**, ошибок в консоли после проверки нет.
Проверка включает границу 5 см и 5.1 см за ней, реальный SDK-raycast,
изменение общей настройки на 3 и 10 см, инициализацию до создания raycaster,
независимость от лазерных настроек и точное совпадение конца с меткой контакта.
Ожидания прежней проверялки «экран в 1 м показывается», «в 20 см остаётся луч 8 см»
и независимого `MaxRayLength` отменены: дальний экран скрыт, а настройка общая с вводом.
Они не подтверждают вид и точность жеста в шлеме. Префабы аватаров не менялись;
ожидания `AvatarLoadoutTests` и `PrefabCompositionTests` остаются актуальными.

Жёлтый цвет сам по себе не различает наведение мимо элемента внутри экрана,
угол больше 65° и отказ штатной проекции UI. Для определения причины такого отказа
дополнительно записать угол
к планшету и найденные кандидаты. Визуальное попадание и зелёная проверка префаба
сами по себе не устанавливают причину пропуска; нужны данные неудачного касания.

## Разделы и экраны

| Раздел колонки | Экран | Префаб | Кому |
|---|---|---|---|
| Обзор | `MenuOverview` (`Main`) | `Screen_Overview` | всем — аналог TAB: ситуация матча, счёт, игроки, хп, время; у админа — кнопки ситуации ([T-33](tasks/T-33-tablet-overview-screen.md)); «Матч с ботами» — игроку, если он один из людей на сервере, и админу ([T-48](tasks/T-48-bots-match.md)) |
| Команда | `MenuTeamSelection` | `Screen_Team` | всем |
| Статистика | `MenuStatistics` | `Screen_Statistics` | всем |
| Калибровка | `MenuPhysicalSpaceSync` | `Screen_Calibration` | всем |
| Админ | `MenuMatchManager` (`MatchManager`) | `Screen_Admin` | админу |
| ↳ Игроки и команды | `MenuPlayersTeams` | `Screen_AdminPlayers` | вложен в «Админ» |
| ↳ Новая серия | `MenuSessionSetup` | `Screen_AdminSeries` | вложен в «Админ» |
| Отладка | `MenuDebug` | `Screen_Debug` | в режиме отладки |
| ↳ Перф-тесты | `MenuPerfTests` | `Screen_DebugPerf` | вложен в «Отладку» |

**Список разделов объявляет режим.** Игровые разделы — поле `GameModeData.menuTabs` (порядок и подписи
режима; пусто — Обзор · Команда · Статистика), системные (Калибровка · Админ* · Отладка*) добавляются
всегда — `MenuTabs.Resolve`. Режим — активный на карте (`MapReferee.ActiveGameMode.ModeData`, в лобби —
разминка); сменился — колонка пересобирается, а если текущего раздела в новом наборе нет, открывается
первый раздел режима. Разделов не больше 6, все ведут на экраны планшета — `MenuTabsTests` по каждому
режиму реестра. Таблица выше — набор по умолчанию.

Видимость разделов — `MenuTab.Visibility` (`Everyone` / `AdminOnly` / `DebugOnly`). `AdminOnly` и
все кнопки админа на экранах решает одно правило `MenuPermissions.ShowAdminUi`: права админа **и**
(админская сборка-планшет `BUILD_ROLE_ADMIN` **или** режим отладки). Игроки на шлемах — обычные
права; настоящий админ — на отдельной сборке; на шлеме админка появляется вместе с отладкой.
Это не права: права проверяет сервер, здесь — только не показывать лишнего. Сторож —
`MenuPermissionsTests` (в коде меню нет других проверок «админ ли»). Входы во вложенные экраны —
`MenuMatchManager.Links` и `MenuDebug.Links` (проверяет `MenuWiringTests`).

**Команда (`MenuTeamSelection`).** Два шага на одном экране: команды (плитки) → скины команды
(плитки); «Назад» со скинов — к командам. Выбор скина отправляет запрос и **закрывает меню**.
Какие команды предлагать, решает `MenuTeamSelection.ResolveAvailableTeams`: команды **активного
режима сцены** (`MapReferee.Instance.ActiveGameMode.Teams`), иначе команды режима, выбранного
на матч (`SessionManager.SelectedGameModeData`), иначе все команды `TeamRegistry`. Активный
режим — первым: выбор администратора описывает следующий матч, и в лобби планшет предлагал бы
команды, которых в лобби нет. Если команда одна (`OffersTeamChoice == false`) — шаг выбора
команды пропускается. У разминки (лобби и любая карта до «Начать матч») своих команд нет,
поэтому предлагаются команды выбранного на серию режима, иначе реестра — Военные и Повстанцы.
Сервер отклоняет запрос команды, которой нет в активном режиме (`TeamChangeRequests.ServerPlayerRequest`);
скин в своей команде разрешён всегда. Когда матч начался (`GameMode.TeamChoiceLocked`), экран
предлагает только собственную команду игрока (сменить скин), а игроку без команды — пояснение:
команду выдаёт админ. Подпись скина — имя без технического префикса `Avatar_`.

**Новая серия (`MenuSessionSetup`).** Режим — ряд кнопок (только режимы матча, `TabModes`:
разминка — отдельное поле `GameModeRegistry.warmup`). Карты под режимом — плитки совместимых
карт (`MapsForMode`), лобби среди них нет. Клик по плитке ставит карту в конец очереди серии,
повторный — убирает (`MapQueue`); номер в очереди — в подписи плитки («2 · TestMap»), плитка в
очереди выделена. «Начать» — главное действие, шлёт `PlayerSession.CmdAdminStartSeries(режим,
карты)`; «Очистить» — второе действие; смена режима очищает очередь. Сервер отбрасывает
несовместимые карты и проверяет право админа (`AdminMapCommands.ServerStartSeries`).

**Админ (`MenuMatchManager`).** Команды матча: «Начать матч», «Пауза», «Продолжить», «Следующая
карта» (на последней карте серии — «В лобби»), «Стоп (конец серии)». Серия после конца карты
сама дальше не идёт: карта стоит в разминке, пока админ не нажмёт «Следующая карта». Каждая
команда видна только когда имеет смысл — правило `AdminMapCommands.IsAvailable` по
реплицированному состоянию; сервер проверяет его ещё раз. Главная команда ситуации (первая
доступная из `PrimaryOrder`: начать, продолжить, следующая карта) — главное действие; «Пауза» и
«Стоп» — в контенте, «Стоп» опасная. Ниже — входы в «Игроки и команды» и «Новая серия».
Нажатие — `PlayerSession.CmdAdminMapCommand`.

**Статистика (`MenuStatistics`).** Таблицы из реплицированных строк `Series`, секции собирает
`SeriesStatsTable.Build`: на каждую карту серии и TOTAL — команды (раунды, карты) и игроки
(У / С / А). Длинная серия прокручивается. Перестраивается раз в 0,5 с и только при изменении.
Карта без серии — та же таблица из одной карты с пометкой «Карта без серии».

**Игроки и команды (`MenuPlayersTeams`).** Строка на каждую сетевую `PlayerSession` этой машины:
ник (поле ввода + «Ник»), кнопка на каждую команду активного режима (текущая выделена). Выше —
названия команд на серию. Главное действие — «Распределить автоматически». Кнопки только шлют
команды админа (`CmdAdminAssignTeam` / `CmdAdminAutoBalance` / `CmdAdminRenameTeam` /
`CmdAdminRenamePlayer`); право проверяет сервер (`SessionPermissions.IsAdmin`, входы —
`TeamChangeRequests`), сервер же чистит ввод (`AdminNaming`). Не-админу — пояснение. Список
перестраивается раз в 0,5 с, только при изменении состава и не пока админ печатает.

**Калибровка (`MenuPhysicalSpaceSync`).** «Калибровать пространство» и «Калибровать рост» —
запускают процесс у `PhysicalSpaceSyncManager`; ход показывает HUD.

### Режим отладки и раздел «Отладка»

Скрытый режим на одном устройстве: админ-пункты, стресс-тест, телепорт, оверлей кадра.
Код — `Assets/Scripts/Debug/DebugMode/`, экраны — `MenuDebug` (`Screen_Debug`) и
`MenuPerfTests` (`Screen_DebugPerf`).

**Включение — только жест «оба стика нажаты 2 с»** (таймер `DebugHoldGesture`, чистый класс).
Одно удержание — одно переключение, отпустили раньше — отсчёт с нуля; тот же жест выключает
режим. Подтверждение — вибрация обоих контроллеров и табличка `PerfOverlay`. Ввод читается
напрямую из XR (`DebugGestureInput`) — работает и в ожидании сервера, когда аватара и планшета
ещё нет; в этом состоянии жест при **уже включённом** режиме делает шлем хостом
(`GameNetworkDiscovery.RestartAsHost`). Режим **не сохраняется** между запусками (шлемы общие).

**Состояние** — статическая служба `DebugMode` (`Enabled`, событие `Changed`). Раздел «Отладка»
виден только в режиме (`MenuVisibility.DebugOnly`); выключили режим — контроллер уводит на
раздел по умолчанию.

**Раздел «Отладка»** (строки — `MenuKit`):

| Строка | Что делает |
|---|---|
| Статус | сеть (хост/клиент), права админа, идёт ли стресс-тест, ботов, последний ответ сервера |
| Оверлей кадра | живой кадр на табличке: среднее, худшее, FPS раз в 0,5 с (`DebugPerfReadout`) |
| Касание меню | «Показать/Скрыть лучи пальцев UI»: точка кончика, его луч и последнее попадание raycaster (`DebugFingerTipRays`) |
| Разделы | «Перф-тесты»; админу — «Матч», «Игроки и команды», «Новая серия» (`MenuDebug.Links`) |
| Боты | админу: «Добавить бота», «Убрать всех» (`BotNetwork`) |
| Телепорт | зоны спавна команд и места перед стенами арсенала (`DebugTeleportTargets`), сеткой |
| Режим | «Выключить режим отладки» |

**Власть — у сервера.** Сетевые сообщения (`DebugModeMessages`, обработчики — `DebugModeNetwork`,
регистрирует `GameNetworkManager`):

- `DebugClientSync` при включении режима и на каждой новой локальной сессии шлёт
  `DebugAdminRequestMessage`. Сервер решает по `DebugAdminPolicy`: права (`PlayerSession.IsAdmin`)
  выдаются, **только если сервер сам разрешает отладку** — Development-сборка (и редактор) или
  флаг запуска `-vrb-debug-admin`. Прод-сервер без флага отказывает, отказ пишется `Warning` и
  приходит на табличку. Выключение режима снимает только права, выданные режимом; хост админ и так.
- Телепорт — `DebugTeleportRequestMessage` с **id точки**, не координатами. Сервер проверяет
  админа, находит точку в своей сцене тем же правилом и зовёт `PlayerController.ServerDevTeleport`
  для аватара **отправителя**. Переносит владелец (`RpcDevTeleport` проверяет автора —
  `MoveAvatarTo` синхронизируемый). Откалиброванного игрока телепорт отрывает от физической
  комнаты — инструмент разработчика.

**Перф-тесты** (`MenuPerfTests`) — стресс-тест с планшета; вход — из «Отладки», «Назад» ведёт
туда же (стек). Выбор живёт в статических полях экрана и переживает пересоздание планшета.

| Часть | Что |
|---|---|
| Режим | «Обычный», «По скинам», «Короткий (10 с)», «Только по карте» (`PerfRunMode`), выбранный — выделен |
| Описание | фазы и длительность — `StressTestPlan.Describe` |
| Куклы | скин («< Скин» / «Скин >»: вперемешку или префаб по имени; в прогоне по скинам — «все по очереди»), число («− кукла» / «+ кукла», 1..`StressTestConfig.MaxPuppets`) |
| Главное действие | «Старт» / «Стоп» (`StressTestLauncher`) |
| Прогон | «Фаза i из N: имя · осталось X с», живой кадр, итог запроса, ответ сервера, путь perf.log последнего прогона — для `adb pull` |

Проверки: `DebugModeTests`, `StressTestPlanTests`, `MenuWiringTests`.

## Как это работает на практике

1. Сцена загрузилась → `LocalMenuManager` берёт `Tablet.prefab` из реестра, инстанцирует
   выключенным, `MenuController.Initialize` собирает экраны и строит разделы колонки.
2. Кнопка меню на контроллере (`MenuInputHandler`) → `ToggleMenu` → планшет перед игроком,
   открыт раздел по умолчанию («Обзор»).
3. Клик по разделу → `OpenTab`; кнопка в контенте → `Push`; «Назад» → `Back`; на корне —
   «Закрыть».
4. Смена экрана: каркас снимает прежнее главное действие, экран в `Show()` ставит своё и
   строит содержимое; прокрутка — в начало.

## Кастомный планшет для режима

Сделайте вариант `Tablet_Base.prefab` (корень с `MenuView`, `UxrGrabbableObject`/`Rigidbody`,
поворот 0) и привяжите его в `MenuPrefabRegistry.asset → RoleConfigurations → SpecificGameModeMenus`.
Сборщик положит в него все экраны из `Screens/`; `MenuDesignRulesTests` проверят его сами
(идут по реестру).
