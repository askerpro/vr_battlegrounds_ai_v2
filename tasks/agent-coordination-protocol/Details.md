## Согласованные требования

- Один актуальный документ на задачу в `tasks/<task-id>/Readme.md`: цель, мотивация, архитектура, план, текущий этап, зависимости, результаты проверок и приёмка. Вспомогательные исходники и документы рядом под Git; сгенерированные и отладочные данные в игнорируемой `reports/`.
- Промежуточные результаты, отладочные данные, пробы и отчёты — в `tasks/<task-id>/reports/` своего worktree, под Git-ignore `/tasks/*/reports/`. Контроль разрешает нативную запись только в отчёты своей зарегистрированной задачи без допуска этапа; остальная запись требует допуска.
- Общий API координации работает через `<git-common-dir>/../.agent-state/coordination/`; код находится в `agent-infra`.
- Документ задачи содержит структурированный блок JSON в fenced-блоке `coordination`. Этот блок описывает план и контракты; автоматически формируемый блок состояния отражает факты координатора.
- Изменять документ может владелец задачи. Публикация использует отдельную ветку `agents/status`, private index и `commit-tree`: HEAD, рабочий индекс и игровой код агента не меняются.
- Общая доска строится автоматически. `tasks/README.md` в ветке `agents/status` — индекс, а не второй вручную редактируемый статус.
- Задача регистрирует все известные этапы: области записи, используемые контракты, затрагиваемые аспекты и зависимости. Для записи поддерживаются точные относительные пути и `/**`.
- Пересекающиеся этапы требуют порядка, а потребитель архитектуры — согласованной ревизии контракта. Независимая работа продолжается.
- Перед записью, запросом Unity worker и вливанием требуется действующий допуск этапа. Допуск не является Unity-арендой.
- Сообщения и подтверждения сохраняются в общей базе. Молчание не считается подтверждением.

## Изменение контрактов

Инициатор публикует запрос: контракт и исходная ревизия, новое требование, причина необходимости, минимальная правка, затрагиваемые аспекты и цена перехода. Владелец контракта публикует следующую ревизию. Влияние определяется по потребителям во всех зарегистрированных планах; неопределённый аспект обозначается `*`.

Предпочтения: использовать действующий контракт → совместимо расширить → добавить адаптер без второго владельца состояния → выполнить ограниченную миграцию. Смена владельца/инвариантов или широкая перестройка требует отдельного архитектурного решения. У API нет права автоматически объявлять такое изменение рутинным.

Каждая ревизия содержит решение о совместимости (`additive` или `breaking`), описание правки, затронутые аспекты, мотивировку, оценку перехода и предоставляющий этап. Владелец и затронутые потребители подтверждают точную ревизию. Инициатор нового требования также участвует. Подтверждения к старой ревизии не подтверждают новую.

Совместимое расширение сохраняет допуски существующих потребителей. Несовместимое согласованное изменение блокирует только затронутые этапы до обновления их требований. Пока изменение предложено, действующий контракт продолжает применяться. Ревизия становится активной только после проверенного и принятого вливания предоставляющего этапа.

## Вливание

Агент публикует желание влить точный SHA принятого этапа. Координатор проверяет:

1. Проверка и приёмка относятся именно к этому SHA.
2. Допуск и контракты актуальны.
3. Необходимые предшественники действительно входят в текущую удалённую `dev` по Git ancestry.
4. Кандидат построен поверх текущей удалённой базы и меняет разрешённые области.
5. Другой push через координатор не выполняется.

Порядок определяется графом зависимостей, а не общим FIFO. Зависимая заявка не мешает независимой. Rebase создаёт новый SHA: требуется обновить проверку, приёмку и заявку. Push — только точного SHA и только fast-forward, без force. При неопределённом результате проверяется удалённая история; слепой повтор запрещён. Вливание не держит Unity-аренду. Публикация базы worker остаётся ответственностью editor-broker.

## Границы технического контроля

- SQLite сериализует регистрацию, согласование, выдачу допусков, резервирование SDK-патчей и заявки вливания.
- Проверка допуска подключается к точкам начала изменяющих действий и Unity request/begin; finish/recovery остаются доступными для безопасного завершения уже начатой операции.
- Прямая запись/прямой push вне подключённых инструментов остаются обходом протокола. Локальный Git-хук сам по себе не заменяет защиту удалённой ветки.
- Семантическую совместимость подтверждают владелец и потребители. Координатор проверяет наличие, полноту и актуальность этих подтверждений.
- Во время подготовки код проверяется в `tasks/agent-coordination-protocol/reports/agent-coordination-build/`; живой runtime и очередь не меняются.
- Активация выполняется после готового пакета и объявления окна обслуживания по AGENTS.md. Старые задачи предварительно регистрируются; незнакомые задачи в строгом режиме получают отказ с понятной инструкцией.
- Игровая логика и тесты механик в этой задаче не изменяются. Для инфраструктуры используются настоящие временные Git-репозитории и SQLite, без Unity.
