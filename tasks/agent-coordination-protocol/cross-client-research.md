[Readme.md](Readme.md), проект доставки — [event-monitor.md](event-monitor.md).

## Документированные интерфейсы и границы

Codex app-server описывает initialize, thread/resume, turn/start и turn/steer.
Последний относится только к активному ходу и требует expectedTurnId. Для idle нужен
новый ход; для этого адаптер должен владеть подтверждённым binding нужного thread.
Наличие ID сохранённого чата само по себе не подтверждает владение живой сессией.
[Официальный интерфейс](https://learn.chatgpt.com/docs/app-server).

Claude Monitor доставляет вывод фонового процесса в сессию, имеет ограниченный срок
наблюдения и условия доступности. Наличие бинарного файла и Git Bash не доказывает,
что инструмент открыт конкретной IDE-сессии.
[Monitor](https://code.claude.com/docs/en/tools-reference#monitor-tool).

Claude asyncRewake документирует пробуждение idle-сессии при exit 2. Обычный async
доставляет результат при следующем ходе. Необходимо проверить запуск, timeout,
повторное выставление наблюдения и единственность доставщика.
[Hooks](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background).

Claude также документирует межсессионные ListAgents/SendMessage: доставка между
tool calls, новый ход в idle, inbound allow/hold/refuse. На Windows транспортом служит
named pipe. Документация описывает Claude → Claude, но не публикует здесь общий внешний
интерфейс для нашего Codex-адаптера. Не использовать приватный pipe-протокол как контракт.
[Межсессионные сообщения](https://code.claude.com/docs/en/cross-session-messaging).

## Соответствие существующему хабу

В agent_coordination/store.py уже есть events(id, recipient, kind, payload, created)
и receipts(task,event). send_message проверяет владельца; inbox выбирает адресованные
и broadcast события без receipt; ack_events идемпотентно подтверждает допустимые ID.
События публикуются в транзакции. Это один транспорт для обоих клиентов.

Потребитель сейчас идентифицируется задачей. Отдельные consumer/session generation,
lease доставщика, watch, coalescing и контроль устаревшего доставщика из будущего плана
не реализованы. Существующий session_id в плане используется guard и не является
реализованным binding доставки. Не создавать второй журнал сообщений в адаптере.

### Архитектурный вопрос перед реализацией и активацией

Пилот подтвердил доставку в собственные управляемые сессии. Он не доказал управление
уже открытыми пользовательскими чатами Codex или доставку Monitor в IDE Claude.
Продакшен binding нельзя объявить известным на основании ID сохранённого чата.

Нужно выбрать модель эксплуатации:

1. Управляемые сессии: запуск/подключение агента через адаптер с подтверждённым
   binding, очередью ходов и жизненным циклом. Даёт проверенный путь автоматической
   реакции, но меняет способ запуска агентов. Перенос существующих задач — отдельный
   handoff, существующие чаты автоматически не подменяются.
2. Существующие чаты: агент сам подключает watcher в своём клиенте; гарантированное
   idle-пробуждение Codex пока недоступно по результатам исследования. До подтверждения
   интерфейса доставка происходит при следующем ходе/входе, guard продолжает работать.

Историческая рекомендация исследования для автономной доставки — первый вариант.
Пользователь затем выбрал более простой маршрут штатных сообщений и ручного inbox;
он описан в communication-policy.md. Watch, fencing и активация управляемых сессий
не реализованы и отложены; ожидание выбора пользователя больше не является блокером.

1. Использовать две явно тестовые сессии с отдельными binding и временным состоянием
   хаба под reports/. Существующие игровые задачи и их inbox в пилот не включать.
2. В Claude проверить наличие Monitor в конкретной сессии. Запустить ограниченное
   наблюдение; после завершения первого ответа отправить тестовое событие. Проверить
   реакцию без нового сообщения человека. asyncRewake проверить отдельным запуском.
3. Для Codex сначала локализовать молчание proxy: сопоставить официально поддерживаемый
   transport и версию, получить initialize response. Не перезапускать общий daemon
   ради проверки. Если подключение не подтверждается, использовать отдельный временный
   app-server с собственной тестовой сессией и честно ограничить результат этим вариантом.
4. Провести Claude → хаб → Codex → хаб → Claude. Сообщения содержат уникальный event_id
   и nonce; ответ цитирует их, ACK выполняется после чтения состояния. Реакция не меняет
   игровой код, контракты, допуски, очередь или worker.
5. Убить только тестовый доставщик после вывода, до ACK; восстановить и получить то же
   событие. Повторный ACK безопасен; повторная доставка не повторяет принятое действие.
6. Проверить два доставщика, idle/active/закрытый клиент, смену binding и остановку
   пользователем. Записать задержку, event_id, клиентский turn ID и outcome без токенов.

Критерий пилота выполнен для управляемых тестовых сессий: корректные ID, обратный
ответ и отдельный PASS восстановления. stdout, initialize response и turn/start
accepted сами по себе недостаточны без завершившейся реакции. Продакшен-приёмка
не выполнена.

Историческое предложение исследования — bounded watch плюс клиентские адаптеры.
Пользователь отложил этот вариант и выбрал inbox со штатными сигналами; собственного
исполнения этого проекта сейчас не планируется. Конфликты блокирует ядро независимо
от уведомлений.
