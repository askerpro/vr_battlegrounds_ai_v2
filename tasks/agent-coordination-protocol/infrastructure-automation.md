## 1. Inbox: регрессия и интерфейс

Сохранить list API CoordinationStore.inbox и result CLI. Добавить inbox_page с метаданными,
свежие адресные события впереди broadcast сообщений, затем служебная история.
CLI inbox принимает --cursor для страницы стабильного снимка и --event для конкретного ID.
Ответ дополнительно содержит pagination: pending_total, direct_pending, has_more, next_cursor,
snapshot_event_id. Cursor не ACK и не постоянная отметка прочитанного; новый опрос начинает
первую страницу, ACK всегда явный. Cursor привязан к task и снимку, страницы не пересекаются.
Не скрывать broadcast сообщения и историю: они доступны на последующих страницах.

RED → GREEN: 100 старых broadcast + новый direct; direct за старым курсором;
точный event вне страницы; второй владелец/чужое событие; unread replay; вставка события
между страницами; последний cursor не используется как начало следующего опроса.

## 2. Публикация: долговечный служебный тикет

Новая команда request-base --owner --sha --source-root --key возвращает тикет сразу.
SHA должен входить в фактически полученную origin/dev, источник — тот же common Git.
Служебный тип тикета publish_base занимает место общей очереди; повтор key идемпотентен.
Один исполнитель брокера без LLM обрабатывает служебный тикет на голове, не прерывает
агентскую аренду/Play/maintenance pause. Токен переключения выдаётся только исполнителю.
Изменение Git/Unity использует существующие mutex, журнал, readiness и recovery.
Уже опубликованный SHA/предок текущей базы — DONE already_published; откат базы запрещён.
Старые заявки worker сохраняются и проходят существующую проверку совместимой базы.

RED → GREEN: FIFO до/после agent ticket; отказ paused/recovery/dirty/unaccepted;
дубликат; конкурентные исполнители; текущая база включает SHA; restart процесса;
сбой после switch/config; сохранение старых заявок и results; отсутствие приватных токенов
в публичном состоянии. Уведомления результата — долговечный inbox, native только сигнал.

## 3. Исполнитель и развёртывание

Скрытый процесс pinned runtime: start/status/stop, один OS mutex, heartbeat и bounded poll.
Автоматическое обеспечение запуска при request-base, без ожидания со стороны агента.
Stop прекращает получение новых тикетов; активный переход завершает безопасно.
После падения активный переход не повторять: RECOVERY_REQUIRED, штатное восстановление.
Не запускать из произвольной ветки агента. Старый publish-base оставить обслуживающему.

Проверки: адресные unittest RED/GREEN, весь затронутый набор broker/coordination,
пакет CLI во временных Git/SQLite/fake-Unity стендах, независимое финальное ревью.
Затем согласованное окно обслуживания, deployment committed runtime, проверка статуса,
снятие только своей технической паузы и объявление через inbox.
