## Принципы (действуют для всех этапов)

- Один формат станций: слоты собирает генератор при запуске карты на каждой машине; в префабах и сценах их нет.
- Сборщик станции не знает геометрии: пресет («оружие → ряд»), ряд корпуса (`ArsenalSlotRow`), сборщик слота
  (`ArsenalSlotBuilder`), раскладка слота (`ArsenalSlotLayout`: умолчание у префаба слота, своя у оружия).
- Применять, не проверять (решение 2026-10-07): размеры оружия и «влезает ли» генератор не знает.
- Обратной совместимости и двух версий одного механизма не держим (решение 2026-10-08).
- Unity — только в своей аренде; тесты изменённой механики — после приёмки пользователем.

## Этап `acceptance` — сеть, шлем, постоянные проверки

Цель: новый флоу проверен там, где хост его не покрывает. Сейчас доказано только хостом (аренда 266).

1. **Два клиента и выделенный сервер** — `PlayModeTestStand` ([стенд](../../Docs/test-stand.md)), своя аренда:
   - клиенты собирают ту же станцию: одинаковые индексы и ID слотов, отпечаток описания совпал с config сервера;
   - выдача оружия и магазинов приходит на клиенты, захват со стены, возврат в коробку приёма, пополнение;
   - экономика и владение стеной у двух игроков разных команд.
2. **Поздний вход и перезагрузка той же карты:** клиент подключается после выдачи; `LoadMap` той же карты —
   новый ключ запуска, старые ID не адресуют новые слоты; удерживаемое и купленное оружие переживает разборку
   станции (не уничтожается через родителя).
3. **Шлем Quest 2/3** (пользователь): дотягиваемость обоих рядов, ощущение коробки приёма, развёртывание, время
   сборки при загрузке карты (замер, без заявления «PASS» без цифр).
4. **Постоянные проверки** после приёмки: PlayMode-тестов в проекте нет — сборщик (`ArsenalComposer.NotPlaying`)
   закрепить либо PlayMode-сборкой тестов (новая сборка — отдельное согласование), либо сохранённой Play-пробой
   `tools/station-probe.cs.txt` как диагностикой. Решение — в начале этапа.
5. Найденные дефекты — правка в `Assets/Scripts/Arsenal/` этого этапа; чужие области — сообщением владельцу.

Готово, когда пользователь принял пункты 1–3 и дефекты закрыты или переданы.

## Этап `prefab-preview` — превью станции в Prefab Mode

Цель: открыть корпус станции в Prefab Mode и увидеть слоты выбранного пресета — оружие, магазины, карточки,
опоры, коробку приёма — без сохранения в префаб. Сейчас корпус в редакторе пустой: видны только ряды.

**Что сохраняется из прежнего дизайна** (механизм, [design.md](design.md#preview-lifecycle-и-сохранение)):
оверлей — соседний корень в сцене PrefabStage вне поддерева префаба, флаги DontSave/NotEditable и маркер владельца;
только визуальные клоны (MeshFilter/MeshRenderer, материалы, TMP карточки), без SDK, NetworkIdentity, физики и
контроллеров; очистка при закрытии стадии, перезагрузке домена, входе в Play, выходе; сохранение префаба не
захватывает оверлей (проверка YAML после Save/reopen); обновление не перечитывает префаб с диска.

**Что меняется под новый флоу:**
- вход превью — ряды открытого корпуса + пресет (выбор в SessionState) + префаб слота ряда + раскладка
  (`ArsenalPresentationResolver.Resolve`) — тот же расчёт, что у сборщика, без второго вычислителя поз;
- размещение — та же формула ряда (`ArsenalSlotRow.Arrange`) без создания реальных слотов;
- индикатора «Fits/TooSmall/Universal» и выбора корпуса нет;
- правка поз — не здесь, а на стенде раскладки; превью только показывает и обновляется при изменении ряда,
  пресета или раскладки.

**Шаги:** уточнить дизайн одним разделом в design.md (входы и обновление) → `ArsenalPrefabStagePreview` (Editor) →
проверки: оверлей не попадает в YAML, нет грязного префаба без правок, переживает перезагрузку домена, очищается →
приёмка пользователем в Prefab Mode.

## Этап `decorations` — нужен выбор пользователя

Прежний дизайн: корпус — отдельный артворк из каталога с вместимостью рядов, генератор подбирает «наименьший
подходящий» и отказывает, если мал. В новом флоу это противоречит принципам: корпус — префаб станции в сцене с
рядами, ряд вешает сколько угодно слотов, «влезает ли» не проверяется. Сейчас каталог корпусов пуст
(`_decorations: []`), сборщик выбор корпуса не использует, но `DecorationId` выбора попадает в config запуска карты
(`MapRunConfig`, область map-runtime-bootstrap).

Варианты:
- **A. Корпус = префаб станции (рекомендую).** Разное оформление — варианты префаба корпуса (Prefab Variant) с
  теми же ключами рядов; карта ставит нужный. Из генератора убрать каталог корпусов, `ArsenalDecorationDescriptor`
  и выбор (`Select`); из config запуска — `DecorationId` (согласовать с map-runtime-bootstrap). Один владелец
  оформления, без второго механизма.
- **B. Сменное оформление поверх корпуса.** Каталог чистого артворка (рамки, вывески, материалы) без рядов и
  функциональных частей; карта или пресет явно называет оформление, генератор ставит его на корпус. Без
  вместимости и подбора. Нужен новый дизайн: точка крепления, сеть (одинаково на клиентах), окклюзия.
- **C. Прежний дизайн с подбором по вместимости** — противоречит «применять, не проверять», не рекомендую.

После решения этап проектируется заново (A — короткая чистка; B — дизайн и план).
