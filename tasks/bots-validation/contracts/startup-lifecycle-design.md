# Старт сервера и первое подключение клиентов — дизайн на согласование, 2026-10-19

Статус: **согласован пользователем 2026-10-19 (S1 да; S2 — срок 180 с; S3 — только замер); S1+S2 реализованы, приняты пользователем (аренда 847) и влиты в origin/dev 1aadb3dc3 (2026-10-20).** Основа — анализ
`reports/trace829/startup-architecture-options.md` (вне Git) и Handoff §7. Цель — чтобы
клиенты подключались при любой длительности старта сервера и любом порядке запуска процессов,
без опоры на удачную роль main/clone.

## 1. Что ломается сейчас (факты trace829)

| Класс отказа | Механизм | Где |
|---|---|---|
| A. Клиент раньше сокета | Явный клиент (localhost) стучится, пока сервер ещё не открыл UDP; `KcpClient.RawReceive` получает SocketException и сразу отключается. Повтора нет — процесс навсегда Offline. Сервер открыл порт примерно через 80 с. | localhost8 |
| B. Сокет раньше карты | `StartServer` открывает порт и сразу рекламирует сервер, затем грузит TestMap1 и спавнит ботов. Клиент успевает подключиться, а сервер стоит в длинном кадре 12 с без отправки, и KCP по тишине 10 с рвёт соединение. | discovery8 |

Общая причина: «сервер запущен» — одно состояние, хотя на деле это четыре разных момента:
логически активен, сокет открыт, карта готова, сервер объявлен. Сейчас сокет и объявление
наступают **до** готовности карты.

## 2. Предлагаемое решение — три этапа, каждый со своей приёмкой

### S1. Сервер открывает порт только после готовности карты (класс B)

Владелец — `GameNetworkManager` (единственный писатель доступности сервера).

1. `ApplyRole` для Server/Host выставляет `NetworkServer.listen = false` и вызывает штатный
   `StartServer`/`StartHost`. Mirror поднимает серверный граф (active=true, handlers,
   `OnStartServer`, SessionContext, MapRunAuthority), но **пропускает** `Transport.ServerStart` —
   сокета нет. Штатный маршрут первой карты (`ServerStartupRoute` → `ServerChangeScene` →
   `MapBootstrap`) работает без изменений: тот же один map run, тот же MapRunKey.
   Проверено по исходнику Mirror: `NetworkServer.Listen` при `listen=false` пропускает только
   `Transport.ServerStart`, а `NetworkServer.Shutdown` возвращает `listen = true` — поэтому флаг
   выставляется владельцем перед каждым запуском, а не один раз.
2. Объявление (`AdvertiseServer`) из `ApplyRole` убирается: discovery-ответы начинаются только
   после публикации.
3. Состояние сервера: `PreparingWithoutSocket → Publishing → Published`, плюс `Failed`/`Stopping`.
   Переход в `Publishing` — по квитанциям готовности от владельцев (не по таймеру):
   - `MapBootstrap.IsServerReady` (descriptor и режим закоммичены);
   - режим завершил `BeginWhenReady` (команды, арсенал), и при включённых ботах стенда —
     квитанция их создания от `DebugOrchestrator` (только Editor-стенд; игровая карта от неё
     не зависит);
   - сетевая граница кадра: следующий EarlyUpdate после поздней квитанции.
4. `Publishing`: один вызов `Transport.ServerStart()`, проверка `Transport.ServerActive()`,
   затем `NetworkServer.listen = true`, затем `AdvertiseServer`. Ошибка bind (порт занят) —
   `Failed` с именованной ошибкой, штатный `StopServer`, без повторов. Отказ сборки карты
   (`MapBootstrapStage.Failed`) — `Failed` без публикации и без остановки: отказ уже принадлежит
   `MapBootstrap`, клиенты получают свой срок ожидания.
5. Host: локальный клиент подключается внутри процесса и сокета не требует — он входит в мир
   сразу. Удалённые клиенты — после той же публикации. Отдельная явная ветка в том же владельце.
6. Live-смена карты (`MapLoader.LoadMap`) сокет **не закрывает**: подключённые игроки остаются,
   это отдельная фаза перехода карты (см. S3), не повтор S1.
7. Диагностика: маркер `server-listening` делится на `server-active` (OnStartServer) и
   `server-published` (подтверждённый bind).

### S2. Клиент ждёт первого подключения с общим сроком (класс A)

Владелец — `GameNetworkDiscovery` (уже владеет StartClient/StopClient и адресом).

Начальная фаза до первого успешного подключения:
`WaitingForEndpoint → Connecting(попытка N) → Synchronizing → Online`, конечные `Failed`
(именованная причина) и `Cancelled`.

- Discovery-режим: клиент просто слушает объявления; раньше публикации сервер не отвечает,
  поэтому ранних попыток нет.
- Явный адрес: при обрыве **до первого Online** (SocketException, тишина, отказ handshake) —
  новая попытка после полного `StopClient` с паузой 1 → 2 → 4 → 5 с (потолок 5 с).
  Общий срок по умолчанию **180 с** (решение пользователя) (PlayLaunch передаёт свой `TimeoutSeconds`). По истечении —
  `Failed: initial-connect-timeout` с числом попыток и последней ошибкой, без бесконечного Offline.
- «Online» в начальной фазе — завершённый handshake (`OnClientConnect`); дальнейшая синхронизация
  сцены идёт штатно.
- После первого Online начальная фаза закрыта навсегда: дальнейший обрыв — штатное поведение
  (Offline, без самовольного переподключения). Пользовательский disconnect/cancel сразу
  прекращает попытки.
- Эпоха стенда (`ConnectionEpoch`) растёт только при реальном подключении — неудачные попытки её
  не трогают, guard `ExpectedConnectionEpoch >= 1` не меняется. PlayLaunch только наблюдает
  фазы и не вызывает Mirror сам.

### S3. Бюджет синхронизации после handshake — только если понадобится

После S1 сервер к моменту подключения уже прошёл тяжёлый старт, и класс B для первого входа
уходит. Остаётся долгая загрузка сцены на **клиенте** после handshake (сервер может выкинуть его
по тишине 10 с). Предложение: сначала измерить после S1+S2; если реальные паузы клиента > 10 с
повторяются — отдельно согласовать per-peer стартовый таймаут через продуктовый подкласс
KcpTransport (только новые peers, возврат к рабочим 10 с после готовности клиента, уже играющих
не трогать). Ограничение: порог `dead_link` живого peer без патча SDK не переключается; глобальное
повышение таймаута — не вариант. Сейчас S3 **не делаем**, только мерим.

## 3. Чего дизайн не меняет

- Таймауты KCP, MaxRetransmits, SDK Mirror/kcp2k — без изменений (S1, S2).
- Один SessionContext, один map run, live-смена карты только через `MapLoader`.
- Роль main/clone не влияет на результат; успешный role-swap не считается приёмкой.
- Медленный вход в Play на worker — отдельный отложенный пункт (после перезапуска worker 5–6 с).

## 4. Ручная приёмка

1. Discovery и localhost, 0 и 8 ботов, dedicated + 2 PC Spectator: оба клиента Online, Ready.
2. Клиент запущен раньше сервера на десятки секунд: ждёт в `Connecting`, подключается после
   публикации; при отсутствии сервера — `Failed: initial-connect-timeout` за 180 с.
3. Длинная подготовка сервера > 10 с (8 ботов): порт открывается после карты, разрывов по тишине нет.
4. Порт занят — `Failed` у сервера с понятной ошибкой; disconnect/cancel клиента прекращает попытки.
5. Host + удалённый клиент; смена карты через MapLoader с подключёнными игроками.
6. В логах раздельно: server-active, server-published, фазы попыток клиента; один bind на запуск.
7. После приёмки пользователем — тесты на состояния S1/S2 (до этого новых expectations нет).

## 6. Реализация относительно дизайна (по ревью network/launch-infra, 2026-10-20)

- Состояния сервера в коде: `Stopped / PreparingWithoutSocket / Published / Failed`. Отдельных
  `Publishing` и `Stopping` нет: публикация — один синхронный шаг `PublishServer`, остановка — штатный
  `OnStopServer`.
- Квитанция «боты стенда созданы» не отдельная: `DebugOrchestrator` создаёт их синхронно в подписчике
  `ServerSceneChanged`, а `GameNetworkManager` снимает флаг смены сцены после подписчиков.
- Срок первого подключения — константа 180 с (`InitialConnectDeadlineSeconds`); PlayLaunch свой
  `TimeoutSeconds` в клиент не передаёт.
- Открытые хвосты (следующей правкой, с проверкой пользователем):
  1. `RequestClientConnect` (адресный reconnect стенда) должен закрывать начальную фазу, если та ещё
     в `WaitingRetry`, — иначе после обрыва возможна самовольная попытка.
  2. Текст `RequestClientDisconnect`: попытки отменяются до проверки `ClientNotActive`.
  3. PlayLaunch: готовность серверного участника — `Published`, а не только `NetworkServer.active`;
     показать `Availability`/`InitialPhase` в Snapshot; startup JSONL в списке архивов Status.
  4. Путь «Лобби, затем карта»: публикация не ждёт принятой, но ещё не начатой отложенной загрузки
     `MapLoader` (запас в один кадр) — согласовать квитанцию с gameplay. Публикация в Лобби допустима.
