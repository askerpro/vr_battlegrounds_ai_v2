# SDK-патч 75: размещение в якорях доезжает позднему клиенту

2026-10-12. Этап `grab-authority/late-join-anchors`. Номер зарезервирован штатным
`patch-reserve` для manipulation. Метка в коде — `VR Battlegrounds patch 75`.

## Дефект

Поздний клиент получает снимок `SaveStateChanges(..., ChangesSinceBeginning, ...)`
(`NetworkStateRelay.CmdRequestInitialState`). Переменная попадает в снимок, только если
отличается от начального значения на сервере (`UxrStateSaveImplementer_1.SerializeStateValue`,
`_initialValues` фиксирует `StoreInitialState` после первого кадра). Предмет, рождённый в
якоре (спавн и `PlaceObject` в одном кадре — пистолет в кобуре из
`PlayerLoadoutManager.ServerGiveWeapon`), а также вынутый и возвращённый, имеет
`_currentAnchor`/`_currentPlacedObject` равными начальным — в снимок они не попадали, и у
позднего клиента кобура пуста. Если значения записывались, чтение присваивало только поля:
ни родителя, ни выравнивания в якоре, ни kinematic. Хват доезжал, т.к. `_currentManipulations`
пишется всегда. Прецедент того же класса — `_rounds` магазина (`DontCheckCache`).

## Что изменено

- `UxrGrabbableObject.StateSave.cs` — `_currentAnchor` пишется с `DontCheckCache`; в конце
  чтения (`level > ChangesSincePreviousSave`) — вызов согласователя
  `UxrGrabManager.ReconcileLoadedPlacement(this, anchorBeforeLoad)`.
- `UxrGrabbableObjectAnchor.StateSave.cs` — `_currentPlacedObject` с `DontCheckCache`; после
  чтения — `UxrGrabManager.ReconcileLoadedAnchor(this, placedBeforeLoad)`.
- `UxrGrabManager.StateSave.cs` — согласователь (две точки входа, общие
  `ApplyLoadedPlacement`/`DetachLoadedPlacement`):
  - предмет в якоре: взаимные ссылки (вытесненный предмет и прежний якорь очищаются, только
    если указывают на эту пару), `isKinematic = true`, родитель `anchor.AlignTransform` при
    `UseParenting`, выравнивание `ApplyAlignment` по `DropSnapMode` — те же шаги, что у
    `PlaceObject` без `Smooth`; `LocalPosition/RotationBeforeUpdate`; `ActivateOn*` якоря как у
    `PlaceObject`;
  - предмет ушёл из якоря: ссылка якоря очищается, если указывает на предмет; родитель
    меняется на `anchor.transform.parent` (как `RemoveObjectFromAnchor`) только если предмет
    всё ещё висит на `AlignTransform`, не удерживается и снимок не переставил родителя;
    kinematic берётся из снимка.
  - Фактическое восстановление/снятие пишет одну строку `State load placed|removed ... (patch 75 ...)`
    при `LogLevelManipulation >= Relevant` (в проекте — Debug); повтор для уже согласованной пары молчит.
  - Нет `BeginSync`/`EndSync`, `propagateEvents`, событий `Placing/Placed/Removing/Removed`, второго
    хранилища: состояние — только поля SDK. Повторный вызов для уже размещённой пары — no-op.

## Якорь, которого у клиента ещё нет (условие network A3, ACK 5300)

Ссылка на незарегистрированный компонент бросает `UxrComponentNotFoundException` уже после
полного чтения (`BinaryReaderExt.ReadUniqueComponent`: метка, Guid, отладочная строка), поэтому
поток не сбит. Раньше исключение пропускало весь компонент предмета (`LoadStateChanges`:
«Cannot deserialize a component»).

- Предмет (`_currentAnchor` не разрешён — якорь на аватаре/боте, который появится позже; id
  через `CombineUniqueId` при спавне аватара): исключение ловится только при чтении, остальное
  состояние предмета читается, `_currentAnchor = null`, согласователь запоминает
  `id якоря → предмет` (лог `State load: anchor <id> of <item> ... deferred`) и подписывается
  на штатное `UxrComponent.GlobalRegistered` только пока есть ожидание. Регистрация якоря под
  этим id (после `CombineUniqueId` — уже с итоговым id) → то же размещение (`State load placed`).
  Если предмет за это время взяли или положили событием — ожидание снимается с предупреждением.
  Новый снимок предмета отменяет прежнее ожидание. Это не копия grab-state: только
  неразрешённая ссылка.
- Якорь (`_currentPlacedObject` не разрешён): явный отказ `LogWarning` с id, якорь пуст.
  Откладывать нельзя: предмет может зарегистрироваться до своего `Awake`, который перезапишет
  `CurrentAnchor = _startAnchor`. Свой снимок предмета, если придёт, поставит его с предметной
  стороны.
- Не покрыто: если у предмета в снимке записан родитель-трансформ, указывающий на
  незарегистрированный якорь (предмет положен в якорь после спавна), исключение бросается в
  `SerializeStateTransform` до чтения позы — продолжить поток нельзя; SDK пропускает компонент с
  предупреждением, содержащим id (`LoadStateChanges`, `LogLevelCore >= Warnings`).

## Поза после снятия с якоря (5133, условие network B)

`RemoveObjectFromAnchor` делает предмет динамическим (смерть/удаление аватара), но событие
снятия не несёт позы, а `RegularPhysicsSyncCoroutine` стартовала только в `RaiseReleasedEvent`.

- `UxrGrabManager.Manipulation.cs`, `RemoveObjectFromAnchor` — после `EndSyncMethod` вызов
  `grabbableObject.StartPhysicsSyncAfterAnchorRemoval()` (событие снятия уходит первым).
- `UxrGrabbableObject.cs` — `StartPhysicsSyncAfterAnchorRemoval`: при `SyncGrabbablePhysics`,
  динамическом теле, не в руке и не в якоре, активном объекте, без NetworkTransform/
  NetworkRigidbody и **не** внутри `UxrManager.IsInsideStateSync` (повтор события на другой
  машине) запускает ту же `RegularPhysicsSyncCoroutine(null, interval)`: первое
  `UpdateRigidbody` — сразу, затем раз в `GrabbableSyncIntervalSeconds` до засыпания. Если снятие
  вложено в другой синхронизируемый метод (`SyncCallDepth > 0`, вложенное событие в сеть не
  уходит), первое `UpdateRigidbody` — кадром позже (`DeferredPhysicsSyncCoroutine`).
  `UpdateRigidbody` без руки проходит `StateEventAuthority.ShouldSend` (у лежащего предмета нет
  держателей). Второго транспорта нет. Опоздавший получает позу лежащего предмета снимком
  (трансформ предмета пишется при отличии от начального).
- Автор снятия — машина, вызвавшая его на верхнем уровне: сервер при смерти/удалении аватара,
  клиент — при своём выбросе магазина (`MagazineEject`); такой клиент теперь тоже шлёт позу.

## Хук «после загрузки»

У `UxrManager.LoadStateChanges` нет события конца загрузки (только покомпонентные
`StateSerialized`/`VarSerialized`). Компоненты читаются в порядке `SerializationOrder`
(синглтон `UxrGrabManager` — раньше предметов и якорей), поэтому согласование идёт в конце
`SerializeState` чтения предмета и якоря — по образцу патча 71 (согласование в
`UxrGrabManager.SerializeState`). Порядок предметов и якорей в снимке произвольный; обе
стороны пишутся всегда, прочитанный позже повторяет то же размещение.

## Почему не трогали запись трансформа

`SerializeStateTransform` решает по каждой переменной (родитель, пространство, поза) сравнением
с начальным значением; принудительная запись родителя невозможна без правки
`UxrStateSaveImplementer_1` (вне этапа). Не нужна: поза в якоре однозначно выводится из
якоря и `DropAlignTransform`, согласователь ставит её сам. Если родитель предмета изменился
относительно начального (вышел из якоря), он и поза пишутся штатно (`parentSerialized` →
`DontCheckCache` для позы).

## Не менялись

Патчи 12, 16, 18, 25–28, 67, 71, 73; `UxrGrabManager.cs`; `Devices/`; запись трансформа; `RaiseReleasedEvent`.

## Цена

Каждый включённый `UxrGrabbableObject` и `UxrGrabbableObjectAnchor` теперь всегда входит в
снимок `ChangesSinceBeginning` (раньше — только изменённые). Инкрементальные
`ChangesSincePreviousSave` не затронуты (ветка выходит раньше).

## Риски

- Игровой код, ждущий события `Placed` на клиенте, при позднем входе его не получит — как и
  раньше для тихой раскладки (`AnchoredItemCollisionIgnore` сверяет по иерархии, ему хватает).
- Предмет в якоре с `DontRelease` и одновременным хватом согласователь выравнивает так же, как
  `PlaceObject` в момент размещения.
- Позднему клиенту нужны и предмет, и якорь (аватар) к моменту загрузки снимка;
  отсутствующий адресат `NetworkStateRelay` уже логирует ошибкой.
