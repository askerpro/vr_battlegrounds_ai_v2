# Mirror patch 3 — NetworkTransformUnreliable: последнее полученное значение осей и ключевой снимок

2026-10-13, задача `mirror-nt-keyframe`, этап `nt-patch`. Номер получен через `patch-reserve` (Mirror, 3).
Маркер в коде: `VR Battlegrounds patch 3`. Файл: `Assets/ThirdParty/Mirror/Components/NetworkTransform/NetworkTransformUnreliable.cs`.

## Что

- Приёмник (оба направления): поля последнего полученного значения осей (`clientReceived*`, `serverReceived*`)
  отдельно от буферов интерполяции. Заполняются после `UpdateSyncData` в `OnServerToClientSync` и
  `OnClientToServerSync`; на клиенте — также позой спавна из `OnDeserialize(initialState)`; телепорт
  (`OnTeleport`) обновляет их. `ResetState` их не трогает.
- `UpdateSyncData`: непришедшие оси берутся из `GetReceivedBaseline` — последний снимок буфера, иначе
  сохранённое полученное значение, иначе (ничего не получено) трансформ цели. Раньше после `ResetState` бралась
  поза трансформа.
- Отправитель (`UpdateServerBroadcast`, `UpdateClientBroadcast`): раз в `keyframeInterval` (новое поле, 1 с,
  0 — выкл.) отправляются все синхронизируемые оси, минуя onlySyncOnChange. Первая отправка — полная.

## Зачем

Находка bots 5510, A/B 5532 (стенд net-round1, тикет 548): после `ResetState` трансформ цели (кость запястья
удалённого аватара) уже изменён на приёмнике хватом, IK и отдачей, и чтение назад запекало эти правки в буфер —
«храповик», запястья бота у наблюдателя уезжали на 1–2,7 м. Отправитель слал только изменившиеся оси без
полного снимка: потерянная ось, которая потом не меняется (высота камеры), не восстанавливалась — камера бота на
полу у части наблюдателей. Касается и аватаров людей (тот же класс).

## Поведение

- Формат `SyncData` не меняется. Трафик: +1 полный снимок в секунду на NT (~25 Б), даже на неподвижном объекте.
- Для подклассов (`NetworkRigidbodyUnreliable*`) поведение то же: их `OnTeleport` вызывает базовый.
- Решение: вердикт network 5520. Отклонены NetworkTransformReliable (блокировка очереди, трафик на Quest),
  `onlySyncOnChange = false` (неизменившиеся оси всё равно не шлются) и входной прокси avatar-ik (дороже).

## Проверки

- Офлайн-компиляция `Mirror.Components` (Unity 6000.4.1f1 csc, без weaver): 0 ошибок, 0 предупреждений в файле.
- Дальше: Unity worker (компиляция с weaver, AndroidCompileGate, EditMode Network), ярус C стенда bots
  (S2C, H1C, поздний наблюдатель — камера ±1 см), приёмка пользователем.

## Ярус C (bots, тикет 551, вход 6ac69feda) и доработка

- Храповик устранён: строгий bakedFromTransform wristR 0–2 на кейс (было 17–28), камера 0 (было до 83); дрейф
  запястий бота у наблюдателя, медиана 3–7 мм (было до 155–623); ствол↔луч, медиана 1,2–1,8°; камера позднего
  наблюдателя 97/97 в ±1 см (критерий avatar-ik выполнен, 5611); трафик бота у клиента 892 Б/с (+~10%).
  Технически принято bots (5607).
- Доработка по avatar-ik 5611: `keyframeWarmup` (0,5 с) — с первой отправки каждая отправка полная. Причина:
  клиент молча отбрасывает NT-сообщения, пришедшие до обработки спавна, а камера аватара получает позу кадром
  позже спавна (SpawnMessage несёт 0,0,0) — без прогрева тело у присутствующих наблюдателей до ~1 с строилось
  от пола. Офлайн-компиляция `Mirror.Components`: 0 ошибок.
- Открыто: левое запястье H1C G (9/47, ΔY −0,8 м) — bots проверяют обновлённой моделью окно ≤1 с после смены тела.
- Левое запястье H1C G закрыто (bots 5624): 55 из 56 строгих событий attempt-7 — артефакты прежней модели
  (patched ΔY ≤ 0,95 см), одно реальное — камера в окне спавна (0,069 с).
- Ярус C поверх f876148f9 (bots 5628, тикет 556): модель «patched», snapshotCheck 0 расхождений на 18 090 снимках;
  bakedFromTransform 0 по root/camera/wristR/wristL; прогрев — все отправки первых 0,5 с полные. Камера бота у
  присутствующих наблюдателей оседает за 144–226 мс (один кейс 522–547 мс — первое тело, поздняя обработка спавна);
  опоздавший 81/81 в ±1 см. Дрейф запястий 3–9 мм, ствол↔луч 1,5–2,1°. Трафик бота у клиента 785–790 Б/с (−12%
  к attempt-7). Учёт без форков, ошибок 0. Технически принято bots.
